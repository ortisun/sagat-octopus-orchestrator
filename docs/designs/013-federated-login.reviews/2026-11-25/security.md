Counts: Blocker 3, Major 13, Nit 9

1. **Blocker. Technical Plan 4 (Begin, Complete, Renew), Requirement 013-009, Requirement 013-018, Architecture decision 0141 decision 7. Login cross-site request forgery through a connection the attacker controls.** `GET /v1/auth/authorize?...&organization=<tenant>` is a plain top-level GET any site can send a browser to. The browser binding proves only that the attempt started in this browser, not that the person or the Studio started it. Complete sets `__Host-sagat_signin` at the provider callback, before the client checked its `state` or showed the PKCE verifier. Attack: any tenant administrator controls a connection; the attacker's page sends the victim to authorize for the attacker's tenant; the attacker's provider authenticates the victim silently as an identity the attacker owns; the callback sets the session cookie; the Studio refuses the foreign `state`, but the cookie stays; on the next reload the Studio renews without a redirect and signs the victim into the attacker's tenant, overwriting the victim's own session. People then type secrets and code into a tenant the attacker reads. An unsolicited SAML response that may start a service-provider-initiated sign-in is a second trigger. Fix: create the session and set the cookie only at `POST /v1/auth/token`, when the client presents the code and its PKCE verifier; never silently replace a live session cookie for another tenant or subject; the Studio refuses a renewed token whose tenant differs from the one the person chose and shows the tenant; an unsolicited SAML response answers a page with a button, not an automatic redirect; test `a_sign_in_started_by_another_site_establishes_no_session`.

2. **Blocker. Technical Plan 4 (Exchange, Renew "Studio and apps"), Requirement 013-005, Requirement 013-018, Decision 013-004. The `apps` client receives platform access tokens in apps-origin script.** Architecture decision 0062 decision 5 and feature 027 (FR-027-014, FR-027-023, SC-027-007) say no issuer token exists in apps-origin script. The design lets `apps` call `POST /v1/auth/token` and `POST /v1/auth/session/token`, both returning access tokens with the viewer's full authority, which defeats the narrowing; renewal from the apps origin needs a credentialed CORS answer, which breaks Decision 013-004's preflight argument; the apps host may be the public-forms host and same-site with the Studio, so the `SameSite=Lax` cookie travels. Fix: `client_id=apps` codes are redeemable only in process by the apps session-creation route and `/v1/auth/token` refuses them; renewal is Studio-only, with no CORS on any `/v1/auth/` route; each code is bound to its `client_id`; contract test `no_route_returns_a_platform_token_to_the_apps_origin`.

3. **Blocker. Technical Plan 4 (Revocation set), Requirement 013-019, Gap 013-003, Non-functional requirement 013-001. The revocation poll loses revocations, and the stated bound is false.** A poll reading rows "newer than its last read" is a timestamp watermark; a revoking transaction stamps `revoked_at` at its start and may commit after a poll advanced past that stamp, so no later poll sees the row (likely for SCIM transactions of up to 1,000 operations, or with process clocks and skew). Failing closed only after three missed intervals serves revoked tokens for about 40 seconds, not 10; Gap 013-003 contradicts the plan and itself. Purging at exactly the token lifetime ignores the verifier's leeway (30 seconds) and the poll interval. Fix: each poll re-reads every row younger than token lifetime plus leeway plus one interval (bounded by the purge), or keeps an overlap window larger than the longest writer transaction plus skew; load the full set before serving the first platform token; fail closed when the set is older than one interval plus a stated margin, and write that number in Requirement 013-019 and Gap 013-003; the platform verifier enforces a 300-second maximum lifetime of its own instead of `AuthConfig::max_token_lifetime` (3,600 seconds); test `a_revocation_committed_behind_the_watermark_is_still_seen` with a held transaction.

4. **Major. Requirements 013-001, 013-010, 013-026, Technical Plan 4. Disabling a connection or tightening its policy leaves existing sessions working.** Nothing revokes the sessions of a disabled, deleted or reset connection, or of a raised authentication context; nothing makes renewal, refresh or silent issuance re-check the connection is active, the session's context meets the requirement, the membership is active and the tenant's federated-only setting. Disabling a compromised provider would leave Studio sessions renewing for 24 hours and CLI refresh tokens for 7 days. Fix: disabling, deleting or resetting a connection revokes its sessions in the same transaction; raising the context revokes the sessions that do not meet it; renewal, refresh and silent issuance re-check the four conditions and refuse with `SESSION_REVOKED` or `AUTH_CONTEXT_REQUIRED`.

5. **Major. Requirements 013-016, 013-019, CUJ 3. Suspension stops only bearer requests that pass through `authenticate`.** Other paths resolve a subject without it: feature 027 app sessions, feature 018 schedules acting for `authorizedBy`, feature 026 links rechecked against their owner, stream and blob deadlines derived from `token_expires_at` (`blobs.rs`, `routes/execution.rs`). A deprovisioned person's schedule keeps firing, app sessions keep invoking, links keep accepting. Fix: list every path that resolves a membership; require `status = ACTIVE` in each through one store method; a SCIM deactivation also revokes 027 app sessions in its transaction; extend the revocation tests to app sessions, schedules and links.

6. **Major. Requirements 013-004, 013-011, 013-015, Architecture decision 0142 decision 1. The stable identifier is not held stable, which lets an e-mail address act as the link.** SAML accepts any name identifier format, including `emailAddress` and `unspecified`. SCIM matches by `userName` (usually the mutable e-mail) or `externalId`, and a `PUT` can change it, re-pointing a membership. Entra ID's OIDC `sub` is pairwise and never equals SCIM's `objectId`, pushing administrators to e-mail subjects. Fix: refuse `emailAddress`, `unspecified` and `transient` at activation unless an immutable attribute is configured; an OIDC connection names its subject claim from a closed list (`sub`, or `oid` with `tid` for Entra ID); the SCIM matching attribute is immutable (a replace that changes it is refused with `mutability`); test that a SCIM `PUT` changing `userName` changes no link.

7. **Major. Requirements 013-003, 013-012, the Google Workspace and Entra ID guides. Shared issuers admit anyone.** Google's issuer is shared by every Google account; Entra ID's `common` and `organizations` endpoints by every Entra tenant, with `{tenantid}` in the issuer inviting a special case. No tenant restriction claim (`hd`, `tid`) is required, the domain limit is optional, and it reads an e-mail without `email_verified`; Entra ID's `email` claim is user-editable (the published "nOAuth" takeover). With just-in-time provisioning any Google user or any Entra user who sets `email` becomes a member. Fix: refuse multi-tenant issuer templates; for known shared issuers require a configured `hd` or `tid` checked on every ID token and refuse activation without it; the domain limit reads only a verified e-mail and never Entra's `email`; refuse just-in-time provisioning on a shared issuer without a tenant restriction.

8. **Major. Requirement 013-001, Technical Plan 3. Changing a connection's issuer or entity identifier keeps every identity link.** Identities are keyed by (tenant, connection, subject), and subjects are unique only per issuer, so after a change the new provider's subject `123` signs in as the old provider's member `123`. Fix: make the issuer and the SAML entity identifier immutable (a new provider is a new connection; links move only by audited action), or add the issuer to the key and orphan old links on change.

9. **Major. Requirement 013-013, Technical Plan 6, Architecture decision 0142 decisions 4 and 5. Group-to-role mapping turns a claim into durable authority and is not scoped to its connection.** A role computed from assertion groups is written to `memberships.role` and stays after the groups stop conferring (an assertion group mapped to `admin` keeps the person `admin`), the "claim authorizes by itself" that FR-029-009 forbids. Rules are not scoped to their connection's groups: a less-trusted connection asserting another connection's mapped group value can promote a member linked through both; a sign-in through either connection recomputes the role; connection B's SCIM can suspend a membership connection A also links. Fix: compute mapped roles from SCIM groups only, or store a mapped role with its source and expiry and fall back to the default when its assertion groups stop conferring; rules match only groups of their connection; one owning connection per membership for mapping and SCIM lifecycle; test with two connections.

10. **Major. Requirement 013-020, Architecture decision 0142 decision 2. An administrator can impersonate another member.** `POST /members/{subject}/identities` links any external identity to any subject, including another administrator's, without the target's consent or fresh authentication; approval policies name subjects, so separation of duties falls and the audit names the wrong person. Fix: linking to an existing subject happens only inside a sign-in by that subject; the administrator route can unlink and pre-provision but never attach an identity to a subject that already has one or to an `admin` subject; require recent authentication (`max_age` or a fresh `AuthnInstant`) for linking, enabling federated-only and creating SCIM tokens.

11. **Major. Requirement 013-018, Architecture decision 0140 decision 3, Technical Plan 4 (Verify). The audience and token type of platform tokens are not fixed.** If the sign-in service issues ID tokens with the same key and `iss`, the API could accept them as access tokens (the `typ` check is off by default); the `aud` is unspecified. Nothing refuses a deployment issuer equal to the platform issuer; nothing reserves the `user:` prefix against deployment-issuer tokens, so a deployment token naming `user:<uuid>` bypasses the session. Fix: access tokens carry `typ: at+jwt`, `aud` the API's resource identifier and `client_id`, all required by the platform verifier; ID tokens, if any, carry another `typ` and the client as audience; start-up refuses equal issuers; refuse deployment-issuer tokens for `user:` subjects.

12. **Major. Requirement 013-024, Technical Plan 5. The guarded egress client cannot do what the design says, and fetches are not bounded per connection.** `EgressPolicy::check_destination` (`crates/domain/src/egress.rs`) is allowlist-only; there is no "any public address" mode, so the new guard is unspecified. Unauthenticated authorize calls can make the platform fetch tenant-chosen URLs on demand, and random `kid`s force key-set refreshes. Fix: specify a new guard (any name, every resolved address classified and refused unless global; allowlisted hosts may resolve to private ranges but never loopback, link-local or metadata; port 443 unless listed); cache discovery and key sets per connection with a minimum refresh interval; the runbook says `SAGAT_IDENTITY_ALLOWED_HOSTS` is deployment-wide.

13. **Major. Requirement 013-025, Technical Plan 2. Key and secret placement is unspecified, and the existing store resolves secrets to workflows.** Feature 017's secrets are namespace-scoped and resolved to execution capabilities; a deployment-wide signing key and a tenant-level client secret have no namespace; the design does not name the mount, path or policy or keep workflow resolution from reading them, and key-value storage hands every process an exportable key that signs for every tenant. Fix: a separate mount and policy for identity material that no feature 017 reference can name; prefer OpenBao Transit signing with a non-exportable key; disjoint key sets for the platform issuer and the `private_key_jwt` keys, and the API never verifies with a connection key.

14. **Major. Requirement 013-022, Technical Plan 8. Domain claims leak other tenants.** If creating a challenge answers `DOMAIN_CLAIMED`, a tenant administrator learns which companies use the deployment. Fix: creating a challenge always succeeds; the refusal comes only at verification, after the DNS record proved control; audit in the claiming tenant; cross-tenant battery case.

15. **Major. Architecture decision 0141 decisions 3 to 5, Technical Plan 5. The SAML profile is incomplete and partly self-contradictory.** Destination and `InResponseTo` belong to the Response, so when only the Assertion is signed they cannot be "read from the verified element only"; the design must say which unsigned Response values are compared by equality and that nothing else is read outside the verified element. Missing checks: `StatusCode` `Success`; subject confirmation `Method` `bearer` without `NotBefore`; the `Signature` an immediate child of the element it signs with `Reference` `#` plus its `ID`; at most one `Signature` per element, both verifying when both are signed; the Assertion a direct child of a signed Response; `KeyInfo` ignored for key selection; `#WithComments` refused by name; Assertion `Issuer` equal to the Response `Issuer` and the connection's entity; an `AuthnStatement` present; RSA keys at least 2,048 bits; the accepted `NotOnOrAfter` capped (10 minutes) so the replay store is bounded; the body size limited before base64 decoding. The "SHA-1-only certificate" check of Requirement 013-004 is mis-aimed: the XML signature algorithm and the key size matter for a pinned key. Fix: add each to the profile and the corpus with its refusal reason.

16. **Major. Requirement 013-006, Technical Plans 4 and 8. Unauthenticated sign-in endpoints let anyone deny a tenant its sign-ins.** A per-tenant discovery budget can be exhausted by anyone; every authorize call writes an attempt row kept an hour, with no ceiling. Fix: limit by address and globally; a per-tenant limit admits requests with a live attempt cookie or session first; cap the attempts table (refuse with `503` before inserting) and purge by the 10-minute expiry.

17. **Nit. Requirement 013-021, Technical Plan 4 (Break-glass).** Federated-only must exempt workers and runners by membership role, never by a claim; the break-glass audit and alert are per request (collapse per `jti`, and a failed audit write refuses the request); state that break-glass bypasses the required authentication context.

18. **Nit. Technical Plans 3 and 4, authorization codes.** No table holds the 60-second code; store it as a hash bound to `client_id`, `redirect_uri` and the PKCE challenge (RFC 6749 section 4.1.3); a second use revokes the session it produced.

19. **Nit. Requirements 013-005, 013-026, CLI loopback.** The loopback redirect is `http` to the literal `127.0.0.1` or `[::1]` (not `localhost`, RFC 8252 section 8.3) with an exact path; a CLI sign-in does not set `__Host-sagat_signin` in the browser.

20. **Nit. Requirement 013-030. Provider error text reaches the Studio.** The Studio prints the callback's `error_description` verbatim (`oidc.ts`); the broker never forwards a provider's `error` or `error_description` to a client redirect, only closed reasons and the trace identifier.

21. **Nit. Claims about today's code and consistency.** "The Studio's existing OIDC code signs in unchanged except for the issuer" is not true: `startLogin` sends a fixed parameter set without `organization` or `login_hint` and makes `state` and PKCE in the page, so a discovery form post cannot carry them. "The content security policy needs no change" is doubtful: the Studio sends `form-action 'self'`, which Chromium applies to the redirect chain of a submission, so the discovery-to-provider redirect would be blocked; state the policy of the sign-in service's own pages. Architecture decision 0140's "a platform token whose tenant claim differs from its connection's tenant is refused" cannot be checked without a session read; restate it as a signer test. The key-set code maps every RSA key to RS256 (`jwks.rs`), so PS256 needs a client that does not inherit that mapping.

22. **Nit. Requirements 013-001, 013-004, 013-021. SAML certificate rotation fights the lockout guard.** Adding a rotation certificate returns the connection to `DRAFT`, refused for the only active connection of a federated-only tenant; let adding or removing a certificate (keeping one valid) leave the state, audited.

23. **Nit. Technical Plan 4, Requirements 013-015, 013-017. SCIM and callback scoping.** `{connection}` in the callback and metadata paths is the global identifier, not the slug; a SCIM path naming a connection must equal the token's (else `404`); `uniqueness` conflicts scoped to (tenant, connection); group `members` resolve only within the token's connection; the `eq` filter parser bounded with a closed grammar; `roles` and `entitlements` stated as ignored.

24. **Nit. CUJ 1, Requirement 013-001, the test sign-in.** A test sign-in through a `DRAFT` connection provisions nobody, links only to the testing administrator's own subject after confirmation, and produces no session usable for the API.

25. **Nit. Requirement 013-006. Enumeration is broader than the test covers.** The identical-answer test must cover `GET /v1/auth/authorize?organization=` too; an active connection is still revealed by its redirect and provider host, and the chooser shows connection names; record it as a gap.

The reviewer confirmed the design's other descriptions of today's code: one issuer and audience in `AuthConfig`, the four columns of `memberships`, the in-memory Studio token, and the development provider's JSON token route.

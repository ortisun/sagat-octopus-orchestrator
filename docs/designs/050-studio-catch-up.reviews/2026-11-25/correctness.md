1. **Major. Technical Plan 3 ("Where it lives"), Requirement 050-002, Task 050-3.** The registry names do not come from "the activated requirements the process re-reads on each heartbeat": `Member::decide` (`crates/application/src/instances.rs`) reads `requirements()` only when the beat's epoch differs from the gate's, and `register` returns only the epoch and what the process lacks. A replica started after an activation registers at that epoch and never reads the list, so it advertises without the name until the epoch moves; half a fleet can disagree indefinitely. The named test activates while the process runs and passes. Fix: read the requirement set after a successful registration and keep it beside the gate on every epoch change; red test `a_replica_started_after_an_activation_advertises_it` driving `register` then `beat` with no epoch change, never with sleeps. Confirmed in code.

2. **Major. Technical Plan 6, Requirements 050-010 and 050-012, Architecture decision 0144 decision 5.** With `decidable=true` a page of 2,000 scanned rows may return nothing, and the design does not say what the cursor carries; the existing list builds `nextCursor` from the last returned item (`crates/api-http/src/routes/primitives.rs`), which would end the list or rescan forever. The inbox does not say it follows cursors, so an empty first page reads as "nothing waits for you"; a refresh that continues from a cursor skips a new short-deadline approval; "decidable first" cannot sort across pages; `decidable=false` is undefined; the named test passes with any forward cursor. Fix: the cursor is the key of the last row scanned and never null while rows remain; the Studio follows cursors up to a stated number of requests per refresh and every refresh starts from the first page; define `decidable=false`; red test with 2,001 undecidable rows then one decidable row found in two requests. Confirmed in code for the cursor pattern; the inbox behaviour plausible.

3. **Major. Requirement 050-010, Technical Plan 6, Architecture decision 0144 "Enforced by", Task 050-4.** The ended-run rule is not in the domain: `decide` has no run state, and the adapter refuses first (`crates/infra-postgres/src/approval_progress.rs`) with its own list of terminal statuses. The property test over run states cannot be pure domain, the inbox needs a second copy of the rule, and `decide` replays a settled request under its key, so "equal" is undefined outside pending requests with fresh keys. Fix: `may_decide(&Principal, run_ended: bool)` with `decide` taking the same input, derived by the adapter from `RunStatus::is_terminal`; the property restricted to pending requests with fresh keys; an integration test of the inbox and the decision on one ended run. Confirmed in code.

4. **Major. Technical Plans 5 and 6 (decision retry; "a settled item shows its new status"), Task 050-10.** A decision on a pending approval of an ended run answers 503 (`RuntimeUnavailable` mapped to `unavailable`, `crates/api-http/src/error.rs`), which a client retries, so a Studio retrying with the same key loops; expiry skips the same rows (`expire` uses `lock_run`, the scheduler maps the refusal to `Skipped`), so such an orphan would stay pending in the new index forever. For an approval settled meanwhile, `decide` answers 409 `ALREADY_DECIDED` without a status, and the namespace list has dropped the row. Fix: a 409 code of its own (`RUN_ENDED`) that the Studio never retries; leave ended-run rows out of the inbox or show "the run ended"; on a decision error re-read `GET /runs/{runId}/approvals`; confirm every run end cancels its pending approvals, or add a cleanup. Confirmed in code for the 503 and the skipped expiry; orphans plausible.

5. **Major. Requirement 050-011, Technical Plan 6.** A request is decidable while `APPROVED` (`PublicationRequest::decide` checks `is_open`, `crates/domain/src/versioning.rs`) and publication recounts against the current policy, so after a policy rise an `APPROVED` request needs another approval yet appears in nobody's inbox. Fix: list open requests that do not satisfy the current effective policy (`PENDING`, and `APPROVED` with fewer approvals than required); put the open-state clause in `may_decide`; test a policy rise after an approval. Confirmed in code.

6. **Major. Technical Plan 6 (publication requests), Requirement 050-012.** The route has no order, cursor, scan bound or index; requests have no deadline; the only indexes are per workflow (`20261016000000_versioning.up.sql`), so a namespace listing scans every request ever made; the "already decided" clause needs `publication_decisions` per row. Fix: order by `requested_at, id` with a keyset cursor; a partial index `(tenant_id, namespace_id, requested_at, id) WHERE state IN ('PENDING','APPROVED')` with its `down`; decisions loaded per page in one query; a scan bound; a paging test across a supersede. Confirmed in code.

7. **Major. Requirements 050-014 and 050-009, Technical Plan 5.** Rejected Updates keep a durable receipt under their key (`updateRunState` commits `REJECTED` receipts for 422 and 409), and any change under the same key is 409 `IDEMPOTENCY_KEY_REUSED`; correcting a stale revision or a refused argument in the same dialog is refused until the dialog closes; changing a decision after a lost response the same. The named test resends an identical body only. Fix: reuse a key only to resend the identical body after a lost response, 429 or 5xx; a new key whenever the arguments, `expectedStateRevision` or the decision change, the fields frozen once sent; red test of a corrected resubmission after a 409. Confirmed in code and contract.

8. **Major. Requirement 050-003, CUJ 1, Technical Plan 4.** A codec problem names a node only by its bare id (`convert.rs`, `problems_of` in `crates/application/src/definitions.rs`), and the Studio resolves only root ids and `/nodes/N` pointers (`validationModel.ts`); a body approval `review` attaches to no node, or to a root node of the same id; the codec also stops at its first error. Fix: problems carry the body name (an additive field or a `/bodies/{name}/nodes/N` pointer on `DefinitionProblem`, which contradicts "nothing else changes in the engine"), or forbid reusing a root id inside a body; a test with colliding ids. Confirmed in code.

9. **Major. Technical Plan 5 (Iterations), Requirement 050-008, CUJ 4.** `RuntimeNode` has no iteration status; counting scoped instances counts a two-step body twice, a step routed by `onError` as a failure, compensations (`~c`) and reconciliations (`~r`) as their own results, `RETRY_WAIT` nowhere, and unadmitted iterations not at all. Fix: define iteration status from the contract (the `return` instance succeeded; a forward node failed with no handled route), group by `instancePath` and `nodeId`, count only forward instances and draw `~c` and `~r` beside their forward node, take "not started" from the owner's item count or a stated server field; tests with a compensation, a retry and an `onError` route. Plausible.

10. **Major. Requirement 050-004, Technical Plan 4, Task 050-6.** The red test cannot fail for its reason: a legacy node has an id and a type, so `readDocument` already keeps it at its index (`model/ir.ts`); only entries without id or type, or with a duplicate id, become extras appended at the end (`documentIO.ts`); body node arrays are not covered. Fix: a red test with an unreadable entry between two nodes and a duplicate-id entry, which fails today; the same rule and a test for body arrays. Confirmed in code.

11. **Major. Technical Plan 4 (replacement table), Requirement 050-005, Architecture decision 0143 decision 3.** The mapping produces nodes the schema refuses and drops data silently: legacy `next` and `onTimeout` are optional while `forEach` requires `next` and `approval` requires `onApprove`, `onReject` and `onExpire`; legacy `base` allows extra properties, free-text ids and unbounded `timeoutMs`, the new kinds do not; legacy `onError` and `foreach.timeoutMs` are not mapped; the legacy body subgraph is orphaned. Fix: map a value only when it passes the target member's schema, otherwise ask with the old value; ask for every absent required field; list every property that will not carry over before confirming; offer to move the legacy body subgraph into a new body. Confirmed in the schema.

12. **Major. Requirement 050-019, Technical Plans 3 and 8, Non-functional requirement 050-003.** With "built" taken only from `scripts.language.*`, a server without the field (0.2.x, another build's Studio bundle, an older replica in a rolling upgrade) leaves every language disabled. Fix: without the field, fall back to the languages 0.2 builds and let the build route decide; state when the Studio re-reads `GET /version` (at sign-in and on a refused build); a test against a response without the field. Plausible.

13. **Major. Requirement 050-021, Technical Plan 5, Task 050-9.** "Raw page text, never parsed" cannot hold: a page is `{items, nextCursor}`, the next page needs the cursor and the bound needs the count, and concatenated pages are not event lines, so the named test blesses the wrong file; 50,000 events at 200 per page is 250 charged admissions over about two minutes, and 429 and a still-appending run are unstated. Fix: parse each page and write one compact line per item; count events and bytes as written; on 429 wait for `Retry-After` and stop after a stated number of refusals; say "as of the last page read". Confirmed in the contract.

14. **Nit. Technical Plans 5 and 6, Requirement 050-009.** `approval_requests_run_idx` is `(tenant_id, run_id, opened_sequence)` without namespace or status, so the run-filtered page is ordered differently, its cursor has another key (bind it to its filter and refuse it with 400 elsewhere), the branch must check `namespace_id`, and the run view's join with `listRunApprovals` can misalign once approvals live in bodies. Fix: state the order and the cursor kind bound to the filter; a cross-namespace test; assert the rows-scanned metric with 3,000 earlier pending rows; or an optional `youMayDecide` on `listRunApprovals`.

15. **Nit. Technical Plan 6 (migration).** A plain `CREATE INDEX` takes a share lock that blocks every approval open, decision and expiry while it builds. Fix: `CREATE INDEX IF NOT EXISTS` with a runbook step to build it `CONCURRENTLY` first, as earlier migrations do.

16. **Nit. Architecture decision 0143 Consequences, Technical Plan 3.** "A server before the structured primitives never offers loops" is stale after the Blocker fix; against a server without the field the Studio offers loops, `switch` and `approval` anyway. Fix: correct it; say only kinds known to 0.2 are offered there, or that validation decides.

17. **Nit. Requirement 050-002.** "Present exactly when the answering replica would accept" contradicts "within one heartbeat" and Gap 050-001; the state is learned at the beat and kept while the registry is unreachable. Fix: "as of this replica's last successful beat".

18. **Nit. Technical Plan 5, Requirement 050-014.** Two tabs or two people each make their own key and both Updates apply. Fix: prefill `expectedStateRevision` with the revision last observed, so a second submission gets 409 `REVISION_CONFLICT`.

19. **Nit. Technical Plan 5, Requirement 050-009.** `decide` checks eligibility before replaying a receipt, so a person whose role was removed between a lost response and the retry gets 403 for a decision that committed; `youMayDecide` read across a role change can disagree between pages. Fix: treat 403 after a sent decision as "status unknown" and re-read the run's approvals; document `youMayDecide` as a point-in-time hint the decision re-checks.

1. Major — The `EnvelopeKeys` port cannot carry the cache key, and the cache refresh makes the Transit adapter read every inventory table
   Where: docs/designs/015-opentelemetry-and-openbao.md Technical Plan 4 (lines 870-877, 897-898, 906-909) against Technical Plan 8 (lines 1260-1267, 1297-1301); Task 015-13.
   What: The design says the cache lives inside the adapter `TransitEnvelopeKeys` and is keyed by (tenant, inventory entry, row id, `data_key_issued_at`). The port's `unwrap(tenant, wrapped, cache)` and `unwrap_batch(&[(TenantId, WrappedKey)])` carry none of those last three, so the adapter cannot build that key. `resolve_secrets` in the application "opens cached rows directly", but it cannot see a cache that lives inside an adapter. The refresh "reads each due entry's current wrapped key from its row", so an `infra-secrets` adapter would issue SQL against the tables of every inventory entry (`secret_versions`, and design 040's `audit_sinks`) and go around `ResealTarget`. This breaks Principle II (ports and adapters). As written, the cache either ends up keyed by the wrapped key, and a rewrap empties it (the opposite of Owner decision 2026-11-27-160), or the key adapter grows storage code for other features' tables.
   Correction: Add a `CacheKey { entry, row_id, issued_at }` to `Cacheable::Current` and to each batch item. Move the cache and its refresh into `crates/application` as a wrapper around `EnvelopeKeys`. The refresh reads current wrapped keys through a method each `ResealTarget` implements (for example `current_wrapped(row_ids)`). The wrapper exposes a cache lookup that `resolve_secrets` uses. Task 015-13 tests it at that layer.

2. Major — A new reason to close the serving gate, outside the registry's decision, with no reason code and no amendment to ADR-0082
   Where: docs/designs/015-opentelemetry-and-openbao.md section Key authority modes and passages (lines 108-121, 127-128, 260-264); Requirement 015-010 (lines 363-367); ADR-0152 decision 1; Task 015-18.
   What: Some gate closings come from comparing the configuration with `key_authority_state`, not from a missing registry capability. In `migrating`, a ring that holds a key whose check value is not recorded closes the gate. In `returning`, a ring that holds a recorded check value or id closes it. Today `ServingGate` has one decider, the registry member, which calls `open(epoch)` after each successful heartbeat (`crates/application/src/instances.rs:370-385`). A second check that runs after the heartbeat is either reopened by the next heartbeat or has to be built into the member's decision; the design says neither. ADR-0082 decision 3 and its amendments name the closing reasons (`BINARY_CAPABILITY_MISSING`, `REGISTRY_SILENT`, and `SCHEMA_TOO_OLD` added by ADR-0131), and the contract lists them (`specs/001-platform-foundation/contracts/openapi.yaml:5095-5099`). A closing for key authority has no reason, metric or alert, so an operator sees a replica answering `503` with nothing to explain it. ADR-0131 set the precedent that a new reason for closing the gate amends ADR-0082.
   Correction: Make the key-authority check an input of the member's decision in the same cycle: the gate opens only when the capabilities and the key-authority configuration both pass. Add a `details.reason` value (for example `KEY_AUTHORITY_CONFIGURATION`) to the contract's `UNAVAILABLE` reasons, with a gauge and an alert, and log the failing condition without key material. Record it as an amendment of ADR-0082, in ADR-0152 and in ADR-0082's Amendments section. Add a test to Task 015-18 that a heartbeat does not reopen a gate the mode has closed.

3. Major — Nothing checks that every sealed table is in the re-seal inventory
   Where: docs/designs/015-opentelemetry-and-openbao.md Technical Plan 5, the re-seal inventory (lines 996-1026); Task 015-34; ADR-0152 "Enforced by".
   What: The only test checks that each `ResealTarget` has a registered entry and that each entry has a `ResealTarget`. A feature that adds a ring-sealed column and registers neither is counted by no guard. Design 040's `audit_sinks` is such a case: it is sealed with today's `SecretCipher` until Task 040-22 (`docs/designs/040-ocsf-event-standard.md:559-561, 751`). In that case `finish-migration` counts zero, step 7 of the way in removes the ring, step 9 destroys it, and those values can never be opened again. Requirement 015-015 relies on the rule "every table that holds sealed values is an entry", and no check fails when it is broken (AGENTS.md rule 21).
   Correction: Add the smallest check: either a `scripts/check-architecture.py` rule that refuses a call of `SecretCipher::seal` or `EnvelopeCipher::seal` outside an allow-list mapping each site to a registered inventory name, or a privilege-audit row that reads `information_schema` and fails for any table with a sealed-column shape (`nonce` with `key_id` or `wrapped_key`) that is not in `key_authority_reseal_inventory`. Add a negative fixture and a row in docs/engineering/architecture-principles.md, and cite the check in ADR-0152 "Enforced by".

4. Major — Feature 032's key inventory still blocks a `transit` cell; the dependency is recorded only in this feature's register
   Where: docs/designs/015-opentelemetry-and-openbao.md Technical Plan 6 (lines 1150-1153); specs/015-opentelemetry-and-openbao/research.md:58 (Gap 015-006); specs/032-multi-region-failover/contracts/operator-cli.md:34-35, which is unchanged.

After step 7 of the way in, none of those keys exists, so that check blocks every failover of a `transit` cell. Add to Task 015-32 a test that feature 032's readiness check passes for a `transit` cell.

1. Major — The key port cannot supply the new cache key, and the cache refresh has no way to read rows
   Where: docs/designs/015-opentelemetry-and-openbao.md:870-876 (`EnvelopeKeys::unwrap`, `unwrap_batch`, `Cacheable`), 906-909 (`resolve_secrets` "opens `local` and cached rows directly"), 1260-1267 (the cache key), 1297-1301 (the refresh); Task 015-13 (1634-1640)
   What: The fix for design finding 2 keys the cache by (tenant, inventory entry, the value's row id, `data_key_issued_at`). However, `unwrap` receives only the tenant, the wrapped key and `Cacheable`, whose two variants carry no data. `unwrap_batch` receives only (tenant, wrapped key) pairs. So `TransitEnvelopeKeys`, which owns the cache, cannot build the key, and `resolve_secrets` cannot look up a cached row. The refresh also "reads each due entry's current wrapped key from its row" by row id. But `TransitEnvelopeKeys` is in `crates/infra-secrets`, which has no database access. No port is named for reading the current wrapped key of a row in any inventory entry, and design 040's `audit_sinks` is one such entry. The builder of Task 015-13 would have to redesign a port from Technical Plan 4.
   Correction: Give the identity to the port, for example `Cacheable::Current(KeyRef { entry, row_id, issued_at })`, and the same `KeyRef` on each `unwrap_batch` item. Name a port that `TransitEnvelopeKeys` uses for the refresh, for example `CurrentWrappedKeys::read(entry, &[row_id]) -> Vec<(row_id, WrappedKey, issued_at)>`. Implement it in `crates/infra-postgres` for each inventory entry, add it to the parts every entry must provide (Technical Plan 5) and state its grant to `sagat_app`. Add it to Tasks 015-10, 015-13 and 015-34.

2. Major — `finish-return` accepts the pre-migration signature made with the retired script-signing key
   Where: docs/designs/015-opentelemetry-and-openbao.md:164 (guard "zero artifacts without a local signature"), 1055 ("`finish-return` counts artifacts with no `local` row"), 423-424 (the migration copies every existing signature as a `local` row), 237-238 (a fresh script-signing key on the way back), 433-435 (`scripts resign` signs with "the local key" in `returning`)
   What: The signature table is insert-only. So every artifact built before the first migration keeps, forever, a `local` row made with the old script-signing key. Way-back step 2 replaces that key with a fresh one, so after the return no runner trusts the old rows. They still satisfy the guard, though, and `finish-return` can commit with `scripts resign` only partly run or never run. Those artifacts then run only on their Transit signature, and they stop running once Transit is removed at way-back step 7. This breaks Requirement 015-015 (no passage finishes while an artifact still depends on the keys it leaves). The guard is SQL over the state row, and the database records no script key id, so it cannot tell the old key from the current one.
   Correction: At `begin-migration`, record the id of the script-signing key the control plane holds in a grow-only `key_authority_state.retired_script_key_ids`, written by the same function as the ring's values. Make `finish-return` count artifacts with no `local` row whose `key_id` is outside that set. In `returning`, close the gate of a control plane whose script-signing key id is in the set. Add a test to Task 015-14 or 015-15 in which `finish-return` is refused while an artifact's only `local` row is the pre-migration one.

3. Major — Reusing an archived key on the way back closes every gate at `begin-return`, and nothing refuses it first
   Where: docs/designs/015-opentelemetry-and-openbao.md:135 (`key-authority-return-v1`), 163 (`begin-return` checks only that the mode is `transit`), 237-264 (way-back step 2; the freshness check applies only "in `returning`"), 128; Task 015-18 (1711-1716)
   What: The freshness check runs only once the mode is `returning`. Under `transit`, a process whose new ring reuses a recorded key id, or old key material under a new id, stays open and still lists `key-authority-return-v1`. So the registry requirement can be recorded and `begin-return` succeeds. Within one heartbeat every such process closes its gate. If the operator built the ring from the archived copy, which is exactly the mistake the check exists to catch, the whole fleet stops serving. Requirements 015-010 and 015-015 promise no downtime, and `begin-migration` refuses in the matching case "instead of being stranded". `begin-return` has no such guard.
   Correction: A control plane or engine should list `key-authority-return-v1` only when no key of its ring has a recorded check value or id. It already reads the state row after every heartbeat. With that rule, a reused ring blocks the registry requirement and therefore `begin-return`. Optionally, `begin-return` should also refuse while a live registry row's `ring_check_values` overlaps `retired_ring_check_values`. Add a Task 015-18 test: with a reused ring, `begin-return` is refused and no gate closes.

4. Major — ADR-0152 decision 1 forbids the offline ring that way-in step 9 requires
   Where: docs/adr/ADR-0152-openbao-transit-holds-the-platform-keys-and-each-custody-has-its-own-mount-and-token.md:31-33; docs/designs/015-opentelemetry-and-openbao.md:223-231, 635-638, 1444
   What: The ADR says no platform key MAY exist outside OpenBao once `key-authority-ring-absent-v1` is recorded (step 8). The design keeps one copy of the ring offline after step 8, until the last backup older than `finish-migration` expires. It says that "no platform key outside OpenBao" holds only after step 9. An operator who follows the ADR destroys the ring at step 8 and can no longer restore those backups. The decision record and the design disagree on a security rule. The same ADR line also still writes "the requirement" instead of "registry requirement" (design finding 8).
   Correction: Rewrite decision 1 to say what the design does. Once the registry requirement is recorded, no platform process holds a local key. The ring is kept only offline, under a custody separate from the pre-migration backups, until the last of them expires, and is then destroyed. Write "registry requirement" in full.

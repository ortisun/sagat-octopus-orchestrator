# Security review of design 041's writer-owned leases (D041-117, D041-118)

Reviewer: `security-reviewer` subagent, read-only, on `ba47aa81` and the merge `5458820b`. Saved verbatim.

No Blocker. 2 Major, 6 Minor, 1 Nit, and 3 suspicions I could not confirm.

## Verified findings

**Major 1. At the limit, the refill wait queues a tenant's reports on pooled connections, and the bound *b* is too small for that case.** ADR-0097:59-60 and :93-103; `docs/designs/041-step-logs.md:1178-1189` and :1236-1240; `specs/041-step-logs/data-model.md:246-253`. *b* assumes every backend ahead holds the usage row for a finalizer's 4.5 ms, with a single refill holder (32.7 ms + 4.5 ms). The design says that at the limit "a refill comes about once per charge"; a refill takes the row mid-report and keeps it until that report commits, so the waiters ahead are refills of ~37 ms each, and about 54 same-tenant refills already exceed *b* = 2 s, while the declared environment allows 160 pooled connections. The model also omits `sagat_quota_lock_log_usage`, executable by `sagat_app` (`20261024000000_durable_quotas.up.sql:572`) and reached through `content_usage.rs:245-274` from `scripts.rs`, `dispatch.rs:251` and `connectors.rs:626`, which holds the row across round trips from Rust. Scenario: a tenant at its quota runs many workers whose reports carry logs; each carry waits up to *b* holding its run lock and a pooled connection; past *b* it fails with `tenant_step_log_refill_wait`; the worker resends, so the load repeats; other tenants on the same replicas wait for pool connections. Before the leases, the at-limit holder held the row only from its finalizer to the end of its commit (p99 4.5 ms); now it holds it for the rest of the report. This breaks the ADR's own rule that "a report must never wait under its run lock for another … replica's or attempt's commit". Smallest fix: before locking, read U = S + Σ `used` without a lock and, when L − U < *n*, refuse at once with `tenant_step_log_quota_exceeded` (a refusal can never overshoot, so exactness holds); cap a tenant's concurrent refill waiters (e.g. *k* slots via `pg_try_advisory_xact_lock`) and answer `step_log_quota_busy` immediately past the cap; re-derive *b* with refill holders and `take_log_prefix` holders included; add a held-lock test with more than 60 concurrent refills at the limit.

**Major 2. The test switch `sagat.step_log_refill_wait` can disable the bound.** `tests/performance/scalability-ha/step_log_spike.rs:323-327`: `v_bound := coalesce(nullif(current_setting('sagat.step_log_refill_wait', true), ''), …)` then `IF v_prev = '0' OR v_prev::interval > v_bound::interval THEN set_config('lock_timeout', v_bound, true)`. With the setting `'0'`, `'200ms' > '0'` is true, so `lock_timeout` becomes 0 — no lock timeout at all, and it also overrides the ingest's lower 200 ms, which the design says is always kept. Any value above *b* turns the bounded refusal back into a wait, against ADR-0027's rule that a session flag may only turn a wait into a refusal; a non-interval value raises an unmapped `22007`. Custom `sagat.*` settings can be set by any role; `sagat_app` can set it per transaction, per session, or permanently with `ALTER ROLE sagat_app SET …`. Not affected: no admission check reads it, so it cannot admit more bytes. Design gap: data-model §3b does not say whether the built refill reads this setting, so T041-5 could copy it. Fix: state in §3b that the built function reads no session setting; change the 100 ms test to `SET LOCAL lock_timeout = '100ms'` (the function already keeps a lower caller value); for the 60 s held-lock tests use `ALTER FUNCTION … SET` in the test database; add a test that sets `'0'` and `'1h'` and expects the wait to stay at *b*.

**Minor 3. The idle reclaim holds leases without the step-log fence, so a limit change's `NOWAIT` can fail.** data-model.md:261-263 against :265-266 and :274-277. The limit-change trigger's `FOR UPDATE NOWAIT` on leases relies on "holding a lease always means holding that fence"; `reclaim_idle` locks leases under the usage row only. A change to a tenant's limit or ceiling during the purge pass's reclaim of that tenant fails with a bare `55P03` and no constraint name. Fix: `reclaim_idle` tries the step-log fence shared first and skips the tenant otherwise; add a held-transaction test.

**Minor 4. Several definer functions are missing from the privilege lists, and `reclaim_idle` takes its interval from the caller.** NFR-041-SEC (design :1889-1894) and the Grants paragraph of design section 3 (:1296-1303) omit `sagat_quota_step_log_reserve`, `sagat_quota_step_log_counters`, `sagat_quota_step_log_reclaim_idle` and `sagat_quota_step_log_refill_bound`; data-model §4 (:324-331) omits `reclaim_idle` and `refill_bound`; the sequence `step_log_quota_refill_wait_timeouts_seq` (data-model :224) is in no revoke or audit list (no default privileges in the migrations, so nothing grants it today). The purge pass runs as `sagat_app` and would call `reclaim_idle(tenant, idle)`: with `idle = '0'` it folds every unheld lease of any tenant — exactness survives, but every writer of that tenant then refills, feeding Major 1. The purge also has no way to find tenants with idle leases, since `sagat_app` cannot read the lease table. Fix: fix the interval inside the function (or clamp to ≥ 10 minutes); add a tenant-less variant that picks tenants itself; list every function and sequence with its grant in NFR-041-SEC and §4 and add each to the privilege audit.

**Minor 5. §4 wrongly says `sagat_app` has no privilege on the usage table.** data-model.md:331 says "beyond what it has on the table today (none)"; `durable_quotas.up.sql:566` grants SELECT on `tenant_retained_usage` to `sagat_app`. So `sagat_app` can read `step_log_bytes` (S, which may be negative) and `step_log_leased_bytes` directly; any path reading S instead of the accessor shows the wrong usage, and one converting S to unsigned fails with a `corrupt_usage` Internal error. Fix: correct the sentence; add a source-text check that only `sagat_quota_step_log_usage` reads either column (or a column-level revoke, replacing the table-level SELECT with column grants).

**Minor 6. `lock_timeout` is not an end-to-end bound.** Spike :330-341, data-model :248-253. `lock_timeout` applies per acquisition; a queued `SELECT … FOR UPDATE` waits for the tuple lock then the holder's xid, and the insert path adds more, so a real wait can be ~2*b* or more, near the 5 s statement timeout at *b* = 2 s, while the startup check only requires *b* < statement timeout; a `57014` is neither named nor counted, so the alert misses it. Fix: keep a deadline (`clock_timestamp()` + *b*) and give each attempt only the time left, or check 2*b* plus margin against the statement timeout; add a test with two waiters ahead.

**Minor 7. The timeout counter cannot tell a bound breach from a caller's own lower timeout.** Spike :337-340: an ingest's 200 ms, or any `lock_timeout` a caller lowers (e.g. `1ms`), raises the same `tenant_step_log_refill_wait` and advances the same sequence. The "any increase over 5 minutes" alert then fires on normal ingest contention near the limit (the earlier design measured 1,075 such ingest timeouts at 8 × 128) and cannot point to the tenant. Fix: two sequences or a closed label `bound="refill"|"caller"`; a structured store warning with the tenant id where the platform's logging rules allow.

**Minor 8. The `charged_at` index prevents HOT updates, and the spike measured the budget without it.** data-model.md:223 creates `step_log_quota_leases_idle_idx ON (charged_at)`. Every charge sets `charged_at`, so every charge is a non-HOT update writing both indexes; fill factor 50 then buys nothing and the lease rows bloat. The spike's table (`step_log_spike.rs:279-283`) has no such index, so the pinned budget line omits those index writes. Fix: drop the index (a per-tenant primary-key-prefix scan covers at most `max_connections` rows), or BRIN (HOT-compatible since PostgreSQL 16).

**Nit 9. D041-117 says the new telemetry is per tenant.** research.md:128: "Telemetry gains the lease rows per tenant"; ADR-0097 decision 8 and data-model.md:295 say no tenant label. Reword so nobody builds a tenant label.

## Suspicions (not verified)

- **S1. Prepared transactions.** With `max_prepared_transactions` > 0, a prepared transaction keeps its lock on the backend's own lease after the backend moves on; the refill's `FOR UPDATE` on that lease (spike :355-356) then waits while holding the usage row and the whole tenant stalls. Check `SHOW max_prepared_transactions` on each target; fix with a startup check that it is 0, or take the own lease `NOWAIT` in the refill.
- **S2. A possible deadlock through `take_log_prefix`.** Its callers hold the usage row then commit through the log finalizer; if that finalizer, or any later statement in those transactions, takes the step-log fence, it deadlocks with a limit change holding that fence exclusively and waiting for the usage row. Check which fences `sagat_quota_flush_deltas` takes for the log class once T041-5 changes it.
- **S3. Retry storms.** I did not check whether the SDKs retry `Unavailable`/`step_log_quota_busy` with backoff and jitter; without it Major 1 amplifies. The counters are published only from the purge pass, so a purge cadence longer than 5 minutes may hide increases from the alert window.

## Classes checked with no finding

- **Tenant boundary:** every lease statement filters by `p_tenant` and `writer = pg_backend_pid()` (spike :346-380, :391-397, :418-420, :437-441, :473-478); reclaims stay inside the tenant; the primary key `(tenant_id, writer)` keeps one backend's leases for different tenants separate; a reused pid inherits room only within the same tenant; `reserve` locks only the calling backend's own lease. No tenant can charge, reserve, lock, reclaim or strand another tenant's lease or room; cross-tenant impact is limited to the shared pool (Major 1).
- **Admitting more than the quota through settings:** neither `lock_timeout` nor `sagat.step_log_refill_wait` reaches the L, S or G checks; a lower `lock_timeout` only refuses.
- **Information exposure:** raised messages carry no ids or values (spike :339, :343, :372, :375, :457); `store_error` keeps the text from clients (`crates/infra-postgres/src/identity.rs:718-725`); `application_name` names only the replica; the counters carry no tenant label (Nit 9 aside).
- **SECURITY DEFINER hygiene as specified** (data-model :235-238): pinned `search_path`, `public.`-qualified names, revokes from PUBLIC and `sagat_app`; the spike's functions are not definer functions, as ADR-0097:35 admits.
- **Lease-row growth:** at most the backends that charged for a tenant within the idle interval, so at most `max_connections` rows per tenant.

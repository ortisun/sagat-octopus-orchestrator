# Correctness review of design 041's writer-owned leases (D041-117, D041-118)

Reviewer: `correctness-reviewer` subagent, read-only, on `ba47aa81` and the merge `5458820b`. Saved verbatim.

No Blocker. The exactness invariants I1–I5 hold on every path I traced, and I found no lock cycle among the parties you listed. The real problems are in the bound *b* and its evidence, the held-room bound as documented, the idle reclaim breaking the limit change's `NOWAIT`, cross-document drift, and several tests that cannot fail for the property they name.

## Major

**1. *b*'s derivation assumes at most one refill ahead; cold start and the near-limit regime violate that, and the fourth run cannot detect the consequence.** `step_log_spike.rs:304-310`, design 041:1178-1194, research.md D041-118 (line 129). *b* = (max_connections−1)·4.5 ms + one refill holder + 4.5 ms, but a refill holds the usage row until its report commits, and *r* = 32.7 ms is the fast path's p99 — a refill holder is by definition on the slow path, whose p99 ADR-0097's own evidence puts near 95 ms. Scenario: at 8×128 with 160 backends, every backend's first charge is a refill (also after a server restart or with unfilled pools; the fourth run's own text expects "one per backend per row"); those refills queue on one row, each held until its report commits; the 167 ms of slack in ⌈1,832.7 ms⌉ = 2 s covers about two slow-path holders beyond the assumed one. Near the limit, ADR-0097's Consequences say "about one refill per charge", so the queue is made of refill holders. Past *b* the report fails UNAVAILABLE and is resent, possibly repeatedly — a step-log charge holding up a terminal state, which ADR-0095 decision 5 rules out. And the fourth run cannot see it: the harness never reads `step_log_refill_wait_timeouts`, a carry error leaves `on_report_commit` as a StoreError (`crates/infra-postgres/src/execution.rs:5666-5668`) and the worker resends, and `CarryHook` increments `calls` but no outcome (`step_log_spike.rs:1304-1307, 1484-1517`), so "a refill past *b* voids the round" cannot fire. No test queues more than one refill holder; `the_refill_bound_follows_max_connections` re-derives the same formula. Fix: make the harness report the timeout sequence delta and `calls − Σ outcomes` per round; re-derive *b* with refill holders in the queue, or take refills off the report path (pre-lease at connection checkout, or option 1e). Confidence: derivation error confirmed in documents; timeouts in the fourth run plausible.

**2. The held-room bound L·C(2k,k)/4^k is not an invariant, yet the design and G041-023 say "only past that is a charge refused as held".** Design 041:1207-1212, research.md G041-023 (line 157), ADR-0097 decision 4 (end). The code (lines 365-377) gives that bound only for k consecutive fresh grants from the same starting free room with no other commits between. Integer division only shrinks grants; A counting dead or zeroed rows only shrinks grants; the *n* part does not break it either, because a refill holds the usage row until its commit, so its *n* is committed usage before anyone else looks. It breaks with stale grants: L = 64 MiB, sixteen writers each granted 1 MiB while free room was large; other writers' commits then raise committed usage to L − 16 MiB − 1 KiB; while those sixteen are mid-transaction (fast path, lease locked), a 3,280-byte carry on another writer is refused `held` and answered mark-only — the formula claims ≥ 64 MiB·C(32,16)/4^16 ≈ 9.0 MiB stays chargeable; the truth is 1 KiB. That is exactly the near-limit, busy-writer regime where held refusals happen. The test `room_held_by_open_writers_is_bounded_by_the_grant` only runs with committed usage 0, n = 1, and nothing committed between grants (I verified it reaches exactly 205,920). Fix: state the bound as F₀·C(2k,k)/4^k for consecutive fresh grants only and the general one as Σ over held leases of min(1 MiB, share at grant time); add a test that commits usage between grants. Confidence: confirmed by arithmetic against the code.

## Minor

**3. The idle reclaim locks leases without the step-log fence, so a concurrent limit change fails with `55P03`.** `step_log_spike.rs:386-401` vs the trigger at 472-473. Data-model §3b (reserve) states "holding a lease always means holding that fence, which the reclaim's NOWAIT relies on"; the idle reclaim breaks that. Scenario: the purge pass is between `FOR UPDATE SKIP LOCKED` of an idle lease and its commit; an administrator changes `tenant_step_log_bytes`; the trigger gets the fence exclusively, then `FOR UPDATE NOWAIT` on leases raises `55P03` and the quota change fails as Unavailable. No test combines an open idle reclaim with a limit change. Fix: the idle reclaim tries the fence shared first (skip the tenant if not), or the trigger locks the usage row then the leases, waiting (safe: the fence excludes every other lease holder, and the idle reclaim waits for nothing after the usage row). Confidence: confirmed in code.

**4. Several tests cannot fail for the property they name.** `a_backend_waits_on_a_fence` (`step_log_leases_tests.rs:142-158`) counts advisory waits cluster-wide; the server is shared and each test gets its own database (`tests/support/mod.rs:249-260`), so another test's backend can satisfy it, and test (c) then commits the release before the limit change is queued and still passes. Filter by the change's pid, or at least `datname = current_database()`. `the_refill_bound_follows_max_connections` (lines 1537-1562) recomputes the SQL formula in Rust — it only catches a typo, and the test server runs with the default max_connections 100 (`support/mod.rs:158-165`), so the `== 400` branch never runs. The default bound is never exercised: every waiting test sets `sagat.step_log_refill_wait` (60 s via `without_the_refill_bound`, or 100 ms), so the default branch (lines 324-325), "a lower caller lock_timeout is kept" (326) and the restore (342) are untested; a mutation inverting the comparison or dropping the restore passes. Add one test with no override and `SET LOCAL lock_timeout = '150ms'` asserting the named `55P03`, and one asserting `current_setting('lock_timeout')` after a successful refill. (The 60 s override does not hide deadlocks: PostgreSQL's detector would still raise `40P01` and the `expect`s would fail.) `a_completion_holding_the_usage_row_refills_while_another_refill_waits` (1234-1267) stages an order production never produces (the content finalizer runs at commit, after the carry); the real case is covered by a2. Confidence: confirmed in code.

**5. A refill's total wait can exceed *b*.** `lock_timeout` applies per lock acquisition; a row-lock wait is a tuple-lock wait then an xid wait, each timed afresh, and following an updated row starts another round; the create path loops twice (lines 330-336). The wait can run past *b* by at least one holder's hold, and with enough rounds the carry statement hits the 5 s `statement_timeout` and fails with `57014`, which is not named `tenant_step_log_refill_wait` and not counted. Fix: bound the total (compute the remaining time and set `statement_timeout` locally, or count `57014` raised inside the refill), or document *b* as per acquisition with a startup check of 2·*b* + one hold < `statement_timeout`. Confidence: plausible (documented PostgreSQL behaviour).

**6. The timeout counter conflates ingest backpressure with refills past *b*.** An ingest keeps its own 200 ms `lock_timeout`, and the handler at lines 337-340 counts and renames that timeout identically, so `step_log_quota_refill_wait_timeouts_total` (alert on any increase over 5 minutes) pages on ordinary ingest backpressure, and the fourth run's validity rule would read it the same way. Label whether the bound or the caller's timeout fired; alert only on the bound. Confidence: confirmed in code.

**7. Spec drift on the grant and on the lock order.** ADR-0097 decision 4, design 2b and D041-117 describe a partial fold (`granted −= used`) with g = max(n − room, …); data-model §3b, the code (363-367) and the fourth-run declaration fold the lease whole with max(n, …). The ADR is the text the owner accepts; it must match the code. G041-023 still says "at most 1/64 of the free room near the limit" (now mutation W2). D041-117 gives the order "fence, writer's lease, usage row"; ADR-0097 gives "fence, usage row, own lease". D041-117 says "the pool's statement timeout stays the guard"; D041-118 supersedes. ADR-0095's Consequences (line 144) say "waited for at most 1 s"; *b* is 2 s. Confidence: confirmed in documents.

**8. ADR-0097's own stated force is contradicted.** Context (line 60): "a report must never wait under its run lock for another tenant's, replica's or attempt's commit." Decision 4 makes a carry's refill wait up to *b* for a usage row held until another attempt's commit, while the report holds its run row. Not analysed: cancel, signal and timer transactions on that run now wait up to *b*, and if the report fails past *b* the step's timeout can fire before the worker resends, turning a completed step into a timed-out attempt (with the old `NOWAIT`, the carry was answered mark-only and the report committed). State the relaxation and add a test of the timeout racing a report that fails past *b*. Confidence: plausible.

**9. The carry's reserved amount is inconsistent between §3b and §8a.** §8a (line 536) reserves "the kept rows' text bytes plus 128 a row"; §3b and ADR-0097 decision 3 add 128 for a possible ceiling marker. The prototype follows §8a (`step_log_spike.rs:619`). A carry that hits the attempt ceiling and plans a marker, with lease room in [planned, planned + 128), misses its reserved lease in the fast-path charge and refills outside the block — the refill waits under the run lock, or a refusal aborts the report. Align §8a with §3b. Confidence: confirmed in documents.

**10. A counts dead and zeroed leases, and "rows ≤ connections" does not hold.** `step_log_spike.rs:365-366`: A includes rows zeroed by a near-limit reclaim and dead pids' rows, which persist until 10 minutes after their last charge; pool churn (sqlx `max_lifetime`) and restarts create more distinct pids in that window than live connections. Grants shrink and extra refills feed Major 1. Count only leases with `granted > 0` (all the derivation needs), and delete zeroed rows in the near-limit reclaim. Confidence: confirmed in code.

## Nit

**11. Prepared transactions break the "one transaction per backend" premise.** A PREPAREd transaction keeps its lease lock after its backend moves on; that backend's next refill takes the usage row then waits on its own lease (`FOR UPDATE`, 355-356) under the caller's restored `lock_timeout` (0 for a report), holding the usage row throughout — every refill of the tenant stalls. Neither reclaim recovers it (both skip the locked row). Other pid cases: a dead backend's lease is reclaimed; pid reuse inherits already-counted room; parallel workers are excluded (functions default to `PARALLEL UNSAFE`); a transaction pooler is fine. Fix: take the own lease `NOWAIT` in the refill, or a startup check that `max_prepared_transactions = 0`. Confidence: plausible (off by default).

**12. The `sagat.step_log_refill_wait` knob must not ship.** Any session can set the placeholder; `'0'` passes the check at line 326 and sets `lock_timeout` to 0 — an unbounded wait. Keep it out of the production function (§3b does not list it). Confidence: confirmed in code.

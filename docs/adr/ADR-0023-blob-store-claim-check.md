# ADR-0023 — Large payloads live in a provider-neutral blob store and travel as descriptors

Status: **Accepted** | Date: 2026-10-09 | Builds on ADR-0002 and ADR-0004; diverges from none. Implements gap G19 in feature 002 (FR-002-008). Run-input and SDK conformance verification is tracked by T002-040.

## Context

Run inputs and step outputs are stored in `payloads`, content-addressed by `(tenant, digest)` and limited to 256 KiB (a check constraint). Everything that matters to the engine goes through that table: the foreign keys of `runs` and `run_events`, the outputs every lease receives, the expressions that read `steps.<x>.output`, and the 4 MiB budget a run may retain. A payload that does not fit was simply refused (G19). FR-002-008 asks to "control payload/result size via blob refs", `docs/architecture/execution-semantics.md` already says "large inputs/outputs go to the object store, the journal keeps `blob_ref`, digest and metadata", and the plan and FR-001-005 name an S3-compatible store.

Three questions were open: where the bytes live, how the engine refers to them, and how a worker reaches them. The product owner decided the first: the store must be **abstract, multi-cloud from the start, with Amazon S3 and Cloudflare R2 as the first two**.

## Decision

1. **A port, two adapters' worth of protocol.** `sagat_application::blobs::BlobBackend` moves bytes (`put`, `get`, `delete`, streams in both directions, keys not paths) and knows nothing of tenants, states or limits. `crates/infra-blobstore` implements it once over the `object_store` crate, because S3 and R2 speak the same protocol: the provider is a configuration (`SAGAT_BLOB_PROVIDER=s3|r2|fs|memory`), and R2 is S3 with region `auto`, path-style addressing and an endpoint derived from the account id. Adding Google Cloud Storage or Azure later is a new `BlobStoreConfig` variant and a builder; no caller changes. Only `crates/infra-blobstore` may depend on a storage client (`scripts/check-architecture.py` enforces it, and the domain may not know one at all).
2. **Claim check.** The engine never carries a large payload. A blob has an id, a size and a SHA-256, and what the journal, the expressions and the next step see is the descriptor `{"$blob": {"id", "size", "sha256", "contentType"}}`, stored as an ordinary small payload. Nothing that already works changes: the foreign keys, the digests, the replay of the journal and the run's output budget all see a few hundred bytes. The engine does not look inside a blob; a workflow author passes the descriptor on and the worker that needs the bytes reads them.
3. **The platform mediates the bytes.** Two additive worker RPCs, `WriteBlob` (client streaming) and `ReadBlob` (server streaming), authorized by the lease of a running attempt (the capability, as for secrets). Workers never receive storage credentials or URLs; the engine process holds them. `CompleteStep.output_blob_ref` (until now refused) takes the id `WriteBlob` returned.
4. **Tenant and namespace scoping are in the key and catalog.** The object key is `tenants/<tenant>/namespaces/<namespace>/blobs/<blob id>`, built only from typed ids. Every catalog query carries both boundaries. Another tenant or namespace sees the same `NOT_FOUND` as a missing id.
5. **The uploader's exact fence is durable.** Each reservation records tenant, namespace, run, step, attempt and generation after matching them to the current step row. `CompleteStep` may attach only a descriptor with that exact scope. An exact replay may resolve the already `COMMITTED` descriptor so a lost successful response remains idempotent; the PostgreSQL transition itself remains `UPLOADED` → `COMMITTED` only.
6. **States move forward and "used" is a transaction.** A catalog row (`blobs`) goes `UPLOADING` → `UPLOADED` when the store holds every byte (size and SHA-256 measured by the server while streaming, compared with what the worker stated) → `COMMITTED` in the *same transaction* that completes the step, and only if it is still `UPLOADED` with exactly that scope, size and digest. Current leases in the same tenant and namespace may read `UPLOADED` or `COMMITTED` bytes by unguessable id; only the exact uploader may commit them.
7. **What nothing uses is swept with durable retry evidence.** An `UPLOADING` row older than `SAGAT_BLOB_ABANDONED_AFTER_SECS` (1 h) and an `UPLOADED` one whose `uploaded_at` is older than `SAGAT_BLOB_UPLOAD_TTL_SECS` (24 h) first move to `DELETING` in PostgreSQL, with a numbered attempt and retry time. A finalized upload's row is removed only after the backend confirms deletion. An upload never confirmed as `UPLOADED` retains a deleting tombstone even after that confirmation: a PUT of unknown outcome may still finish later. Periodic idempotent deletes reconcile those late bytes. A provider failure or crash retains the retry record. A tenant may hold at most `SAGAT_BLOB_MAX_PENDING` (64) active non-committed uploads; a tombstone releases its slot only after successful deletion and its audit commit.
8. **Auditing is part of each database decision.** `blob.uploaded` is appended in the transaction that records the measured upload, `blob.read` before bytes are returned (identical retries collapse), and `blob.deleted` in the transaction that removes a finalized row or first confirms a cleanup tombstone. Repeated tombstone reconciliation adds no duplicate audit. Records contain tenant, namespace/blob id, actor and the attempt identity where applicable, never content, digest or credentials. An audit failure rolls back its state change or refuses the read.
9. **Limits are explicit.** A blob is at most `SAGAT_BLOB_MAX_BYTES` (64 MiB); at most `SAGAT_BLOB_MAX_TRANSFERS` (32) transfers run in a process; one transfer takes at most `SAGAT_BLOB_TRANSFER_TIMEOUT_SECS` (600), enforced inside the body of the upload so that a stalled upload fails and cleans up instead of being cancelled; ordinary calls keep `request_timeout` (30 s), now enforced by the admission layer so that the transport timeout can allow the longest transfer. The backend retains at most one configured part plus bounded parts in flight; a single-part blob is necessarily held as that part.

## Why

- A claim check keeps the engine's invariants intact and its cost flat: the rest of the system never learns that blobs exist, and a run that handles a 50 MiB document costs the same rows as one that handles a 5 KB document.
- A narrow, object-safe port with the provider chosen at start-up is what "abstract and multi-cloud" means in code; one implementation over the S3 protocol is what makes S3 and R2 a matter of configuration instead of two codebases to keep equal.
- Mediating the bytes keeps credentials in one place, makes the lease the only capability, lets the platform measure and hash what it stores, and works identically on every provider. Presigned URLs would move bytes without the engine, but they put provider-specific URL semantics, signing windows and per-object authorization into the worker protocol and every SDK.
- Committing in the step's transaction is the only way to make "uploaded", "used" and "swept" mutually exclusive without a distributed protocol.

## Trade-offs

- Blob bytes pass through the engine process: bandwidth and one connection per transfer. The caps above bound it; presigned URLs are the optimisation if a measurement ever demands it (a new ADR, additive to the protocol).
- A descriptor in a step's input is JSON the author must pass on explicitly; the engine cannot evaluate expressions over the content of a blob.
- Reads are authorized by a current, unexpired, worker-bound lease in the blob's tenant and namespace plus the unguessable id, not by "a blob named in this step's input" (G67).
- Blob uploads from steps that declare secrets currently fail before the first byte is stored. Inline outputs already scan current secret versions, but the equivalent bounded, cross-chunk raw and JSON-escaped scan for blob streams is pending; the platform does not claim leak detection for a stream it has not scanned.
- A crash after `WriteBlob` and before the step's completion leaves an `UPLOADED` blob that is swept after 24 h. A crashed upload leaves an `UPLOADING` row, and a failed multipart abort may leave provider-managed incomplete parts that catalog cleanup cannot address by object key. The bucket must expire incomplete multipart uploads through its lifecycle policy.
- Ordinary REST run input remains limited to 256 KiB. The additive streaming upload and explicit inputBlobRef contract below supports larger opaque inputs without expanding ordinary JSON request limits.
- Committed blobs are never deleted: payload rows are not either, and the retention and classification policy the specification lists as an open question is not decided (G69).
- Tombstones for uploads of unknown outcome also remain until an explicit reconciliation/compaction policy exists. A client or provider timeout is not proof that a late PUT cannot occur. The bounded cleanup batch keeps retry work limited per pass; confirmed tombstones do not occupy active upload slots.
- S3 and R2 are exercised against an S3-protocol server that verifies Signature V4, not against the real services; the contract suite that runs against them exists and is marked `ignore` until someone supplies credentials (G70).

## Review criteria

Open a new ADR with benchmark data (throughput and memory of concurrent transfers on a reference machine), failure tests, operational cost and compatibility with runs in flight if: presigned URLs are wanted (workers would receive provider URLs), the engine must evaluate expressions over blob content, blobs need a retention or classification policy, or another provider's semantics (conditional writes, consistency, multipart rules) cannot be reached through the port as it is.

## Run-input extension (T002-040)

- `POST /v1/run-input-blobs` accepts a raw stream under the authenticated tenant and `X-Octopus-Namespace`, requiring current `run:start`. Its optional size/hash preconditions are checked while streaming. The response is only `{id,size,sha256,contentType}`. It uses the configured provider, transfer/pending limits, expiry, durable cleanup and upload audit; no storage credentials or URLs cross the API.
- Catalog ownership is tagged `STEP_OUTPUT` (the existing exact fence) or `RUN_INPUT` (the namespace and uploader subject, initially unbound). There are no placeholder run or step identities. Workers cannot read an unbound run-input upload.
- `POST /v1/runs` accepts `inputBlobRef` instead of `input`, never both. The authenticated uploader may bind an exact uploaded descriptor once. The run row records the blob identity, and blob commitment, run creation, journal, initial tasks, outbox, audit and idempotency share one PostgreSQL transaction. Exact replay uses a fingerprint containing the input mode and blob id, before catalog lookup, and rechecks current authorization.
- This is explicit claim-check input: the stored input and expression `input` value are the bounded canonical `$blob` descriptor; the original bytes remain opaque. A declared workflow `inputSchema` is checked against that descriptor, with external schema references forbidden, and is never claimed to validate the external bytes. `TaskLease.input_blob_ref` names the catalog-backed run input; a normal JSON object resembling a descriptor does not populate that field. Workers use the existing lease-authorized streaming read.
- Rerunning an authorized source run and a child inheriting its exact input may reference the existing committed blob through the source run's durable provenance. They do not reclaim an upload or accept a caller-selected committed blob. Reads after commitment retain the documented tenant/namespace plus live-lease boundary.
- Existing inline starts and protocol fields remain compatible. No auto-loading, secret injection, raw payload read endpoint or relaxation of the secret-declaring output-upload restriction is introduced. Retention of committed references remains the existing explicit open policy.
- Worker registration persists the accepted protocol minor. Protocols 1.0–1.2 receive inline work
  as before, but cannot lease a run after its catalog provenance contains a bound run-input blob or
  a committed step-output blob. The bounded candidate query filters those runs before its cap, and
  the locked-run transaction repeats the check before lease admission. JSON shape is never used as
  provenance, and skipped tasks remain `READY` without consuming an attempt.
- Required proof: interrupted/late upload cleanup; wrong uploader, tenant and namespace; read before/after bind and stale lease; duplicate start and conflicting mode/body; schema rejection before durable use; crash/audit failure during bind; rerun/inherited-child provenance; actual REST streaming plus worker read.

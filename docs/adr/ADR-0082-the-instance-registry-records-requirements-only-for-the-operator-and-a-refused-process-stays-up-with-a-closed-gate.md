# ADR-0082: The instance registry records requirements only for the operator, a refused process stays up with a closed gate, and it learns of a requirement within one heartbeat

**Status:** Accepted (2026-11-13, OD-2026-11-13-4; proposed 2026-11-08)
**Decided by:** agent (task T018-080), after the correctness, security and architecture reviews of 2026-11-08; the owner has not accepted it.
**Refines / supersedes:** refines ADR-0050 decision 9 (fleet capability activation), which says that a feature needing every control-plane or engine process to honour it is activated through a registry; supersedes none. ADR-0081 still governs the flags of the features that are not on the registry yet.
**Enforced by:** `tests/integration/schedules-bulk-operations/instances.rs` (the operator functions are not executable by `sagat_app`: `the_runtime_role_reads_the_registry_and_calls_three_functions_only`; the guards: `requirements_and_the_epoch_change_only_through_the_activation_functions`; the cap and its eviction: `a_table_full_of_silent_rows_makes_room_and_a_crash_loop_cannot_lock_the_fleet_out`, `the_table_holds_a_thousand_live_rows_and_refuses_the_next_one`; the bounds of the operator's transaction: `a_feature_step_that_takes_too_long_is_cut_off_and_nothing_is_recorded`), `instances_hostile.rs` (a row is touched only for its token, both roles), `instances_process.rs` (a refused process stays up and serves nothing, a control plane and an engine; the engine lists what its configuration runs; a closed engine fires no schedule and reads no connector), `instances_rest.rs` (every operation of the contract is refused by a closed gate but liveness; a stream and a task stream stop), `tests/fault/schedules-bulk-operations/instances.rs` (the race between an activation and a registration, in both orders, held by a lock and watched in `pg_stat_activity`), `apps/control-plane/src/registry.rs` and `crates/application/src/instances.rs` (the unit tests of the fail mode and of the pace), `apps/execution-engine/tests/registry.rs` (the capability follows the passes; every loop the engine spawns obeys the gate), the privilege audit of `integration_platform_foundation` (the three operator functions are listed with their reason), and `infra/observability/tests/instance_registry_test.yaml` (the two alerts).

## Context

ADR-0050 decision 9 requires a registry so that a feature which every control-plane and engine process must honour is switched on only when every live process can. Building it (task T018-080) forced decisions that are hard to reverse, because processes and operators depend on them from the first release that ships the registry, and that surprise a reader of the code:

- Who may record a requirement. A requirement makes every process of a kind that lacks the capability refuse to serve: a wrong one stops a fleet.
- What a process does when the registry refuses it, or cannot be asked. The processes already behaved, before the registry, as "alive, not ready, ready once migrated"; a runbook and a test say so.
- How fast a running process learns of a requirement, and what is exposed in the meantime.
- What a full table means, since a process that restarts in a loop leaves a row for every start.
- What a failing heartbeat means: a database that cannot be reached is not the same as a registry that answers with an error.
- What the capability of an engine is: what its binary can do, or what its configuration will do.

## Decision

1. **Recording or removing a requirement is the schema owner's act, never the runtime role's.** `platform_requirement_lock`, `_activate` and `_remove` MUST NOT be executable by `sagat_app`; the operator command runs with the schema-owning role, as `provision-tenant` does. The functions a process calls (`instance_register`, `instance_heartbeat`, `instance_deregister`) MUST be the only writes the runtime role can make to the registry, and each MUST touch a row only for the token that registered it (the registry stores the hash; the runtime role cannot read it). Triggers `ENABLE ALWAYS` MUST refuse a change of a requirement or of the epoch outside the activation functions, an epoch that moves by more than one, and a requirement that changed in a transaction in which the epoch did not move.
2. **The activation is one transaction and is bounded.** It locks the epoch `FOR UPDATE`, verifies every live instance of the required kinds (seen within 30 s on the database's clock), records the requirement, moves the epoch, writes the history (who the command said, and which database role did it) and runs the feature's own step. The feature's step MUST NOT take a lock that a transaction reading the epoch may hold: it reads, it does not lock. The transaction MUST have a lock timeout, a statement timeout and a bound on the step, all shorter than the statement timeout of the processes that wait for the epoch.
3. **A refused process stays up with a closed gate.** A process that is refused, or cannot reach the registry, MUST NOT exit and MUST NOT serve: every call but the liveness probe is `503 UNAVAILABLE` (with `details.reason` `BINARY_CAPABILITY_MISSING` only when a capability is missing), readiness fails, no pass runs, no connector is read, no shard is held, the worker API answers `UNAVAILABLE`; it asks again every second and serves as soon as the registry lets it. A table of 1,000 live rows is not a refusal: the check of capabilities has passed, so the process serves, loudly, and is not counted.
4. **A requirement is learned within one heartbeat.** The epoch is carried by the heartbeat (10 s, jittered to 12 s), not by a query of its own. The bound is stated in the specification: a process learns of a requirement within about 12 s plus the time of the call, and only a process that was not live (silent for 30 s) at the activation can be in that window, because an activation is refused while a live process lacks the capability.
5. **The fail mode.** A heartbeat that fails because the connection fails leaves the process serving (a registry that cannot be reached is a database that cannot be reached; stopping the fleet would make an outage longer). A heartbeat that fails for longer than the liveness window for any other reason (a lock or statement timeout on its own row, a permission or function error) MUST close the gate: the process is invisible to activations and never learns of an epoch change while the database works. Readiness MUST fail when the last answer of the registry is older than the liveness window, whatever the gate says. A heartbeat that ends MUST stop the process (the engine's critical tasks; the control plane's `select`).
6. **At the cap, rows that are no longer live give way.** The count of the table is made under an advisory lock, after the epoch lock, so the limit is exact for new ids; a registration at the limit evicts the rows silent for 30 s, oldest first, and is `FULL` only when 1,000 rows are live.
7. **The capabilities of a process are what its configuration runs.** An engine lists `schedules-v1` only when its configuration runs the schedule pass; an engine restarted without it after an activation is refused at registration and closes its whole gate. A capability is never listed for what the binary could do and the process will not.
8. **The registry has a connection of its own and the process leaves after it has drained.** The heartbeat MUST NOT share the pool of the requests; the row MUST be deleted after the server has drained, not when shutdown begins.

## Considered options

1. **The decisions above (chosen)** — a hostile or buggy API process cannot make the fleet refuse to serve by recording a requirement; a process that is refused keeps the behaviour operators already know; the bound on learning is short and stated; a crash loop cannot lock the fleet out.
2. **Record requirements through a function the runtime role can execute, behind an application check** — one less credential for the operator, but a compromised API process could record any requirement and stop the fleet; the application check is the thing that would be compromised.
3. **A refused process exits** — simple, and a crash loop is an alert by itself, but it breaks the documented behaviour (alive, not ready, ready by itself once migrated), restarts a process that a restart cannot cure, and fills nothing but logs; tested by `an_instance_pointed_at_an_unmigrated_database_is_alive_but_not_ready_until_migrated`.
4. **Learn of a requirement with a read of the epoch at every admission** — immediate, but a statement per request (or a per-second poll per process) to learn what changes a few times a year; the 12 s bound costs nothing when nothing changes and is closed by the fact that only a not-live process can be in the window.
5. **List the capabilities of the binary, whatever the configuration** — the first implementation; it let an activation pass for an engine that would then fire nothing, which is the failure the registry exists to prevent.
6. **Keep non-live rows for a day and refuse at the cap** — the data model's first text; a process that restarts every ten seconds fills the table in under three hours and every healthy restart is refused.

## Consequences

Good: the activation is the one place a requirement is decided, with an audit that survives the removal; a fleet that is mid-upgrade shows as refused processes that recover by themselves when the build or the requirement changes; an engine that does not run the schedule pass cannot be counted on by the handover.

Bad: the operator needs the owner credentials to activate (a runbook step, as for `migrate`); an engine's capabilities change with its flags, so a rollout that turns a pass off after an activation is refused until the pass is on or the requirement is removed; the registry costs one more connection per process and a statement per heartbeat; a holder of the runtime role can still fill the table with rows of its own, hold the registration lock open, and so delay the start of new processes (G2000) — the database cannot close what the role can legitimately do; 029's request path cannot take the epoch lock as `sagat_app` (G2001) and needs a definer function of its own; a rollback of the binary below a recorded requirement is not supported, and the down migration refuses once any history row exists, so a rollback of the schema needs the history read and removed on purpose.

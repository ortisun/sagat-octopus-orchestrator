# ADR-0101: The Studio builds its interface on the Astryx design system, behind its own interface module and with its own theme

**Status:** Proposed
**Decided by:** owner (direction, 2026-11-21: "use Astryx as the design system", for the existing Studio, as a full migration); the rules below are an agent's proposal for the owner to accept
**Refines / supersedes:** refines [ADR-0016](ADR-0016-the-studio-is-a-same-origin-app-over-the-rest-api-that-follows-runs-by-journal-sequence.md); supersedes no decision record. It replaces one clause of research decision D138 of feature 007 ("No UI kit with its own theming: plain CSS with design tokens"); the rest of D138 (lock file, packages at least two weeks old, no install scripts, no content delivery network) and D154 to D159 stay in force. D2400 to D2404 record how they are kept.
**Enforced by:** the Studio's ESLint configuration (`frontend/apps/studio/eslint.config.js`: the import boundary and the ban on raw controls), `src/ui/theme/theme.test.ts` (the theme's recorded values, its contrast pairs, the mapping of every role and the exact pin) and `src/styles/tokens.test.ts` (no literal colour and no undefined custom property in a Studio stylesheet). All three run in `npm run lint` and `npm test`, which the frontend job of the continuous integration runs.

## Context

The Studio (feature 007) had a hand-written interface layer: eight primitives in `src/ui`, about 3,200 lines of stylesheets and its own token set in `base.css`. Every screen of every later feature (payload classification, database connections, operations, integrations) added controls, tables and dialogs by hand, each with its own keyboard, focus and state handling to get right and to test.

The owner asked for Astryx as the design system. Astryx (`@astryxdesign/core`, Meta Open Source, MIT licence, repository `meta/astryx`) is a React component library with themes. The newest release on 2026-11-21 was 0.7.17, one day old; D138 asks for a package at least two weeks old, so the version chosen is 0.7.11 (published 2026-11-07). Facts measured on 2026-11-21:

- It needs React 19 or later (the Studio has 19.3.0) and the runtime package `@stylexjs/stylex` 0.19.
- It ships prebuilt stylesheets and JavaScript. A Vite application needs no compiler plugin: two stylesheets in cascade layers (`reset`, `astryx-base`) and a `Theme` provider that applies the theme in the `astryx-theme` layer.
- A theme is defined in TypeScript (`defineTheme`). It can be applied in two ways: from its source when the application starts (the `Theme` provider writes a style element), or from a stylesheet that the Astryx command line tool (`@astryxdesign/cli`) compiles beforehand. Astryx recommends the compiled form because an application rendered on a server would otherwise paint once without the theme's component overrides; the Studio is rendered in the browser only. The command line tool brings 78 development packages (Babel, PostCSS, a code transformer), 16 of which were younger than two weeks on 2026-11-21, runs on every `npm test` if a freshness check uses it, and writes per-user state outside the repository. `@astryxdesign/core` alone brings 10 packages, all older than two weeks.
- `@astryxdesign/core` declares an install script that only prints a setup hint. The project installs with scripts disabled (`frontend/.npmrc`, the continuous integration and the container build), so it never runs.
- It renders in the Studio's test environment (jsdom): a native `<dialog>`, a real `<table>`, text inputs with a linked label, hint and error.
- It is before version 1.0 (first published 2026-06-24), so a release may change an interface or a behaviour. One was seen while this record was written: in 0.7.11 a disabled button carries the native `disabled` attribute unless it has an explanation or is busy; in 0.7.17 it always stays focusable with `aria-disabled="true"`.
- Three behaviours differ from the hand-written layer. A disabled text input or selector stays focusable and carries `aria-disabled="true"` instead of the native attribute, so a person using a keyboard can still reach it and read it. A selector is a button with the `combobox` role and a `listbox`, not a native `<select>`. The error of a field is linked to its control (`aria-describedby`) and announced through a live region that Astryx keeps on the page, instead of being an element with the `alert` role beside the control; in a strip of tabs an arrow key moves the focus and Enter or Space selects.
- Its styles set inline custom properties, which the Studio's content security policy already allows (`style-src 'self' 'unsafe-inline'`, D153). It loads no remote font, script or stylesheet.

Constraints that do not move: the accessibility floor of FR-007-008 (D155), the recorded visual direction of the owner's design export (D154: the dark colour roles, the Geist typefaces, the shell), light and dark themes that follow the system (D157), bundled fonts and no content delivery network (D138, D159), and English labels (D156).

## Decision

1. The Studio's controls, layout primitives, navigation, dialogs, tables and feedback elements MUST be Astryx components. A screen MUST NOT hand-write a control that Astryx provides.
2. Only `frontend/apps/studio/src/ui/` MAY import from `@astryxdesign/*` or `@stylexjs/*`. Every other module imports the Studio's own interface module (`src/ui`). The interface module keeps the Studio's vocabulary (a `Banner` has a tone, a `Dialog` has a title and an `onClose`) and maps it to Astryx, so that a change of an Astryx interface is absorbed in one directory.
3. Outside `src/ui/`, a module MUST NOT render a raw `button`, `input`, `select`, `textarea`, `dialog`, `table` or heading element. An exception needs an ESLint disable comment on that line that names the reason (for example a cell of the graph canvas that a library owns).
4. The Studio has one Astryx theme of its own, `sagat`, which carries the recorded direction: the surfaces, text, lines, accent and status colours of `specs/007-workflow-studio/design/README.md` for dark, the accessible derivation for light, Geist and Geist Mono, and the recorded radii. Its colours are in `src/ui/theme/roles.ts`, the only file with a literal colour; `src/ui/theme/sagatTheme.ts` maps them to Astryx's tokens. The theme is applied from that source when the application starts: there is no generated stylesheet. The stock Astryx themes MUST NOT be shipped.
5. A Studio stylesheet MAY exist only for a surface that Astryx has no component for (the workflow canvas, the run graph, the timeline, the code editor's frame). It MUST take every colour, type size, spacing, radius and shadow from an Astryx token (`--color-*`, `--spacing-*`, `--radius-*`, `--text-*`, `--font-*`, `--shadow-*`) or from a Studio layout token that is itself declared in `src/styles/base.css`. It MUST NOT hold a literal colour.
6. The Studio uses the prebuilt Astryx stylesheets. It MUST NOT add a StyleX compiler to its build, and MUST NOT copy an Astryx component into its source (`astryx swizzle`), unless a later decision record says why.
7. `@astryxdesign/core` and `@stylexjs/stylex` are pinned to exact versions and follow D138. The Astryx command line tool MUST NOT be a dependency of the Studio; to read a component's documentation, run the scoped package at the pinned version without installing it (`npx @astryxdesign/cli@<the pinned version> component <Name>`), never the unscoped name `astryx`, which is another publisher's package. The packages follow D138 (lock file, `npm ci --ignore-scripts`). An upgrade is its own change: read the change log, run the unit tests and the browser journeys, and look at the screens.
8. Where an Astryx component and the accessibility floor disagree, the floor wins (D155): the interface module adds what is missing (for example the `alert` role of an error banner) and the difference is listed in the design record.

## Considered options

1. **Astryx behind the Studio's own interface module, with a `sagat` theme, on the prebuilt stylesheets** — chosen. The owner's direction is met on every screen; the recorded brand and the contrast floor survive as a theme, checked by a test; a library that is before version 1.0 is held behind one directory; the build gains no compiler.
2. **The theme compiled beforehand by the Astryx command line tool, with a test that the committed stylesheet is fresh.** What Astryx recommends, and what this change first built. Rejected after the security review of 2026-11-21: the tool's 78 development packages (16 younger than the two weeks of D138), its run on every `npm test`, and the unscoped `astryx` name that `npx` resolves to another publisher's package, for a benefit (no unthemed first paint on a server) the Studio does not have.
3. **Feature code imports Astryx directly.** Less code in `src/ui`, and the Astryx documentation applies as written. Rejected: about seventy modules would depend on the interface of a library that may change in a minor version, and the Studio's rules that Astryx does not know (an error is announced, a status is text and shape as well as colour) would be repeated at every call site.
4. **A stock Astryx theme (Neutral).** No theme to maintain. Rejected: it replaces the direction the owner approved on 2026-10-11 (the green accent, the dark surfaces, Geist) without a decision to do so, and its pairs are not the ones the Studio's contrast test has measured.
5. **Compile Astryx from source with StyleX (`@astryxdesign/build`).** Lets the Studio write StyleX and place its styles in their own layer. Rejected for now: a Babel and PostCSS chain in the build for no requirement the Studio has; the prebuilt path supports `className` and theme overrides.
6. **Keep the hand-written layer.** No migration cost. Rejected by the owner's direction, and it keeps the cost of hand-made controls for every later screen.

## Consequences

- Good: one source of controls with their keyboard and focus behaviour; a new screen composes components instead of writing styles; dark, light and forced-colour behaviour comes from one theme; about 3,000 lines of stylesheet are removed.
- A disabled control is marked by the native attribute or by `aria-disabled`, by Astryx's choice for that control and release. Unit tests and browser journeys assert "unavailable" through a helper in `test/` that accepts both, so an upgrade does not rewrite them; an activation of such a control does nothing.
- A selector is a `combobox` with a `listbox`. Tests choose an option by opening it; the browser journeys do the same. A person no longer gets the operating system's native picker.
- The bundle grows. Measured on 2026-11-21 against `develop` (production build, the code editor's workers left out): the entry script from 385 kB to 944 kB (305 kB compressed), all scripts from 5.07 MB to 5.81 MB (1.38 MB to 1.63 MB compressed), all stylesheets from 257 kB to 498 kB (41 kB to 79 kB compressed). The Studio's own stylesheets shrank from 3,199 to 1,869 lines. No journey sets a size budget; the performance journey measures time and is the check that matters, and it has not been run on this change.
- A dependency before version 1.0: an upgrade can break the interface module. The pin, the boundary and the upgrade rule above bound that cost.
- The theme costs a little work when the application starts (the provider derives the style element from the source) instead of a file compiled beforehand. If the Studio is ever rendered on a server, this choice must be revisited.
- Rollback: the interface module is the seam. Reverting the migration commit restores the hand-written layer; nothing persisted, no contract and no run in flight depends on this decision.

## Evidence

- Spike of 2026-11-21 in the Studio's own test environment (on 0.7.17, before the pin was moved to 0.7.11): Astryx `Button`, `Dialog`, `Selector`, `TextInput`, `Banner`, `TabList` and `Table` rendered and were operated through Testing Library in jsdom in one passing test. The contract of the interface module on the pinned version is `src/ui/ui.test.tsx`.
- `npm audit --audit-level=moderate` after adding the three packages reports only the `minimatch` advisory of `typescript-eslint`, which is on `develop` already and is fixed on the 0.2 line by hotfix 0.2.1; none comes from Astryx. The lock file gains ten packages (`@astryxdesign/core`, `@stylexjs/stylex`, `intl-messageformat` and three `@formatjs` packages, `css-mediaquery`, `invariant`, `loose-envify`, `styleq`), each published on or before 2026-11-07, and changes no other entry.
- The unit test result, the browser review and what was not run are recorded in `specs/007-workflow-studio/quickstart.md` under "Astryx design system" (tasks T007-059 to T007-066).
- Requirements: FR-007-008, FR-007-009, SC-007-005 of [`specs/007-workflow-studio/spec.md`](../../specs/007-workflow-studio/spec.md); research entries D2400 to D2404 and gaps G2400 to G2402.

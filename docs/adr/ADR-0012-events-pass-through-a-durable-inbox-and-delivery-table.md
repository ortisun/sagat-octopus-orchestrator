# ADR-0012 — Events pass through a durable inbox and a durable delivery table; matching is asynchronous and idempotent

Status: **Accepted** | Date: 2026-10-09 | Builds on ADR-0002, ADR-0004 and ADR-0008; diverges from none.

## Context

ADR-0002 makes PostgreSQL the authority and the outbox the way to tell the outside world, and ADR-0004 says every external effect is at-least-once. Feature 004 has to take events in (signed webhooks, the API, Kafka, SQS, NATS, a calendar), turn them into started runs and woken steps, and send events out (a finished run, to the subscribers of a namespace). Three questions were open:

1. Where does an incoming event live between "the provider was told 202" and "a run started"? A queue in front of the database would make the 202 a promise that a different system keeps.
2. How is an event delivered to a run *once* when the matcher can crash between starting the run and recording that it did?
3. `specs/004-events-webhooks-messaging/plan.md` proposes the crates `crates/events` and `crates/connectors`. Broker clients (rdkafka-class libraries, an SQS client, `async-nats`) bring sockets and protocol state; the architecture rules (AGENTS.md, rule 5) keep those out of the domain.

## Decision

1. **The inbox is the source of truth for an incoming event.** Admitting an event is one transaction on `inbox_events`, keyed by `(tenant, namespace, source, event_id)`. The key is the deduplication; the SHA-256 of the body tells a retry (same body: `DUPLICATE`, still 202) from a reuse of the id (different body: `409 EVENT_ID_REUSED`). The window comes from the database clock, is at least twice the signature skew and a minute more (so a captured request cannot be replayed as a new event inside the time it would still verify), an event that has not been dispatched is never forgotten with its window, and an id used again after its window is a new event that starts its runs again (the run's idempotency key includes the instant of the admission).
2. **Matching is asynchronous and every effect of it is idempotent.** The ingress answers 202 once the row is committed. A dispatcher claims events with a lease, matches `workflow_triggers` (stable ids; the filter is not part of the identity) and the steps that wait for the event, and records an `event_deliveries` row *in the same transaction* as the thing it did: a run created under an idempotency key derived from the event, or a step woken. A dispatcher that dies half way leaves a lease that runs out; the next one repeats what was not recorded and nothing else. One consumer that cannot be served (no room for its run) does not keep the others waiting, and an event that is only waiting for room does not use up its attempts. A wait and an event that arrive in either order meet: the event looks for waits, and a wait looks back (`event_since`, its start minus the declared look-back) for events, each in its own transaction, so there is no ordering in which both miss.
3. **A webhook is trusted by its signature and by nothing else, and the signature covers what gives the event its meaning.** HMAC-SHA256 over a label, the timestamp, the event id, **the type, the subject, the correlation key** (the headers that choose the triggers that fire and the waits that wake) and the raw body, `v1=<hex>`, tried against the versions of the secret in force (rotation), constant-time; the label keeps what the platform sends from passing for what a provider sent. Every failure — unknown endpoint, bad signature, stale timestamp, missing secret — is the same `401`. A database error while verifying is a `5xx`, never a verdict. The cost of a caller who has proved nothing is bounded before a secret is read or a hash computed (header size and signature count, timestamp window) and before the database is touched beyond the endpoint (two-stage token bucket per endpoint, body cap).
4. **Outgoing events are rows written with the fact they tell.** The deliveries of a finished run are inserted in the transaction that commits `run.finished` (ADR-0002's outbox). A worker claims per subscription, the subscription's rate is enforced by the claim itself (`next_slot_at`, so it holds across replicas), each attempt is recorded with the state it leads to and fenced by the attempt number (a worker that was too slow records nothing), and the schedule is a bounded jittered backoff that honours `Retry-After`. A delivery that never works is `DEAD`, visible, and redrivable; a subscription whose deliveries keep dying is switched off. Delivery is at-least-once with a stable `X-Octopus-Delivery-Id`; the platform does not promise more, and says so.
5. **A connector acknowledges a message only after the event is in the inbox.** The Kafka position (the library has no consumer groups) is a row, moved in the same transaction as the admission with a compare-and-set; partitions are leased; NATS is acked and an SQS message deleted after the commit. A message that cannot become an event is *set aside* (a bounded dead letter an operator can redrive or discard) in the same transaction that moves the position, so one poison message does not stop a partition. A full backlog leaves messages with the broker.
6. **Broker clients are adapters.** They live in a new crate, `crates/infra-connectors` (with the guarded egress client for outgoing webhooks). The domain holds the rules (limits, verdicts, backoff, settings) and the application holds the services and ports; neither imports a broker, a socket or `reqwest`. The crates `events` and `connectors` of the plan are not created (G73).

## Why

- A 202 that means "durable in the system that decides" lets the platform be restarted, scaled or partitioned without a promise being lost, and needs no second system to reconcile with.
- Exactly-once *delivery* does not exist between independent systems. Exactly-once *effect* does, when the effect and its record are one transaction and the effect has an idempotency key; that is what the dispatcher does for runs and wakes.
- Searching in both directions avoids a lock between a waiting step and the inbox: each side takes only its own row lock, and the look-back is what makes the order irrelevant.
- Rate, retry and switch-off belong to the data (`next_slot_at`, `attempts`, `consecutive_dead`) rather than to a process, so a restart or another replica changes nothing.

## Trade-offs

- A dispatcher adds a hop: the latency from admission to a started run is the dispatcher's poll interval (50 ms in the tests, configurable) plus the work. The ingress p95 is what the plan sets a target for; the run start is measured separately (`tests/performance/reports/004-events-webhooks-messaging.md`).
- There is no ordering guarantee across events (G74). Events of one correlation key are dispatched oldest first within a claim, but two dispatchers and a retry can reorder them; a workflow that needs order carries a sequence in the event and checks it.
- `inbox_events` is a hot, short-lived table: rows are purged after their window once dispatched. The payload is kept for the window and is a retention decision for the operator (G80).
- The broker libraries open their own sockets after the first connection, so the egress policy is applied to the bootstrap names and addresses and not to what the brokers advertise (G76). The compose profile for production must restrict the network of the engine.

## Review criteria

Open a new ADR, with data from `tests/performance/reports/004-events-webhooks-messaging.md` and failure tests, if the inbox becomes the bottleneck (partitioning `inbox_events` by tenant hash, or moving ingress ahead of the database), if ordering per correlation key becomes a requirement (per-key sequencing in the dispatcher), or if outgoing events need to reach a broker (Kafka/SQS producers are not built, G77).

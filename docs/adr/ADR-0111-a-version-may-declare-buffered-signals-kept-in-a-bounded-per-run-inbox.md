# ADR-0111: A workflow version may declare buffered signals, kept in a bounded inbox of the run and consumed once by a later wait

**Status:** Accepted (2026-11-26), by delegate (OD-2026-11-24-4), on the approval of design 054 that day; implementation and its evidence pending (Enforced by)
**Decided by:** delegate (OD-2026-11-24-4), accepting the agent's proposal made under the owner's delegation (Owner decision 2026-11-20-6, widened by Owner decision 2026-11-24-4), on the owner's decision that release 0.3.0 contains every missing parity feature (Owner decision 2026-11-24-1), of which the roadmap assessment of 2026-11-11 lists "buffered signals (an early signal is refused today)"; the coordinating session decided that buffered signals are design 054 and that superseding Architecture decision 0050 decision 4 in part is within the delegation, this record to be accepted if design 054 is approved
**Refines / supersedes:** supersedes in part Architecture decision 0030 decision 17 (a signal is accepted only by an already waiting step) and Architecture decision 0050 decision 4 (no buffered signal; no table holds a signal for later delivery), for workflow versions that declare a buffered signal and for nothing else; refines Architecture decision 0027 (two new resources, `pending_signal_bytes` and `tenant_pending_signal_bytes`); refines requirement FR-018-024 (Signal-with-Start) and FR-018-039 (reset reapply) of feature 018, and feature 004's rule that signals are accepted only by a waiting step; refines Architecture decision 0032 decision 8 (rollback): once a version declares a buffered signal, a rollback below this release is refused for good, since published versions are never deleted. Keeps Architecture decision 0050 decisions 1 to 3 and 5 to 9 (lock order, no aggregate written by a run-driven transition, no reopen) unchanged.
**Enforced by:** design 054 ([`docs/designs/054-buffered-signals.md`](../designs/054-buffered-signals.md)): the unit tests of the declarations and of the planner in `crates/domain`; the replay-equals-projection corpus with buffered, consumed, moved and discarded signals; the barrier tests of a signal against a wait's entry, a wait's timeout, the run's end and a continuation, and of two waits on one signal (`fault_buffered_signals`); the slot-order test of Signal-with-Start with a buffered signal (`tests/fault/schedules-bulk-operations/slot_order.rs`); the run-driven barrier test with a pending signal (`run_driven_locks.rs`); the check of the run's byte ledger over outputs and pending payloads together; the privilege audit of the new table (`integration_platform_foundation`); the conformance scenario `buffered-signals` in six languages; the refusal test of `SIGNAL_PENDING_BYTES_FULL` (Task 054-9); the two rules of `scripts/check-architecture.py` over the writers of `run.finished` and over comparisons of `run_version` (Task 054-9); the budget lines of design 054's Task 054-16. Until they exist the rules are review-only.

## Context

Today a signal to a run is delivered only to root `waitEvent` steps that are waiting when its transaction commits, each of them receiving a copy; otherwise `signalRun` answers `409` "the run is not waiting for that signal" (`crates/application/src/runs.rs`), and Signal-with-Start rolls back with `SIGNAL_NOT_ACCEPTED_AT_START`. Architecture decision 0050 rejected buffering on 2026-10-29 because it needs a lifecycle for undelivered signals (expiry, transfer across continuation, quotas) and changes what a `409` means; feature 018 left buffered signals out of scope. In Temporal a signal is part of the history whether or not code waits for it, which is what makes "send the approval before the workflow reaches the approval step" and a signal-driven work queue possible. Design 044 (workflow as code) needs the same substrate: a workflow function reads signals from a channel at the moment it chooses.

The objections of Architecture decision 0050 are answered by making buffering an explicit property of a published version, bounded by what the author declares, stored under the run's own lock, and given a lifecycle in each transition that already exists.

## Decision

1. **Opt-in per version and per signal name.** A version declares `signals: [{"name", "maxPending", "maxBytes"}]` (`buffered` is optional and, when present, `true`, as design 044 writes it; `maxPending` 1 to 1,000; `maxBytes` 1 to 262,144, default 65,536). In a graph version a declared name MUST be the event type of at least one `waitEvent` node of the root graph; in a code version (design 044) the consumer is the workflow function. For every name not declared, and for every version published before this decision, signals behave exactly as today, `409` included.
2. **One signal, one consumer.** A signal of a declared name satisfies exactly one wait. When root waits of its name are waiting, it is delivered to the one with the lowest node id, the order in which the planner also enters waits, and to no other; when none is, it is kept in the run's inbox, in the run's transaction, journaled `signal.buffered` with its sequence, audited `run.signalled`, and answered `202` with `buffered: true`. To a code run every signal of a declared name is kept.
3. **A wait consumes the oldest pending signal of its name at its entry.** In the transaction that makes a root `waitEvent` wait (the resolution of its correlation), the store reads and deletes only the oldest pending row of its name through the inbox's index, and the wait is satisfied at once (`wait.satisfied` with `via: buffered` and the signal's sequence). The inbox is consumed before feature 004's look-back, which acts only on a wait still waiting after its entry. A code run consumes by sequence in its completion's transaction (design 044).
4. **Bounded by the declarations.** Publication refuses a version whose `maxPending` sum above 1,000 or whose `maxPending × maxBytes` sum above 2,097,152 bytes (half of the run's 4 MiB of retained bytes, so that pending signals never take room step outputs below 2 MiB need); at run time a signal is refused when its name holds `maxPending` (`409 SIGNAL_INBOX_FULL`), when a code run's pending bytes and the payload together would pass 2 MiB, which only the moves of a continuation under another version can bring about (`409 SIGNAL_PENDING_BYTES_FULL`), when its payload exceeds `maxBytes`, or when the run's step outputs and pending payloads together would pass 4 MiB (`429`, as today). Payloads are run content in `payloads`, charged to the tenant's content quota (Architecture decision 0027), never read while pending (no read returns a pending payload, its digest, or its size to a caller without `run:payload:inspect`), and the consumed one is the step's output. A namespace's and a tenant's pending bytes are bounded by two new resources of Architecture decision 0027, `pending_signal_bytes` (namespace) and `tenant_pending_signal_bytes` (tenant aggregate) (refused `429 QUOTA_EXCEEDED`, `PENDING_SIGNAL_BYTES`), so senders cannot exhaust the tenant's content quota through inboxes.
5. **A lifecycle in transitions that already exist, under locks they already take.** The inbox holds pending rows only; each settlement deletes the row and is journaled. Continue-as-new moves the pending signals whose name the successor's version declares (a signal at most 100 times, then it is discarded and counted, so each accepted signal writes a bounded number of records), in order, in the handoff's transaction (chain lock, then run lock, Architecture decision 0030), and discards the rest with a journaled count. The run's end discards every pending signal and journals the count before `run.finished`; a run that ended or is stopping refuses new signals, every path that ends a run (the planner's and the store-side ones) discards, and a check on `runs` refuses a terminal status with pending signals. A graph run whose root waits of the name have all been entered and whose version cannot continue as new refuses a signal (`409 NO_CONSUMER_AHEAD`) rather than keep what nothing can consume. The continuation's handoffs, and every path that reads a run outside its lock and compares its version at write time, accept a run whose version advanced only by buffered signals (one helper, kept by a source rule), so signals cannot starve them; a client's public `expectedRunVersion` keeps its exact meaning, bounded by the inbox's fill, and publication refuses, in a version that can continue as new, an entry `waitEvent` of a declared name, which a handoff would open without the planner. A reset rebuilds the pending rows of its prefix and, with reapply `SIGNALS`, treats a signal buffered after its point as a recorded signal: delivered, or buffered again when the new run's version declares it. No run-driven transition writes any aggregate row (Architecture decision 0050 decision 3 holds).
6. **Signal-with-Start buffers instead of refusing**, for a declared name: the new run is created and the signal is delivered or buffered in the same transaction; the binding-then-run lock order of Architecture decision 0050 is unchanged. An open holder is signalled as `signalRun` is.
7. **Switched on by the fleet, with a floor.** A version that declares a buffered signal publishes only once the operator recorded the requirement `signal-inbox-v1` (Architecture decision 0082) for control planes and engines; publication holds it through the shared `platform_requirement_hold` until it commits (refusing `CAPABILITY_NOT_ACTIVE` until it is recorded), records the version's level, and the requirement cannot be removed while a version of that level exists.

## Considered options

0. **Feature 004's path for an event that arrives before its wait** (`waitEvent.lookbackMs`, `inbox_events`, consumption recorded per consumer in `event_deliveries`, `steps.event_since` and `event_scanned_at`): admit a signal as an inbox event correlated to the run and read it through that path. Weighed by design 054 (Technical Plan 5) and rejected: its events live for a deduplication window and a look-back of at most seven days, then vanish without a record; every wait that looks back gets a copy; it delivers in a later scan, not at the wait's entry; its rows are namespace-wide, outside the run's lock, counters and lifecycle; its payloads are outside the run's retained bytes and outside `payloads`. Its consumer (the `waitEvent` node), its `wait.satisfied` event and the `payloads` store are reused. When a wait declares both a look-back and a buffered name, the inbox is read first, at the entry.
1. **Opt-in per version and name, an inbox of the run (chosen).** Runs in flight and existing callers keep today's answers; the inbox has no new lock and no aggregate edge; design 044 reuses it.
2. **Buffer every signal of every run.** Temporal's model, but it changes the answer to a call that callers rely on today (`409`), for runs already in flight (constitution principle IV). Rejected.
3. **Keep refusing (Architecture decision 0050 decision 4).** Leaves a parity gap that the owner put in release 0.3.0 (Owner decision 2026-11-24-1), and leaves design 044 without a substrate. Rejected.
4. **An expiry per buffered signal.** A signal that expires silently is a lost business message; the inbox is bounded by count and bytes, and lives as long as the run. Rejected for 0.3.0.
5. **Copies for waiting steps, one consumer when buffered.** The number of waits a signal satisfies would depend on timing. Rejected (design 054, Decision 054-003).
6. **Rows kept after settlement with a state and a partial index.** The table would grow with the history a journal already records. Rejected (Decision 054-004).

## Consequences

- An approval sent before its step is reached is no longer lost or refused, for versions that declare it; Signal-with-Start works for a workflow whose entry does some work first.
- A `409` from `signalRun` still means "not accepted" for every undeclared name; a `202` with `buffered: true` means "kept for a later wait while the run lives".
- One table of pending rows, written under the run lock; a count on `runs`, so a transition of a run with an empty inbox reads and writes nothing more; a wait's entry reads one indexed row only when the run has pending signals; a continuation and an end add at most three statements when the inbox is not empty. The budget suite gets lines for them.
- Every check of a run's 4 MiB counts pending payloads: they are charged to the run's existing byte ledger (`run_instance_usage`), beside its output bytes, under one database check of the sum.
- Rollback: removing `signal-inbox-v1` is refused while a version of level 1 exists, retired included; since published versions are never deleted, the first such version makes the floor permanent (it refines Architecture decision 0032 decision 8).
- A graph version that handles one signal per continuation segment moves every pending signal at every handoff (up to 1,000 rows and journal events); the guide points a high-volume queue to a code version.
- The publication hold and the floor are the shared mechanism of Architecture decision 0112.

# ADR-0091: The engines hand the cron triggers over automatically, through a narrow definer function, once the fleet is quiet and converged

**Status:** Proposed (2026-11-14)
**Decided by:** owner for the behaviour (OD-2026-11-14-4, "Automático no upgrade", against the assistant's recommendation to keep it manual); agent for the mechanism (tasks T018-082 to T018-087), not yet reviewed by the three repository reviewers, not accepted.
**Refines / supersedes:** amends ADR-0083 decision 4 (the handover is no longer made only at an operator's command) and its accepted limit on audit (D2042); **narrows ADR-0082 decision 1** (one function the runtime role may execute records one requirement, `schedules-v1` of the execution engines, under conditions it re-checks itself); extends ADR-0083 decision 5 (the lock order gains the policy row); amends `plan.md` of feature 018 ("the registry ships in a release before the handover can be used") and the premise of the header of migration `20270113000000_instance_registry` (lines 20-21, the same sentence; an applied migration is not edited, so the new migration's header says it). ADR-0082 decisions 2 to 8 and ADR-0083 decisions 1 to 3, 6 and 7 stand.
**Enforced by:** nothing yet; the checks are tasks. T018-085 writes them: the barrier race tests in `tests/fault/schedules-bulk-operations/auto_handover.rs`, the runtime-role tests in `tests/integration/schedules-bulk-operations/trigger_auto_handover.rs`, the `ALLOWED` list of `tests/integration/platform-foundation/runtime_privileges.rs`, the released-v0.2 upgrade test, and `infra/observability/tests/trigger_schedules_test.yaml` for the new alert. Until those exist and run, this ADR is a design only (constitution, rule 11).

## Context

Feature 004 fires cron triggers from the engines' legacy pass. Feature 018 makes every cron trigger a schedule and hands the firing to the schedule pass once, one way (ADR-0083). Today an operator does it with `control-plane schedule-trigger-handover --apply`, run with the schema-owning role, because the functions it calls are not executable by the runtime role `sagat_app`:

- `schedule_trigger_handover_complete`, `schedule_trigger_handover_census` and `schedule_trigger_handover_lock` are revoked from `sagat_app` (`crates/infra-postgres/migrations/20270114000000_trigger_handover.up.sql:240-248`), and so are `platform_requirement_activate`, `platform_requirement_lock` and `platform_requirement_remove` (`20270113000000_instance_registry.up.sql:290-293`, `:390-392`). ADR-0082 decision 1 says why: a compromised API process must not record a requirement that stops the fleet.
- The command refuses a vacuous census: without `--expect-live` it refuses when no engine is live (`apps/control-plane/src/handover.rs:163-180`).
- The runbook asks the operator to attest from the orchestrator that no engine or control plane older than this release runs (`docs/runbooks/schedules.md` section 6.2, step 1). That attestation is the only defence against G2005 (an engine binary older than the registry never registers and keeps its legacy pass, which ignores a pause) and G2020 (an old control plane publishes a trigger after the handover and its first ticks are lost).

The owner decided on 2026-11-14 that the handover happens during the upgrade without an operator's command (OD-2026-11-14-4), that schedules are on by default (OD-2026-11-13-8, so every engine of 0.3.0 lists `schedules-v1` unless `SAGAT_SCHEDULES_ENABLED=false` is set), and that the upgrade order is migrate, then engines, then control planes (OD-2026-11-14-3). Four facts of the code constrain how:

1. **`migrate` runs before the engines exist and must finish first.** In the compose stack the control plane and the engine start only after `migrate` has completed successfully (`infra/docker/compose.yaml:93-102`, `:162-164`, `:205-207`); the Helm chart has no migrate job at all (`infra/helm/templates/` holds none), so there `migrate` is an operator step. A `migrate` that waits for convergence would wait for engines that wait for it.
2. **The registry cannot see a 0.2 binary.** The registry ships in 0.3.0, the release that hands over; its migration says it must ship "in a release before any feature activates through it" (`20270113000000_instance_registry.up.sql:20-21`), and `plan.md` says the same. An operator's attestation covered that gap; automation removes the operator.
3. **A 0.2 engine is visible elsewhere.** Every engine of 0.1.0 and 0.2.0 runs the shard keeper unconditionally and announces itself in `scheduler_members` (`git show v0.2.0:apps/execution-engine/src/lib.rs`, line 168; `git show v0.2.0:crates/infra-postgres/src/partitioning.rs`, lines 51-60), and runs the legacy cron pass (`v0.2.0:apps/execution-engine/src/lib.rs`, lines 197-204). An engine of this release registers with `scheduler_owner` set to the same name (`apps/execution-engine/src/lib.rs:195-200`) before its keeper takes a shard (`:332-337`), and a refused or closed engine holds no member row (`docs/runbooks/instance-registry.md` section 3). So a live member with no live registered engine of the same name is an engine the registry cannot see.
4. **The runtime role can already stall what the handover locks.** `sagat_app` holds `UPDATE` on `workflow_triggers` (`20261012000000_events.up.sql:330`), so it can `LOCK TABLE workflow_triggers` in the mode the handover takes; it can already hold the registration lock open (G2000). A function it may execute adds no new way to stall publications or registrations.

What stays true: the check under the lock (`schedule_trigger_unconverged()`, an `EXISTS` over `schedule_trigger_drift`, `20270114000000_trigger_handover.up.sql:56-95`) is the one definition of converged (ADR-0083 decision 4); a registration takes the epoch `FOR SHARE` (`20270113000000_instance_registry.up.sql:197`) and an activation `FOR UPDATE` (`:323`), so an engine that registers without `schedules-v1` either commits first and is counted (`:333-341`) or waits and is refused (`:199-204`); the legacy pass reads the state at most every two seconds and fails open (`crates/scheduler/src/events.rs:706-738`, `crates/application/src/schedule_triggers.rs:242`); the control of a trigger-owned schedule opens five seconds after the commit (`schedule_triggers.rs:246`).

## Decision

1. **Who acts: the engines, through one narrow `SECURITY DEFINER` function (option a).** A new migration MUST add `schedule_trigger_handover_automatic(p_instance uuid, p_token bytea)`, owned by the schema owner, `search_path` pinned, `EXECUTE` granted to `sagat_app` and to nobody else. It MUST record nothing but the requirement `schedules-v1` for `EXECUTION_ENGINE` and the move of the handover from `LEGACY` to `HANDED_OVER`, and only when every condition of decision 2 holds inside its own transaction; it MUST take no argument that weakens a condition (no window, no count, no actor text). The existing owner-only functions stay owner-only; the new one calls them as their owner (`platform_requirement_activate`, or `platform_requirement_lock` when the requirement was recorded before, as D2051; then `schedule_trigger_handover_complete`'s checks), so there is one implementation of each check. The caller is the trigger reconciliation pass of an engine that runs the schedule pass (`crates/scheduler/src/trigger_schedules.rs:283-310`): after a convergence measurement that read `0`, while it reads `LEGACY` and the policy `AUTOMATIC`, at most once a minute per replica with jitter, first through a lock-free precheck that answers the same reasons, and only then through the function. The adapter MUST set `statement_timeout` (3 s) before the call, as `PgInstanceStore::operator_transaction` does (`crates/infra-postgres/src/instances.rs:116-126`).

2. **The condition, in one transaction, in this lock order and no other.** (i) The requirement epoch `FOR UPDATE` (`lock_timeout` 2 s): no registration commits meanwhile, so an engine that registers without `schedules-v1` is either counted or refused, never missed. (ii) The policy row `FOR SHARE`: its mode MUST be `AUTOMATIC`. (iii) The census, which MUST all hold: the caller is a live `EXECUTION_ENGINE` row whose token hash matches `p_token` and which lists `schedules-v1` (so the census is never vacuous: at least one engine is live); no live engine lacks `schedules-v1`; **no live `scheduler_members` row** (`expires_at` after now) **has an owner that no live engine row names as its `scheduler_owner`** (an engine the registry cannot see); **at least one live `CONTROL_PLANE`** is registered (the last step of the upgrade order has begun); and **the fleet is quiet**: the newest `started_at` of a live serving instance (either kind) and of a live scheduler member is at least `quiet_seconds` (policy row, default 600) before `clock_timestamp()`. (iv) The table of the cron triggers in `SHARE ROW EXCLUSIVE` through `schedule_trigger_handover_lock()` (2 s, `HANDOVER_BUSY`), then the handover row `FOR UPDATE`, then `schedule_trigger_unconverged()` MUST be false. (v) The requirement, the epoch, the history, the state, and the audit of decision 4, then commit. A failed condition MUST raise one of the closed reasons of decision 3 and change nothing. Before taking (i) the function MUST read the state without a lock and return `ALREADY_HANDED_OVER` when it is so (as `20270114000000_trigger_handover.up.sql:161-165`).

3. **The quiet window is the stability window; there is no count of converged rounds.** The check under the lock is authoritative, so convergence measured over N rounds adds nothing to correctness. What the window buys is a fleet that has stopped changing: a rolling update of engines or control planes registers a new row per replica, and each one restarts the window, so the handover comes `quiet_seconds` after the last process of the rollout started, when the old replicas of a normal rolling update are gone. `quiet_seconds` is the owner's to change (decision 5), between 0 and 86,400.

4. **A blocked handover says why: metric, alert and log.** The closed reasons are `POLICY_MANUAL`, `SCHEDULE_PASS_OFF` (this engine runs without the schedule pass), `ENGINE_LACKS_CAPABILITY`, `ENGINE_UNREGISTERED`, `NO_CONTROL_PLANE`, `FLEET_NOT_QUIET`, `UNCONVERGED`, `BUSY` and `CALLER_NOT_REGISTERED`. Every engine MUST export the gauge `trigger_schedule_handover_blocked{reason}` (1 for the reason it last found, 0 for the others, all at 0 once it reads `HANDED_OVER`): the trigger pass from the precheck and the function, and the legacy cron pass of an engine that runs no schedule pass with `SCHEDULE_PASS_OFF`, because an engine with `SAGAT_SCHEDULES_ENABLED=false` runs no trigger pass and would otherwise say nothing. It logs, once per change of reason, the reason and, for `ENGINE_LACKS_CAPABILITY` and `ENGINE_UNREGISTERED`, up to sixteen instance ids or member names (no tenant data). The alert `SagatTriggerHandoverBlocked` MUST fire when `max by (reason) (trigger_schedule_handover_blocked{reason!="POLICY_MANUAL"}) == 1` for one hour, with a runbook section per reason; an operator who keeps a fleet off schedules on purpose sets the policy to `MANUAL`, which silences it.

5. **The opt-out is an owner-only database policy, not an environment variable.** A singleton `schedule_trigger_handover_policy (mode AUTOMATIC | MANUAL, default AUTOMATIC; quiet_seconds, default 600; changed_by, changed_db_role, changed_at)` MUST be writable only by the schema owner, through `control-plane schedule-trigger-handover --policy automatic|manual [--quiet-seconds N] --operator NAME`, and readable by `sagat_app`. An environment variable such as `SAGAT_SCHEDULES_AUTO_HANDOVER` MUST NOT be the opt-out: replicas could disagree, and the runtime role, which the function trusts for nothing, could ignore it. Offering the opt-out at all is a product choice (O1954); this decision is the recommendation, with `AUTOMATIC` as the default the owner chose.

6. **Audit: the platform record and one tenant record per affected tenant.** The handover row MUST gain `changed_mode` (`OPERATOR` | `AUTOMATIC`, null while `LEGACY`) and `changed_instance` (the engine's instance id for `AUTOMATIC`, null otherwise); an automatic handover records `changed_by = 'system:engine'` and `changed_db_role = session_user` (`sagat_app`), and the registry history records the same actor. In the same transaction, under the lock, one `audit_records` row MUST be written for every tenant that has at least one cron trigger: action `schedule.trigger_handover`, actor `system:engine` or the operator's subject, resource `platform`/`schedule_trigger_handover`, reason the mode. This replaces "the handover has no tenant audit entry" (D2042) for both paths. Tenants seeing a platform act in their audit is a product choice (O1955); the cost under the lock is not measured (G2244). The process that committed it MUST log one line at `info` (`the cron triggers were handed over to the schedule pass`, with `mode`, the instance id, the epoch, the live engines and the tenants audited; the operator path keeps its OS user and host) and increment `trigger_schedule_handovers_total{mode}` (a closed label, created at zero); every engine already sets `trigger_schedule_handed_over` and logs the stop of its legacy pass (`events.rs:717-720`).

7. **The operator command stays.** `schedule-trigger-handover` keeps every check and refusal it has, records `changed_mode = OPERATOR`, writes the audit of decision 6, and its dry run also prints what the automatic path would answer now (the reason, or "the engines will hand over automatically within a minute"). It does not require the fleet to be quiet or a control plane to be registered: an operator who runs it attests those, as the runbook says today.

8. **One-way, unchanged.** Nothing in this ADR adds a way back; the guard of the handover row and of the requirement stay (`20270114000000_trigger_handover.up.sql:105-121`, `:225-238`).

## Considered options

1. **(a) A narrow definer function the engines call (chosen).** It runs where the information is (the reconciliation measures convergence), in every deployment, with no manifest change and no owner credential in a long-running process. It narrows ADR-0082 decision 1 for one requirement only, and that requirement can stop no live engine because the function refuses while any live engine lacks it. What a holder of `sagat_app` gains is the choice of the moment among the moments the owner already decided are right, and a new path to hold the epoch `FOR UPDATE` (G2243), which it could already approach through the registration lock (G2000).
2. **(b) The `migrate` job, as the owner, retried until the condition holds.** Keeps ADR-0082 decision 1 whole. Lost: `migrate` must finish before the engines start (`compose.yaml:162-164`, `:205-207`), so a `migrate` that waits for converged engines deadlocks the upgrade, and one that returns must be run again after the engines converge, which is an operator step again. The Helm chart has no migrate job to retry.
3. **(c) The control plane at start-up.** Control planes start last in the upgrade order, which is a useful signal. Lost: the control plane runs as `sagat_app` too, so it needs the same function as (a); at its start the reconciliation has rarely converged (minutes at 10,000 triggers, ADR-0083 Consequences), so it needs a loop, a background job in the API process; and (a) gets the same signal by requiring a live control plane.
4. **(d) A long-running owner-credentialed job (a CronJob or a compose service running `schedule-trigger-handover --auto`).** Keeps the owner-only rule. Lost: it puts the schema owner's credentials in a process that lives as long as the platform, which ADR-0082 avoided by making the operator's act one-shot, and it is automatic only where the operator deploys it.
5. **Convergence for N consecutive rounds instead of a quiet window.** Lost: the check under the lock already decides convergence; N rounds would only delay, and would not see the old replicas a rolling update leaves running.
6. **No detection of unregistered engines; rely on the census.** Lost: with no operator to attest, the census cannot see a 0.2 engine (Context, fact 2), and the automatic handover would most often happen in the middle of the engines' rolling update, the moment G2005 is likeliest.

## Consequences

Good: an upgrade to 0.3.0 with defaults hands the cron triggers over by itself, about ten minutes after the last control plane started, once the schedules have converged; a fleet that cannot be handed over says why, per reason, in a metric, an alert and a log line; the engines a 0.2 rollout leaves running block the handover instead of being attested away; tenants see the change in their audit.

Bad and accepted: the runtime role may execute one function that records a requirement (ADR-0082 decision 1 is narrowed, not kept); a 0.2 engine started after the handover still ignores a pause (G2240, the residual of G2005); an old control plane that survives the quiet window still loses the first ticks of a trigger it publishes (G2241, the residual of G2020), and nobody attests the control planes any more; a fleet that never stops starting processes (an autoscaler, feature 036, or a crash loop) never hands over by itself (G2242) and the operator command is the way; a caller can hold the epoch lock open after the function returns (G2243); a holder of `sagat_app` can register a fake engine row to satisfy "the caller is a registered engine", which is a liveness proof, not authentication (G2245); the audit rows are written under the table lock at a cost not yet measured (G2244).

Operational cost: one lock-free precheck per replica per minute while `LEGACY`; one locked attempt per replica per minute only while every precheck condition holds; nothing after the handover (the state is read first and a handover is final).

Compatibility with runs in flight: none changes. The gate of the legacy pass, the shared key, the five-second control window and the reconciliation are those of ADR-0083.

**What the release notes of 0.3.0 MUST say** (OD-2026-11-14-4):

- the cron triggers of every published workflow move from the legacy cron pass to the schedule pass **automatically** once every live engine runs the schedule pass, no engine older than 0.3.0 is running, a control plane of 0.3.0 is running, nothing has started for ten minutes and every trigger has its schedule; when it happened (`trigger_schedule_handed_over`, the log line, `SELECT state, changed_mode, changed_at FROM schedule_trigger_handover`, the tenant audit entry);
- it is **one-way**: there is no command to go back, the schema `down` refuses after it, and engines must not be rolled back below 0.3.0 after it, because a 0.2 engine ignores the pause of a trigger schedule (G2005, G2240);
- to keep the choice of the moment: run `control-plane schedule-trigger-handover --policy manual --operator NAME` with the owner role right after `migrate` and before the engines (the quiet window leaves ten minutes even after); then `--apply` when ready;
- the accepted losses: G2005 (a 0.2 engine started after the handover ignores a pause), G2020 (an old control plane still publishing after the handover loses the first ticks of that trigger), G2021 (a backfill over ticks the legacy pass started more than seven days before starts them again);
- an engine with `SAGAT_SCHEDULES_ENABLED=false` holds the handover (alert `SagatTriggerHandoverBlocked`, reason `SCHEDULE_PASS_OFF` or `ENGINE_LACKS_CAPABILITY`) and, after an operator's handover, is refused at registration.

**Rollback.** Before the handover: set the policy to `MANUAL`, or roll the binaries back to 0.2 (they never call the function) and the schema with the existing `down` (which refuses once a registry history row exists, ADR-0082 Consequences). After it: not supported, as today.

## Test plan (T018-085; every test written first and seen failing for the right reason)

Races are held by an open transaction or a held lock and watched in `pg_stat_activity` (`wait_event_type = 'Lock'`), never timed, as `tests/fault/schedules-bulk-operations/instances.rs` does.

- **An engine that registers without `schedules-v1`, both orders.** (1) A test transaction calls `instance_register(..., '{}')` for an engine and stays open; the function is called on a second connection and is seen waiting on the epoch; the registration commits; the function refuses `ENGINE_LACKS_CAPABILITY` naming the instance, and nothing is recorded (state `LEGACY`, epoch unchanged, no history, no audit row). (2) A test transaction calls the function (conditions true) and stays open; the registration is seen waiting on the epoch; the function's transaction commits; the registration answers `CAPABILITY_MISSING`, and the engine's gate stays closed.
- **A publication in flight, both orders.** A publication that inserted a cron trigger and is open makes the function wait at most two seconds and answer `BUSY` with nothing recorded; a function holding the table lock makes the publication wait, and after both commit the trigger has its schedule (the publication made it) and the view is empty.
- **Two engines, and an engine and the operator, at once.** One answers `HANDED_OVER`, the other `ALREADY_HANDED_OVER`; the epoch moved by one; one history row; one audit row per tenant.
- **The policy changed to `MANUAL` while the function runs, both orders.** Held by the policy row lock: either the handover commits and the policy change finds it done, or the function finds `MANUAL` and refuses.
- **The census conditions, one at a time.** A live scheduler member with no registered engine (a 0.2 engine modelled by its `announce` statement, as `v0.2.0:crates/infra-postgres/src/partitioning.rs` writes it) refuses `ENGINE_UNREGISTERED`; a member that expired does not; no live control plane refuses `NO_CONTROL_PLANE`; a row started inside the window refuses `FLEET_NOT_QUIET` (the test writes `started_at` in the past as the owner, no sleep); a wrong token refuses `CALLER_NOT_REGISTERED`; an unconverged trigger of each kind of the view refuses `UNCONVERGED`.
- **A crash at each statement.** The backend of the function is terminated while it is held at each of its waits (the epoch, the policy row, the table, the handover row) and after the last write before the commit: nothing is recorded, and the next call hands over.
- **The runtime role.** As `sagat_app`: the function is executable and the operator functions, the policy write and the history read are refused; a call while any condition is false changes nothing; the state cannot be moved by any other statement (the guard).
- **The privilege audit.** `runtime_privileges.rs`: the new function is not in `ALLOWED` (the role holds it); the policy write of the operator command is, with its reason; the entries of lines 105-113 stay.
- **The migration** (`.claude/skills/migration/SKILL.md`): a timestamp after every migration on `develop` and the open 018 branches; additive (a new table, two nullable columns); grants in the file; the new text columns classified; a `down` that restores the previous schema and refuses while the handover row says `AUTOMATIC`; migrate up, down and up with data, both roles.
- **The released-v0.2 upgrade.** From the `v0.2.0` schema with cron triggers and a 0.2 engine's member row live: migrate; a 0.3.0 engine and a 0.3.0 control plane register and converge; the handover is refused `ENGINE_UNREGISTERED` until the 0.2 member leaves, then `FLEET_NOT_QUIET` until the window passes (backdated), then is made by the engine; one run per tick across the whole sequence; a pause is refused before and honoured after the control window.
- **The alert.** A `promtool` rule test of `SagatTriggerHandoverBlocked` (fires for each reason but `POLICY_MANUAL` after an hour, never after the handover), and its runbook anchor in `contract_observability_operations`.

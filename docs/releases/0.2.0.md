# 0.2.0

This release combines the implemented PostgreSQL/OpenBao connection feature, per-field payload
classification, Studio navigation and run authoring, CLI diagnostics, and the verified bounded
workflow execution increments. It does not claim completion of feature 014's remaining tasks.

## PostgreSQL connections and OpenBao

Administrators can configure namespace connections and create or select OpenBao-backed credentials
in Studio. The same logical connection is available to all five SDKs, visual workflows and ad hoc
database execution. Runs pin connection revisions; current access and secret authority are checked
again when a capability is used. Probes execute through the isolated database runner and retain
the tested revision and durable outcome.

PostgreSQL is the only supported driver. OpenBao uses versioned static credentials through KV v2.
This release does not provision a customer database or change its account password when a stored
credential is rotated. Database settings, workload authentication, destination allowlists and
resource limits require operator configuration; production defaults do not use OpenBao dev mode
or root tokens.

Connection management/use, ad hoc execution, writes and result reading have distinct permissions.
Credentials stay out of workflow definitions; logs and telemetry omit SQL, parameters and credentials.
Results are bounded and disclosed
only through the separately authorized result operation. An external write has at-least-once
attempt semantics; an ambiguous outcome requires reconciliation or manual review, not a blind retry.

See [connections](../runbooks/database-connections.md), [runner](../runbooks/database-runner.md),
[OpenBao](../runbooks/openbao.md) and [recovery](../runbooks/database-recovery.md).

## Classified values and a breaking event-read change

New workflow versions can classify fields as public, internal, pii or secret. Interpretation is
pinned to the published version. Existing versions remain at rules 0 and disclose no values through
the new operation. PII requires an explicit namespace grant and an audited reveal; administrators
also need that grant. Secret-classified values are never disclosed. Structural inspection remains
available under its existing permission.

**Breaking:** `getInboxEvent` omits `data` by default; `getConnectorDeadLetter` omits `body` and
`headers` by default; `listConnectorDeadLetters` never returns those values. Detail values require
`reveal=pii`, `event:read`, current `payload:read-internal`, and a reveal grant in that namespace.
A successful reveal is audited before returning values, with private, non-cacheable responses.
Clients must handle absent value fields rather than assume earlier raw payload responses.

See [classification](../runbooks/payload-classification.md) and [events](../runbooks/events.md).

## Studio and CLI

Namespace menus appear after explicit selection and include Connections, Secrets and Ad hoc
database. Run lists adapt to narrow screens, retain status/workflow filters in the address and
can start a durable run through the platform API. Start Run refuses numbers that cannot be
serialized exactly; use strings for exact integers and decimals. Clear filters also resets Origin.
Graph controls remain visible on the taller canvas. The committed onboarding diagnostic corpus
now executes through the current CLI validator.

## Execution boundaries

The server's integrated worker protocol is 1.6: scoped identity was introduced in 1.5 and managed
database capabilities in 1.6. SDK defaults and capability negotiation retain their documented gates;
package version 0.2.0 does not change protocol negotiation by itself.

This build exposes the restricted publication subsets documented in the workflow runbook. General
nesting remains closed. Large-workload acceptance and unfinished capacity/control/finalizer work
remain pending; accepted declaration limits do not establish production capacity guarantees. The
eight open feature-014 tasks remain open. Managed database nodes are root-only and cannot share a workflow definition with collections,
loops or continuation policy. Source-level proof fixtures do not enable
an unsupported production path. See [workflow boundaries](../runbooks/workflow-primitives.md) and
[ADR-0036](../adr/ADR-0036-integrated-scoped-managed-and-classified-execution.md) and the
checkpoint boundary in [ADR-0040](../adr/ADR-0040-release-checkpoints-preserve-incomplete-feature-boundaries.md).

## Upgrade and recovery

Back up PostgreSQL and test the upgrade on a restored copy. Stop admissions, drain or stop all
control-plane, engine and runner writers, and run migrations once as the database owner. Deploy
compatible engines, workers, readers and Studio before enabling new-capability publication and
starts; then resume admissions. During rollback, stop new starts and retain compatible readers
and workers until runs using new capabilities drain. Retain their schema and history; do not run
down migrations automatically. Mixed old/new writers are unsupported by the coordinated security
upgrade procedure. Render Helm with explicit API/worker/metrics and DNS/PostgreSQL/OIDC peers, plus
NATS peers when configured; missing, empty and global peers fail closed. The prior-release compatibility gate covers retained v0.1.0
root runs and the old Studio, not arbitrary old-server writes of new scoped workflows.

Standalone, unreleased feature-017 migration numbering must not be applied over the integrated
migration history. Checksum/history mismatches intentionally refuse startup. Preserve backups and
follow ADR-0036; do not edit an applied checksum or rerun renamed migrations to force acceptance.

OpenBao cutover has one authoritative provider, with no automatic local fallback. Application
rollback alone does not restore migrated credential authority. Coordinated recovery must preserve
PostgreSQL references, the OpenBao Raft state/tombstones and the intent-binding key. Follow the
quiesced recovery procedure and keep cleanup stopped until references are verified. Arbitrary-point
cross-store recovery is not promised.

## Distribution

The CLI and all five SDK packages use 0.2.0. Distribution remains GitHub Releases only: CLI archives
for Linux x86_64/arm64 and macOS arm64, SDK packages, SHA256SUMS and GitHub provenance attestations.
There is no npm, PyPI, NuGet or Maven registry publication. Go uses the module tag `sdks/go/v0.2.0`.
No environment is deployed by publishing these artifacts. See [release verification](../runbooks/release.md).

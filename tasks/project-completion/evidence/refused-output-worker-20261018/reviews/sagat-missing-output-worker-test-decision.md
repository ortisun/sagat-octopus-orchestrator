## Decision and limit

The proposed mechanism can honestly test the output-dependent-compensation clause of section 11.4: execute a fixture worker's actual compensation implementation against the unmodified `TaskLease.input_json`, then report the implementation's real error through public `FailStep`. Its required input is a worker application contract. The engine has never promised to infer that requirement from the activity name. No new IR field, platform failure code, grant, or input evaluator is needed.

This differs materially from choosing `FailStep` because `iteration == 16`: the same application function must succeed with retained reservation outputs and fail when its required field is absent. A strict parser alone proves the input requirement; consuming the parsed identifier in a tiny test-owned reservation release action additionally makes the successful compensation concrete. Neither proves an external provider was undone.

The earlier note correctly identifies the absent authored input declaration, but its conclusion that any worker-defined dependency is necessarily a fake fixture is too broad for the literal section 11.4 wording. The canonical declaration binds `line.release`; its implementation supplies its own ordinary business input contract. If “declared inputs” in section 11.2 instead intends an engine-enforced IR dependency, this mechanism cannot satisfy that stronger requirement, and no supported bounded implementation identified here can. Clarify the contract rather than claim such enforcement.

Suggested narrow clarification: “For a compensation activity declared with `compensateWith`, its worker implementation may require the forward output in the ordinary task context. Demonstrate that implementation's real missing-input error through the existing worker failure/manual-review policy; this is not an engine precheck of arbitrary worker requirements.”

## Smallest useful test unit

One new integration scenario, fixture-local handler/types and a sized output helper can live in the existing `tests/integration/workflow-primitives/byte_ceilings.rs` (or one focused test module if root prefers its size boundary). Do not generalize `Flow` or change production code to add this proof. The existing successful compensation case remains useful for a handler whose required inputs are available without the refused output.

1. Produce 17 genuine successful forward reservation results through the existing public fixture. Change the new scenario's result shape from the existing JSON string to `{ "reservationId": <unique opaque string>, "padding": <ASCII string> }`. Compute padding from the serialized empty-padding object; assert each fully serialized output is exactly 250,000 bytes, below the 256 KiB value ceiling. The first 16 outputs retain exactly 4,000,000 bytes; the seventeenth candidate makes 4,250,000, above 4,194,304. Keep Return's result `1` as in the current fixture. Read/assert the actual quota and retained-output facts; do not assume merely changing the shape preserves them.
2. The fixture worker uses one `release_reservation(input_json, fixture_reservations)` implementation for every compensation. Its typed deserialization requires `steps.reserve.output.reservationId`; no `Option`, serde default, empty fallback, iteration branch, or lookup through test expectations. The handler receives only actual lease bytes and its own application state. It must use the parsed identifier, for example removing that exact reservation from a test-owned in-memory set created by the forward fixture. This is a test business action, not provider I/O. Keep the handler in the client/test harness; never install business logic in the engine, evaluator or scheduler. Existing `Flow` uses real gRPC transport, although the integration harness itself is one process; this test does not prove production process isolation.
3. Complete retained compensations only after that same handler succeeds. Assert the exact returned/released identifier matches each corresponding unique forward result and that the retained reservations were removed. No extra all-success run is needed for this positive control. The handler must have no access to the expected-output map used by assertions, so it cannot silently source an identifier outside the lease.
4. On the refused member, assert its forward step remains SUCCEEDED, its output reference is absent, its actual compensation lease has the correct target identity/key, and its valid JSON task document lacks `steps.reserve`. Invoke the same handler and observe the typed input error with no release action. Report that error using a fixed documented fixture application code, e.g. `FIXTURE_RESERVATION_OUTPUT_REQUIRED`, with `retryable=false` and no payload-bearing message. Do not call this a built-in platform missing-input code. Do not convert an unrelated malformed/unknown-reservation error into this diagnosis.
5. Observe the existing persisted compensation `WAITING`, `waiting_kind=OPERATOR`, fixture failure code and run `MANUAL_REVIEW`. Verify the saga still owes the exact refused member, the forward success is retained, and no successful/skip event was manufactured for that compensation. Run ordinary scheduling again and verify it remains unresolved, with no final COMPENSATED. Verify journal replay at this point. No sleeps, retry-backoff SQL, synthetic terminal-state writes or output reinsertion are required.
6. Use the existing authorized HTTP operation `RESOLVE_STEP`, exact `lines[16]/reserve~c` address, outcome `FAILED`, the same fixture error code and an honest fixed explanation that the missing reservation output prevents release. This is safer than pretending a successful release or claiming manual provider repair. Assert exactly the relevant `saga.step_resolved` audit (tenant, actor, full resource identity, failed outcome/reason), genuine `step.resolved`, final `COMPENSATION_FAILED`, the still-unreleased fixture reservation, and successful journal replay. The original RUN_DATA_LIMIT stop remains the original cause. `RETRY_COMPENSATION`/`SKIP_COMPENSATION` are unnecessary to prove this case.

## Acceptance boundary

The current 17-member fixture is a current-binary producer, not the old binary producer demanded by section 11.4's introduction and Q10c. It can close a focused current-version missing-output regression after actual execution; it cannot close old/current upgrade acceptance. Reuse the same worker handler against genuine old-produced reservation objects for that later gate. Also, `Flow::verify` proves durable journal/projection replay; it is not by itself a literal process restart.

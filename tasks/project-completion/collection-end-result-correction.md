## 3. Narrow preparation contract

1. Retain the existing pinned definition, own Run revision, scope identity, ordered checkpoint digest list and aggregate digest/content. The current scheduler snapshots `RunTx::data`, definition and state under an own-Run lock and drops that read transaction (`passes.rs:989-1047`). Its later collection write is an optimistic computation: revision recheck and source digest equality are mandatory.
2. Build the aggregate exactly as today. Stage it in cloned `RunData` at the **actual owner ExecutionInstanceId**. Clone the observed `RunState`, apply the same successful CollectionFinished and owner StepRouted decisions, and call the existing `release_pending` reducer before deciding whether evaluation is needed. Keep all the resulting ordinary reduction events; do not jump directly from the pinned End declaration to the evaluator. This preparation uses the observed own-Run state/charges and the existing command's time basis; it does not mutate durable state.
3. Invoke the shared bounded `ExpressionEvaluator::run_result` calculation **only if** that reduction returns the actual matching `Evaluation::Output { node, expression }` for the pinned successor End. It includes existing error redaction and 256 KiB / 4 MiB checks. Extract the current Output calculation into a small application helper reused by Engine and scheduler; do not duplicate evaluator or quota semantics. If reduction settles with no pending evaluation, including a genuine INSTANCE_LIMIT stop before End activation, prepare **no evaluation answer**. An unexpected pending evaluation is a typed refusal, not permission to execute another primitive. Keep non-End routing on its existing path.
4. Add to `CollectionFinish` a semantically meaningful optional typed End answer, for example `Option<Result<Vec<u8>, FailureCode>>`, with construction/access through the existing command. `None` means **no Output evaluation was requested**: this includes non-End routing, an End with no expression, and a reducer refusal before evaluation even when End declares outputExpr. `Some(Ok(b"null"))` is a retained JSON null, not absence. `Some(Err(code))` carries no output bytes. Only the existing EXPRESSION_ERROR and RUN_DATA_LIMIT answers belong to this evaluation boundary. INSTANCE_LIMIT is an ordinary reducer event/code, never an invented evaluation error or output answer. The command carries no caller-selected final status and needs no generic reduction DTO.
5. On a **new application**, the store obtains the successor from the pinned definition, validates revision/source/budget state, and independently repeats the same pure collection-finish/routing/release reduction from its locked pre-transition state. Its actual pending evaluation controls answer consumption: a matching Output request requires exactly one answer; no pending Output requires no answer, including the pre-evaluation stop. Reject a missing requested answer or an unexpected supplied answer with InvalidTransition; do not silently turn either into EndReached. Reject unexpected pending evaluations. The store persists its own reproduced events rather than trusting a supplied refusal classification or final status. Digest validation derives from exact supplied output bytes; SQL never evaluates the expression.
6. Source digest/Run revision mismatch rejects the computation; recompute only from a fresh snapshot. Do not retry an evaluated answer or a prepared no-evaluation branch against a changed revision. The own scheduler/Run guards still extend through COMMIT. A matching committed finish is a replay of the recorded branch, not a fresh reduction/evaluation; section 5 defines this boundary.

The immutable published End expression is authoritative. Shared evaluator reuse is an internal implementation choice, not an excuse to change the output expression language, classification, limits or accepted public shape. Existing non-End collection routing and optional no-result terminal behavior must remain covered.

## 4. One transaction, one terminal decision

### Storage and reducer boundary

Keep `BeginSafely`, tenant/namespace qualification, immutable member-chain serialization where already applicable, the **child's own** Run lock, own scheduler shard owner/generation/expiry guard held to COMMIT, current revision check, scope and checkpoint checks, capacity/instance rows, and source byte verification. Current authorities are `primitives.rs:289-351,634-650,2554-2663`; the scheduler authority is made from `hold_for(run)`, not the parent lease. No parent Run lock is added here.

Refactor the existing collection finalizer's terminal portion to use the existing `PgRunTx` staging/persistence machinery inside its **existing transaction**. `PgRunStore::begin_in_transaction` (`execution.rs:169`) and `PgRunTx` (`2968`) provide a real existing transaction owner; they are not an evaluator port. The transaction must load the pre-transition state before changing scope projections. Keep SQL preparation and persistence access crate-private; do not expose an unguarded connection or a public generic transaction callback.

The implementation must demonstrate the following order as one uncommitted unit:

- Validate the first-application preconditions and retain the aggregate payload through the normal tenant quota path.
- Produce the same primary `CollectionFinished(Succeeded, aggregate_digest)` and owner `StepRouted` events with the same owner identities and consecutive source sequence references. The scope closes successfully even if a later End expression fails **or the ordinary planner stops before End evaluation**. Neither may retrospectively turn a genuinely successful collection into a failed source.
- Stage the owner aggregate in `Effects.outputs` and owner step `output_digest`, before any certification can observe that successful finish. Keep `iteration_scopes.result_digest` as the same aggregate digest. This writes only the owner being finished now; it never repairs an already closed owner.
- For End, independently run the existing pure `RunState::apply` / `release_pending` reduction from the locked pre-transition state. The existing `Progress`, `RunEvent`, `Resolution` and `Effects` types already express it. Use `resolve(Resolution::Output)` and validate/consume the supplied answer only when reduction actually requests the matching pinned End evaluation. If reduction instead emits RunStopRequested(INSTANCE_LIMIT), End cancellation and RunFinished, persist those ordinary reducer events with no evaluation answer or End output. Do not synthesize StepFailed(EXPRESSION_ERROR), accept an unused answer, insert EndReached, or special-case the final Run status. A nonmatching or unexpected pending evaluation is a typed refusal, not implicit execution of another primitive. Keep non-End routing on its existing dedicated path.
- Use the normal result persistence: End success output is retained in `payloads`, associated with the End step, named by `end.reached.payload_digest`, and copied by digest into `runs.result_digest`; normal reducer events and the final Run status/revision are persisted together. Existing implementation: `execution.rs:3848-3904,3944-3974,4093-4153`. Reusing that pipeline avoids hand-maintaining the End failure event sequence, stop code and error routing.
- Retain exactly one `collection.finished` outbox record under the command's existing outbox identity. Let the one terminal reducer/persistence owner emit RunFinished and its outbox; remove the obsolete parallel manual End/Run terminal writes from that branch. Metadata hints contain identifiers/status/trace, never payload values.
- Optional audit and `telemetry_pending` head commit with the journal. Do not double-insert audit or double-advance telemetry when delegating to normal persistence (`execution.rs:4051-4078,4156`; `primitives.rs:546-569`). Then COMMIT once.

An **evaluated** End failure returns StepFailed with the existing evaluation code; no End payload, EndReached result or Run result is produced. A **pre-evaluation** instance-limit refusal has no Output answer and is not an End evaluation failure: retain the ordinary RunStopRequested(INSTANCE_LIMIT), cancellation and terminal reduction instead. The ordinary reducer determines stop/routing/RunFinished in both cases. The genuinely completed collection and its owner aggregate stay successful and retained, with their source references intact. Existing scope compensation is not redesigned here and no terminal status may be manually forced around it.

## 5. Replay, immutable source and ordinary child boundaries

A completed historical finish with no End payload remains that historical result. Never evaluate End during replay, populate its old Run result, rewrite its EndReached event, or update an old owner. `verify_run` already accepts historical None/None and checks new Run result digest equals the latest EndReached payload digest (`execution.rs:406-422`). Keep that rule.

The current matching collection replay recognizes lifecycle SUCCEEDED plus aggregate digest, finish outbox identity and finish sequence before revision CAS (`primitives.rs:2611-2632`). Adding an End answer needs a careful match rule:

- First-application commands require an answer only when the store's independently reproduced reduction actually requests the matching Output evaluation. A pinned expression alone does not establish that precondition.
- Canonical original replay of a **new** completed finish validates its recorded terminal branch against the same source. For an evaluated branch, validate retained End outcome/output and reject contradictory supplied bytes. For a recorded **pre-evaluation INSTANCE_LIMIT refusal**, require no answer, verify the successful collection/owner routing bindings and the actual subsequent INSTANCE_LIMIT stop/cancel/finish metadata, and verify no End output, EndReached result or Run result was recorded. The recorded cancellation branch has no evaluated End outcome to compare. Do not demand one, call the evaluator, or rerun release_pending against the now-finished state. Both branches return `applied=false` with no output writes, byte charge, audit, outbox or other mutation. An unexpected supplied answer for the recorded no-evaluation branch is DuplicateMismatch, not a new evaluation attempt.
- Historical original replay with no supplied End answer must keep the recorded no-result result and remain metadata-only. Do not reinterpret absence as a fresh expression decision.
- A new End evaluation failure **or genuine pre-evaluation refusal** leaves the collection SUCCEEDED and the Run failed/stopping. Permit only the matching already-committed replay in that state; the old `RUNNING|WAITING|SUCCEEDED` prefilter must not accidentally reject this newly legal replay or permit a fresh finish on a failed Run. Replay and first-application status checks must be separated.
- Exact event/step/Run bindings distinguish a retained evaluated answer, a recorded pre-evaluation stop/cancellation, and the historical successful EndReached with omitted output, without adding a public version flag. No-evaluation replay reads these bounded retained metadata facts; it does not derive a missing answer from current definitions or mutable final status alone. If a branch cannot be proved from retained facts, stop and record a compatibility decision; do not guess.

Native source certification retains five references: admission, return, checkpoint, collection finish and owner routing (`leaf_certification.rs:552-650`). Preserve their event kinds, addresses, detail meanings and actual sequence identities. In particular the owner routing reference remains the finish sequence + 1. A new successful owner's output exists **before** its first native certificate. Subsequent End evaluation, terminalization or parent notification may change mutable execution/relationship state but must not change that selected owner, iteration, checkpoint, retained source events or original certificate.

The ordinary child regression creates the child through the public parent child node and real scheduler path; child is unchained and carries the actual ParentLink. Existing public child helpers are in `leaf_certification_child.rs:54-126,312-390`. Do not seed `runs.result_digest`, child status, parent flags, journal, a certificate or receipt. ## 6. Mandatory separately bounded decision `.1d.0Q`: legacy output reads and aggregate quota refusal

This dependency is identified by this read, not solved by silently broadening the fanout task.

**Read compatibility requirement.** An active pre-correction Run can already have a successful `lines` scope and its authoritative retained aggregate while `steps.lines.output_digest` is NULL. Its later End can read `steps.lines.output`. A new first finish writes only its own current owner output. It must not backfill the old owner, source certificate, journal or closed Run.

**Preferred compatible read, subject to the separate quota decision:** load a read-only RunData fallback for a successful root collection whose owner output is absent, from its existing scope aggregate payload, qualified by tenant/Run/full owner identity and verified against the recorded successful finish/digest. Prefer the real step output when present; a contradictory present digest is corruption, never an overwrite. Do not recompute old member expressions, infer a result from a node name, reopen a scope or create a historical End result. A committed old no-result Run stays no-result. This fallback is derived from real immutable producer output; it is not synthetic final state.

**Accounting that must accompany it:** the existing ledger is seeded and incremented from `steps.output_digest` references only. A fallback aggregate is therefore absent from that ledger. Adding it only to evaluator context but omitting its size from future Run budget checks is unsafe. A possible bounded solution is an effective total of the existing ledger plus verified missing-owner aggregate bytes, without updating historical owner rows or journal. Its storage guard must agree with preflight, charge new physical step-output references once, and avoid double counting when a new owner output is already present. This needs a genuine legacy producer/restart fixture, not a SQL UPDATE that erases a new output to pretend an old writer ran.

**Concrete unresolved typed failure:** old sources or an empty collection can make the effective aggregate itself exceed the remaining Run budget at final finish. The current `CollectionDrainReason::Failed { iteration, code }` requires a real still-admitted failed member or pending Return (`primitives.rs:1856-1916`); a completed checkpoint or empty collection cannot satisfy it. The only no-iteration failure currently available is `StorageQuotaExceeded`, pinned to that exact code, audit action and SQL constraint (`domain/execution/event.rs:424`; `primitives.rs:1793-1804,1833-1844`; migration `20261106000000_collection_storage_quota_drain.up.sql`). Neither can honestly encode this `RUN_DATA_LIMIT`.

The next bounded decision must choose and prove an internal **collection-boundary data-limit drain** consistent with the existing RUN_DATA_LIMIT contract, or provide a source-backed alternative that handles these real states. It may need an additive enum/event-codec/schema constraint change. This document does **not** authorize adding a fictional iteration index, repurposing the storage-quota audit, weakening the logical ceiling, a production feature/profile flag, or amending an already applied migration. It also does not authorize a broad general drain redesign.

If the selected solution needs a new durable reason, enumerate all readers before implementation: domain event/state/scoped-saga matches; PostgreSQL full/path readers, event codec and drain/finish persistence; scheduler fallback; current migrations/compatibility fixtures; contract documentation and telemetry's existing failure classification. Exact migration timestamps are allocated later by root (`014 plan.md:150`), after checking parallel work. Old readers must not encounter a new reason they cannot decode; compatible binary rollout/rollback needs a reviewed gate. ADR0030/0032 already require quota preservation and additive compatibility, but an incompatible deployment strategy would require a separate decision and must not be hidden in this patch.

**Acceptance gate:** .1d.0Q remains open. Do not mark C1/.1d.0 resolved or authorize result-bearing .1d success evidence merely because the fresh scalar test passes. This is a substantive bounded implementation prerequisite, not a whole-protocol review request.

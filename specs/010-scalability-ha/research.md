# Research & Decisions: Performance, scalability and high availability

## Main decision

Partitioned/indexed PostgreSQL; scheduler owner leases; worker pool autoscaling; telemetry-guided tuning. Evaluate another journal backend only via ADR/benchmarks.

## Rationale

Scale scheduler, workers and millions of waits without state loss, and quantify the real limits of the architecture. The decision respects the recovery, auditability, security and versioning properties defined in the Constitution.

## Alternatives considered

1. **Generic ad hoc queue-based solution:** rejected as the sole durability mechanism, since message delivery is not equivalent to a transaction over workflow state.
2. **Independent services per feature from day 1:** postponed to avoid operational and consistency complexity without a benchmark.
3. **SDK-specific logic:** rejected for core invariants, to avoid behavior differences between languages.

## Risks and mitigation

- Complexity/scope risk: deliver P1 user stories separately, running contract tests.
- Semantic ambiguity risk: encode reducers and golden fixtures, do not decide via UI alone.
- Crash/redelivery risk: test harness with real failures at checkpoints.
- Security risk: specific pentest and tenant isolation from the first milestone.

# Decisions and gaps of the implementation (feature 010)

The design is [ADR-0020](../../docs/adr/ADR-0020-the-scheduler-is-sharded-by-run-and-owned-by-lease-with-a-fence.md); the operation is [`docs/runbooks/scaling.md`](../../docs/runbooks/scaling.md) and [`docs/runbooks/disaster-recovery.md`](../../docs/runbooks/disaster-recovery.md); the measurements are [`tests/performance/reports/scalability-ha.md`](../../tests/performance/reports/scalability-ha.md) and [`tests/performance/reports/disaster-recovery.md`](../../tests/performance/reports/disaster-recovery.md). Numbering continues from feature 012 (decisions D229, gaps G239).

## Decisions

- **D229 — 64 fixed shards by the run's identifier.** The last byte of a UUIDv7 is random, so the shards are even; 64 is the largest set that is one machine word (`ShardSet(u64)`), which makes a set of shards copyable, comparable and sendable as an array of smallints. Per namespace or per tenant would make one busy customer one hot shard; consistent hashing with virtual nodes buys a rebalancing nobody needs at 64 and costs a ring in the database. The number is part of the indexes, so it is fixed for the life of a database and the chart refuses more replicas than shards. A child that ended is reported to its parent, so its shard is the parent's (`run_shard(parent_run_id)`).
- **D230 — Ownership is a lease row with a generation, in the same database, on the database's clock.** The alternatives were advisory locks (owned by a connection: a pooler or a reconnect moves them without a decision, and nothing fences the action), a Kubernetes `Lease` or etcd (a second authority the action's transaction cannot ask), and `SKIP LOCKED` alone (stops two replicas acting twice, not looking twice). The share is `ceil(64 / replicas alive)`; a replica takes the lowest free shards and gives back the highest it holds beyond its share, so replicas that start together contend for the same few and the loser moves on; the keeper runs every `lease / 5`, with the loops' jitter of 20 % (a third, the first choice, left room for one failed round and not for two: the pause comes after the round, which takes time of its own; found by the correctness review), so two failed rounds in a row are survivable. `scheduler_members` is apart from the leases so that a replica that holds nothing yet is counted.
- **D231 — The fence is a `SELECT ... FOR SHARE` of the shard row in the action's own transaction, and it names the owner as well as the generation.** A takeover is an `UPDATE` of the row that skips it while it is locked (`FOR UPDATE SKIP LOCKED`), so it never overtakes a transaction that found the lease good; one that starts after finds the new generation. It does not wait: a node lost mid-action leaves its transaction, and the lock, on the server until the server ends it, so the pools cap how long a transaction may sit idle (60 s) and a takeover that waited would wait that long, for every shard of its call (found by the security review). The owner is the replica's name plus a random suffix chosen at start: a generation that is reused (a restored database, a promoted asynchronous standby that lost the last takeover) can never be mistaken for the one it replaced, and a restarted pod with the same name is not the process it replaces. Tests: `integration shards.rs` (the fence for the current lease and for nothing else, a takeover that waits), `fault failover replicas.rs` (a replica held up past its lease is refused when it goes on; with the fence removed it fires the timer and the test fails, which was tried).
- **D232 — A replica that cannot reach the database stops by itself.** The snapshot of what it holds carries `valid_until` on the replica's monotonic clock, set to the *start* of the round that renewed it plus the lease: the database granted the lease after that instant, so the snapshot never outlives it. `fault failover database.rs`: a replica cut off by a proxy holds nothing after one lease with no call made, and rejoins with new generations when the network returns. What this assumes about the rate of the monotonic clock is G252.
- **D233 — The candidate queries bound their index range with `now()`, not `clock_timestamp()`.** Found while looking at the plan the benchmark prints: `due_at <= clock_timestamp()` is a *filter*, because a volatile function cannot be the bound of an index range, so a pass with nothing due read every waiting step in order; `now()` (the start of the statement, which is when these autocommit queries are asked) is stable and becomes `Index Cond`, so the pass reads the entries that are due and stops. The idle tick of feature 002's report (10 000 waits) did not show it; a million would have. A contract test refuses a comparison with `clock_timestamp()` in the two files of candidate and monitor queries, and the benchmark prints the plan at each size.
- **D234 — Fairness is weighted max-min over the tenants a pass finds, work-conserving, with a bound on the discovery.** If the first page is short everything was taken (one query, the common case). Otherwise pages are read leaving out the tenants that already show their share (at most 16 pages), and the batch is shared: a tenant with less than its share gets all it has, the rest is split by weight, inside a tenant the oldest first, and the chosen candidates are put back in the order they were met. Properties are unit tests (`fairness.rs`: 10), the effect is `integration fairness.rs`, `e2e us04` (with a negative control that fails without fairness), and the benchmark's noisy-neighbour table. Weighted round robin was the other form the spec names; max-min is the same idea without a cursor to store and it does not waste a pass's budget on a tenant that has less.
- **D235 — The candidates of a pass are acted on concurrently** (`buffer_unordered(SAGAT_SCHEDULER_CONCURRENCY)`, default 8, at most 64), each in its own transaction on its own connection. Feature 002 measured about 145 timers per second per loop with one at a time; the benchmark's table shows what 8 and 32 do on this machine.
- **D236 — The outbox dispatcher looks, chooses, then claims by id.** For a replica with a placement: `due_outbox(window)` (read-only, shard first, tenants left out), the same fair selection, then `claim_outbox_ids` with `FOR UPDATE SKIP LOCKED` re-asking `delivered_at IS NULL AND next_attempt_at <= now()`. One owner per shard means no contention in the claim, the messages of a run come out in the order written, and fairness applies to the broker the way it does to the passes. The atomic `claim_outbox` stays for a dispatcher with no placement (tools, tests), where peek-then-claim would make concurrent dispatchers claim fewer than they could.
- **D237 — Observability without a tenant, run or activity on a metric** (ADR-0017 stands). The monitor sets `scheduler_lag_seconds{pass}`; the keeper sets the shards held and the replicas; the passes count the fenced and the held back. A **pool** is a name the operator gives to a set of activities in configuration (`SAGAT_WORKER_POOLS=name=act.a,act.b;...`, at most 32 pools and 512 activities) and the only label of its two gauges; the monitor measures it across tenants with one pass over the ready steps grouped by activity. A tenant-scoped queue API for tenants to scale their own workers was considered and rejected: the autoscaler would need a long-lived credential, which a short-lived token cannot be (G248). A monitor that loses its lease zeroes its gauges, because a gauge keeps its last value for as long as the process lives and two replicas would export two answers to one question.
- **D238 — The chart is validated first by rendering it, with a separate live policy verifier.** `helm template` in a contract test reads the objects back: the engine's configuration is parsed by the engine's own `EngineConfig::from_lookup`, every variable it sets is in the help of the binary that reads it, every pod is hardened like the compose file's, every autoscaler query names only metrics the code emits, and unsafe values are refused at render time. The feature-009 completion adds required role-specific ingress and dependency-scoped egress. `tests/security/sandbox/kubernetes-network-policy.sh` applies those policies and service accounts to kind/Cilium, validates derived PodSpecs under restricted admission, and checks controlled allowed and denied TCP/DNS paths. It still does not run migrations, create secrets, install the full product or exercise KEDA.
- **D239 — No leader election outside the database.** See D230. The one singleton that remains (the monitor, the projector) keeps its `engine_leases` row, as before.
- **D240 — The harness makes its populations through the platform's own services, never by writing rows,** and distinguishes the three axes the spec names (capacity to wait, throughput of transitions, latency under backlog). The quota of active runs per namespace (10 000 by default) is raised the way an operator would: a ceiling (`control-plane quota-ceiling`) and the tenant's limit. The report carries, with every figure, the hardware, the load average, the build profile and the configuration of the database, because the figures mean nothing without them.
- **D241 — Disaster recovery is drilled with real clusters, and RPO and RTO are not published.** `infra/dr/drill.sh` starts the clusters, takes a base backup of a database in use, names a restore point, destroys the schema, restores to the point, compares a digest of the journal and of the audit trail before and after, and replays every run against its projections; and it kills a primary with `kill -9` under a workload that records every run the platform acknowledged, promotes the standby, and counts the acknowledged runs that are missing (none allowed with a synchronous standby). What it measures is that procedure on that machine.
  **Superseded 2026-10-16 (owner decision):** for the reference topology (the Helm chart with PostgreSQL and a synchronous standby) the platform publishes objectives: RPO 0 for acknowledged work, failover RTO at most 5 minutes (promotion plus shard takeover) and point-in-time restore RTO at most 1 hour. The drill fails above them (`infra/dr/drill.sh`, configurable objectives) and the `release` workflow runs it before publishing; measured on one runner, not on a real cluster. An asynchronous standby documents its own RPO as the replication lag it measures.
- **D242 — Tests can use a `nats-server` process instead of a container** (`SAGAT_TEST_NATS_BIN`), with its own port and store per test, killed with it. It is the same server and the same flags; it exists so that a machine without a container engine can run the tests that need a broker, as `SAGAT_TEST_DATABASE_URL` lets it run the ones that need PostgreSQL. CI keeps the containers.
- **D243 — Old and new engines can run together.** An engine of the previous version works on every shard, with no fence; the new ones work on their shards with it. The result is the same because every action is applied under the run's lock and re-checked by the domain: it is redundant, not wrong (`fault scalability-ha`: four placed schedulers and two unplaced ones fire 200 timers once each). The old indexes stay, so the old engines keep their plans.
- **D244 — Fairness can be turned off for measuring** (`SAGAT_SCHEDULER_FAIRNESS=false`), which takes the oldest candidates of the owned shards, as before the feature. It exists so the benchmark and the end-to-end test can show what fairness changes; it is documented as a diagnostic.
- **D245 — Weights are 1 to 16, per tenant, set by the platform operator and audited** (`control-plane scheduling-weight`, action `quota.changed`, resource `scheduling-weight`, in one transaction with the change). There is no API for a tenant to set its own: a weight is a claim on a shared resource, like a quota ceiling, and is granted, not taken.
- **D246 — A tenant is left out of a page with `tenant_id <> ALL($3)`, a residual filter, not an index condition, and so the exclusion is bounded in pages and not in entries.** The index is shard first, then time, so the rows of a tenant that is left out are *read and discarded*, not skipped: a search that finds nobody has read the whole due backlog of the tenants it left out (and the heap row of each, because `tenant_id` is not in the index). The list of tenants left out is capped at 256 and the pages at 16; the cost in entries is bounded by D249, which rests the search, and not by the query (found by both reviews). A tenant-first index would answer the exclusion exactly and would not serve the shard-first scan the pass needs.

- **D247 — The quota of active runs is read from counters the database keeps** (`run_active_counts`, sixteen slots per namespace, kept by triggers in the transaction of the change, `SECURITY DEFINER`, readable and not writable by the runtime role). Found by the benchmark: a start counted the runs that had not finished (`SELECT count(*) ... finished_at IS NULL`, an index entry per active run) under the lock that serialises the starts of a namespace, so the hundred-thousandth wait cost a hundred times what the thousandth did, at about 125 starts per second and falling when the run was stopped at 100 000 runs; a million could not be made. The lock stays (the quota is still exact when starts race for the last places: `integration counts.rs`), the counters are always the count (`counts.rs`: through starts, cancels, deadlines and completions, and under the runtime role), and a counter never goes below zero.
- **D248 — Taking a shard skips a locked row, releasing one does too, and the pools cap idle transactions** (`idle_in_transaction_session_timeout`, 60 s; zero for the migration pool). A takeover is one statement over the shards the replica wants; one shard held by a transaction that was cut off must not keep the free ones from being taken. Giving a shard back is an optimisation and never waits.
- **D249 — A pass rests its search for other tenants after a search that found nobody new, for `SAGAT_SCHEDULER_DISCOVERY_REST_MS` (100 ms; it was 2 s in the first version, and a benchmark showed a tenant behind a burst waiting out the whole drain: the rest is proportional to what the search costs and a floor of seconds is a latency the search never earned) or ten times what the search took, whichever is longer (at most 60 s)**, and so does the outbox dispatcher. See ADR-0020, decision 10. During the rest a pass shares the first page of the oldest candidates, which for one tenant is what it did before; a tenant that arrives behind a burst waits for the rest to end. A search that found somebody is rested only when it was costly (D257). The first version rested after any search whose last page was empty and so starved the tenant it had just found; the benchmark found it, and `a_discovery_that_finds_nobody_says_so_and_a_rested_one_reads_one_page` and `a_search_that_found_nobody_rests_and_a_tenant_behind_the_burst_is_found_when_it_is_over` hold it.
- **D250 — A pool's queue counts what a worker could take:** the claim's conditions (a run that is not paused, not being stopped, a compensation not behind an open breaker), an activity named twice in a pool once. Otherwise a tenant that pauses runs pins the pool's scaler at its maximum (security review).
- **D251 — The keeper adopts leases that are its own and its snapshot does not know** (the answer to an `acquire` was lost on its way back), after renewing them so that they last as long as the snapshot says, and publishes the renewed snapshot as soon as the renewal is done. A replica that fails a round sets its gauges from what it can act on, not from its last good round; a monitor that cannot take its lease sets its gauges to zero (correctness review).
- **D252 — No arithmetic with an infinite timestamp.** A shard never held has the epoch for `expires_at`, and the remaining time of a lease is computed only for a lease still good: before PostgreSQL 17 `timestamptz - timestamptz` raises on an infinite operand, which the CI's PostgreSQL 16 would have met on the first keeper round and a local PostgreSQL 18 hid (correctness review). The migration also refuses to go on if an index it would skip with `IF NOT EXISTS` is invalid.
- **D253 — The scheduler uses no more concurrency than the pool carries less two** (the keeper and the claim's own use), and says so when it clamps.
- **D254 — The control plane's probes are the API's own** (`/v1/health` to live, `/v1/ready` to ready, on the API port); `/livez` and `/readyz` are the engine's, on its admin port. The chart had them the other way round and its control-plane pods would not have started: found by the security review (a chart that was never installed hides this), now held by `every_probe_of_the_chart_asks_for_a_path_its_process_serves`.
- **D255 — The counters' trigger function cannot be hijacked.** `SECURITY DEFINER` runs with the owner's rights, and the search path `pg_catalog, public` left `pg_temp` out, which PostgreSQL then searches first for relations: a role that made a temporary table named `run_active_counts` in the session that fired the trigger would have the owner write to it (and, with `EXECUTE` granted to PUBLIC, could attach the function to a table of its own and move any tenant's counters). The path now names `pg_temp` last, every name is qualified, `EXECUTE` is revoked from PUBLIC, and a test makes both attempts as the runtime role. (Security review, high.)
- **D256 — The renewal of the leases skips a locked row, and the keeper runs every `lease / 5`.** A renewal that waited for a row held `FOR SHARE` by the orphan of a cut-off connection held the rows it had already renewed (stalling their fences) and then failed all of them at the statement timeout; it now skips the row, the keeper adopts a lease of its own that its snapshot did not know in the same round, and `lost` counts only what the replica cannot act on afterwards. (Correctness review.)
- **D257 — A search that fails shares what was read and is rested; a search that found somebody is rested when it was costly.** The first version let a timed-out second page fail the whole selection: the pass took nothing, set no rest, and the burst never drained. `rest_after` is the one rule (ADR-0020, decision 10). (Correctness review.)
- **D258 — The remainder of a weighted share goes to the largest fractions,** not to the heaviest weight: with thirteen tenants of weight 16 and one of weight 1 sharing 200, the light tenant is owed 0.96 and was given 0 at every pass. (Correctness review.)
- **D259 — Smaller findings of the two reviews, all fixed:** a view of the leases per pass (a tick longer than the snapshot's validity made every later action `fenced`); a lease cannot be `infinity` (a `CHECK`, and the keeper no longer panics on a time it cannot take as a duration); `/livez` includes the keeper's rounds; a sample that fails zeroes the gauges the autoscalers read; the outbox backlog is counted by the monitor and not by every dispatcher at every round; `SAGAT_SCHEDULER_BATCH` and `SAGAT_OUTBOX_BATCH` are at most 5000; the chart refuses what the binaries refuse at start (secrets without a protected hop, a pool name Kubernetes would refuse, more pools or activities than the engine takes, a batch or a concurrency out of bounds) and an HPA scales up as slowly as KEDA.
- **D260 — The floor of the search's rest is 100 ms, not 2 s.** The noisy-neighbour scenario showed that a tenant the first page already showed (so "nobody new" was found) was served once and then waited out a rest of two seconds, which was longer than the whole drain of 10 000 timers: the quiet tenant's median was three times the equal-weights figure it should have been, and a weight of 4 looked worse than a weight of 1. A search that costs 10 ms does not earn two seconds of rest; ten times its cost does the work (a tenth of the pass at most), with 100 ms as the floor. The scenario also gave B's timers an order that depended on where vacuum had left free space, so they are now given due times in the order the scenario says.

## Gaps and limits

- **G239 — The share is by count, not by load.** `ceil(64 / replicas)` shards each; a replica that is slow, or whose shards are the busy ones, is not relieved. Nothing moves a shard because of load.
- **G240 — The indexes of feature 002 stay, and the eleven new ones are extra write amplification** on every step and run update (the report's bytes per run show it). Dropping the old ones is a decision for a benchmark with the old engines gone. On a large database the new indexes should be built `CONCURRENTLY` before the migration (`data-model.md`).
- **G241 — The journal is not partitioned or archived.** `run_events` grows with the runs and the transitions; nothing detaches old partitions or ships them. The report gives the cost of a run and of a transition so the growth can be sized; the plan from the spec ("Evaluate another journal backend only via ADR/benchmarks") is not exercised, and no benchmark here suggests it is needed at the sizes measured.
- **G242 — No read replicas.** Every read and write goes to the primary. Reads that tolerate lag (the Studio's lists, the alert list, the telemetry projection) could go to a standby; nothing routes them.
- **G243 — Only the scheduler's passes and the outbox are divided by shard.** The event dispatcher, the delivery worker, the telemetry projector, the connectors and the monitor are loops of features 004, 008 and 005 that coordinate by `SKIP LOCKED` or a lease row, as they did; "hot partitions by correlation" (many events for one key) is a property of one run, which is one shard's work (G254).
- **G244 — Fairness finds at most 16 saturating tenants per pass** (`ROUNDS`). If more than 16 tenants each have more than their share due, the others are found as those drain; `scheduler_fairness_exhausted_total` counts the passes in which it happened. It is a bound on the cost of a pass, not on the wait of a tenant, which is the number of passes the saturating tenants need.
- **G245 — Resolution in completion hardening: exact per-activity concurrency quota.** A namespace may override the maximum number of unexpired `LEASED`/`RUNNING` steps for one activity. Concurrent claim transactions serialize on the tenant/namespace/activity, count under that lock, and either lease in the same transaction or leave the step ready; a full activity does not prevent the bounded candidate scan serving another activity. Forward, compensation and reconciliation tasks count against the activity name they advertise, so different provider queues have separate limits and identical names share one. Missing settings preserve the generic namespace/tenant limit and its backward-compatible unlimited default. The administration path is tenant-bound, ceiling-checked and audited; the refusal metric has only the fixed `activity_concurrency` label.
- **G246 — The worker claim path is unchanged:** per-activity oldest-first candidates, one transaction per run under `SKIP LOCKED`. The report shows how its throughput and latency behave as the workers and the API replicas grow, and where it stops; a sharded claim (candidates by shard, a worker starting at a shard of its own) would spread the contention and relax the strict order, and was not built without evidence that it is the limit.
- **G247 — Resolved for T010-038: full product deployment and real KEDA response.** A disposable one-node kind 1.37 cluster with Cilium 1.20.2 and KEDA 2.18.1 installed PostgreSQL, migrations, the development OIDC provider, the real Helm control plane and engine, Prometheus and Python SDK workers under restricted admission and NetworkPolicies. Sixty authenticated workflow runs produced a measured peak of 56 ready steps; KEDA scaled the worker Deployment 1 → 3, all 60 succeeded, both external metrics returned to zero and the Deployment returned to 1. An undeclared pod was denied and a deleted engine pod was replaced. Exact artifacts and commands are in `tests/performance/reports/kubernetes-validation.md`. The single-node run does not prove node drain, cross-node rescheduling or disruption-budget/surge behavior; those remain a separate multi-node disruption test.
- **G248 — A pool is operator-named and counts across tenants.** A tenant cannot see or scale on its own queue by the platform's help; the monitor's pool measurement is one scan of the ready steps grouped by activity every round (cheap while the backlog is, linear in it when it is not).
- **G249 — The benchmark is one machine and one day.** PostgreSQL and the services share it and so does other work (the load average is in each section); there is no network between them and no high availability of the database; 5 000 transitions per second is reported as reached or not reached on that machine, and what a cluster would do is not claimed. Larger populations than a million are not tried.
- **G250 — The drill is PostgreSQL, on one machine.** It does not cover the object store, the broker, the key ring's escrow, a standby in another zone, the time to fetch a base backup from remote storage, or the engines reconnecting through a virtual address, a pooler or DNS (the chaos suite kills every connection and cuts one replica off, which is the part the platform controls).
- **G251 — The object store's replication and backup are not covered** (script artifacts, payloads over the inline limit); the runbook says so.
- **G252 — Clock assumptions.** Times are the database's. The one local timer, `valid_until`, is on a monotonic clock and assumes it runs at the rate of the database's clock within the margin the keeper leaves (the snapshot is dropped at the start of the round plus the lease, while the database lets another replica take the shard at the *end* of the lease granted after the start). Skew in the *rate*, not the offset, is not simulated.
- **G253 — Edge cases of the specification not exercised:** a full disk (the database turns read-only; the platform's reaction was not tried), a slow NATS consumer (the platform sees its own publishing, not the consumers' lag), and backpressure of an external provider (feature 009's compensation breaker exists and is not part of these tests).
- **G254 — A single huge run is one shard's work.** A run with many thousands of parallel branches or events concentrates on the shard of its identifier; sharding by run spreads runs, not the inside of one.
- **G255 — The rolling upgrade is tested with placed and unplaced schedulers in one process,** not with a binary of the previous release against one of this.
- **G256 — The structural claim of US02 is a test at 1 500 waits; 100 000 and 1 000 000 are benchmark results,** produced on purpose and recorded in the report, not checked on every change.
- **G257 — No view of the shards or the lag in the API or the Studio:** shard ownership and the scheduler's lag are metrics and SQL (`docs/runbooks/scaling.md`).
- **G258 — Reviews.** Two rounds of two independent read-only reviews (security and correctness): the results and what each finding became are in `quickstart.md`; the findings are D246, D248, D250-D252 (first round) and D254-D259, G265-G269 (second).
- **G259 — The runtime role can rewrite the lease tables** (`UPDATE` on `scheduler_shards`, full DML on `scheduler_members`), and the control plane, which faces the network, connects as that role. A process that held its credentials could park shards for ever or shrink everyone's share. The values the keeper cannot read are now refused by a `CHECK` (no `infinity`), and no path to rewrite them was found; the same process can already do more elsewhere; narrowing it needs a role for the engine apart from the one for the API, or transition functions that allow only `generation + 1` on a takeover.
- **G260 — `control-plane scheduling-weight` writes `tenant_scheduling`, which the runtime role cannot, so it needs the owner role like `quota-ceiling` does,** and the audit record names the generic operator and not the previous weight. The chart's Secret holds the runtime role, so the command is run from an operator's machine, not from a pod.
- **G261 — A start still serialises per namespace.** The counters made the quota check cheap; the advisory lock that makes it exact is still taken for the namespace and for the tenant, so starts of one namespace go one at a time through the check (about what a commit takes). The report's starts per second is that limit.
- **G262 — The outbox claim is not fenced:** a dispatcher that loses a shard between choosing and claiming still claims what it chose. It publishes at least once, as always; it can publish a message twice or out of order. Hints are idempotent.
- **G263 — The keeper uses the engine's pool,** so a pool saturated by the worker API can starve the renewal (the leases are then lost and the shards go to a replica that can use them, which is safe and is also a cascade); a connection of its own was not made.
- **G264 — The fairness search of a burst still costs one read of the backlog of the tenants left out per rest** (D246, D249), bounded to about a tenth of the pass's time by the adaptive rest, and a tenant behind a burst waits up to a rest (2 s or ten times the search) to be found; a tenant-first index (or the skip scan of PostgreSQL 18) would remove it and was not built.
- **G265 — A pool's gauges count the ready steps of every tenant whose activity has the pool's name,** whether or not that tenant has a worker that could take them (found by the security review). A tenant can start runs of its own workflows with an activity name a pool serves and, with no worker, keep `pool_ready_steps` and `pool_queue_lag_seconds` high; the pool's autoscaler then sits at its `maxReplicaCount` and `SagatPoolBacklog` fires for good. The ceiling is what bounds the cost (the operator chose `maxReplicaCount`); the metric carries no tenant (ADR-0017), so it cannot say whose steps they are. Pools fit workers the operator runs for tenants it trusts; a tenant that must not be able to move the scaler is given its own install, or a pool name its activities do not use. Counting only the steps of tenants with a binding (worker_bindings are patterns, a tenant administrator writes them) or capping a tenant's share were considered and not built: the first does not stop a tenant that binds, the second stops a legitimate large tenant from scaling the pool.
- **G266 — Resolved: the chart originally emitted ingress-only NetworkPolicy.** Chart 0.4.0 requires explicit dependency peers and emits separate egress policies: control plane to DNS/PostgreSQL/OIDC, engine additionally to configured NATS, and worker pools to DNS plus release-scoped control-plane/engine pods; deployment-specific collectors and other dependencies use role-specific extra rules. Empty peers, zero-prefix CIDRs and unsafe ports are refused at render time. `contract_scalability_ha` reads the rendered rules back and the kind/Cilium verifier exercises allowed and denied paths. Kubernetes NetworkPolicy cannot select an external dependency by hostname/SNI, so operators still own accurate CIDRs/selectors; the live verifier is not a full product install (G247).
- **G267 — The engine's autoscaler follows a signal a tenant can raise** (`scheduler_lag_seconds` rises when many timers fall due together). The ceiling is `maxReplicaCount` (never more than 64), each replica adds `database.maxConnections` connections, and the chart now refuses to render when the control plane plus the autoscaler's ceiling, times that, exceed `database.serverMaxConnections` (when the operator sets it). A pooler in front of the server removes the bound; the chart does not install one.

Merging the two branches in SQL, ordered by time, would make the page what one query over both would return.
- **G269 — Resolved: every critical engine task is supervised.** `apps/execution-engine/src/supervision.rs` owns the scheduler, shard keeper, housekeeping, event, telemetry, monitor, optional connector/delivery/outbox tasks, and the admin and worker-gRPC servers. An unexpected success, error, panic or cancellation marks the process unhealthy, stops the siblings and returns a runtime error (exit 1); an intentional shutdown drains for at most 30 seconds before aborting a stuck task. The focused tests cover unexpected return, panic, sibling shutdown, clean shutdown and the bounded drain. Agent-run verification after the implementation reported all 32 `sagat-execution-engine` tests and package Clippy passing; that result is implementation-session evidence, not the historical CI run cited below.
- **G270 — The transitions figure is the harness's ceiling, not the platform's.** The load generator, up to eight API replicas and 128 worker tasks run in one process on eight threads, on the machine that runs PostgreSQL, at a load of 12 from other work; the share of the database's active backends waiting for the client's next statement (34 to 57%) says the database was not the limit. 5 000 transitions per second was not reached and was not tried under conditions that could reach it. A figure for the platform needs the workers and the database on separate machines.

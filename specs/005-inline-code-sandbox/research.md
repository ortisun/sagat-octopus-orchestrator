# Research & Decisions: Script registry, code editor and inline execution

## Main decision

ScriptRegistry controls src/digest and the build pipeline; worker supervisor manages isolated pools. Inline Go/C#/Java are compiled automatically into artifacts and executed outside privileged processes.

## Rationale

Allow writing and publishing code directly on the platform without manual application build/deploy. The decision respects the recovery, auditability, security and versioning properties defined in the Constitution.

## Alternatives considered

1. **Generic ad hoc queue-based solution:** rejected as the sole durability mechanism, since message delivery is not equivalent to a transaction over workflow state.
2. **Independent services per feature from day 1:** postponed to avoid operational and consistency complexity without a benchmark.
3. **SDK-specific logic:** rejected for core invariants, to avoid behavior differences between languages.

## Risks and mitigation

- Complexity/scope risk: deliver P1 user stories separately, running contract tests.
- Semantic ambiguity risk: encode reducers and golden fixtures, do not decide via UI alone.
- Crash/redelivery risk: test harness with real failures at checkpoints.
- Security risk: specific pentest and tenant isolation from the first milestone.

## Questions for spike validation

- Latency and overhead benchmarks on the critical path defined for this feature.
- Detail compliance and retention requirements according to the deployment environment.

## Decisions taken in this feature

- **D95 — A container per build and per run is the sandbox, and the runtime under it is the engine's to choose.** ADR-0013. No network (`none`), a read-only root, a size-limited `/tmp` mounted `noexec,nosuid,nodev`, every capability dropped, `no-new-privileges`, the default seccomp profile, user 65534, a private PID and IPC namespace, memory with swap off, a CPU quota and a CPU-time limit, a limit on processes, on file size and on open files, no core dumps, no log driver, nothing mounted, a label for the sweeper. A spike against real containers proved each: the cloud metadata address and the engine's address are unreachable with an immediate error (not a timeout), the capability, no-new-privileges and seccomp lines of `/proc/self/status` are what is claimed, a memory bomb is killed by the kernel and read back as such, a fork bomb stops at the process limit and takes nothing else with it, a CPU burner is stopped at the wall clock, a log flood is cut and the script stopped, the scratch area is bounded and cannot execute.
- **D96 — The code travels on standard input, the result on one line of standard output, the log on standard error, and every request to the outside is the supervisor's decision.** The archive upload of the engine API is refused for a read-only root, and a writable root is a disk the script can fill. The shim writes the files to the scratch area, imports them, and speaks JSON lines: `ready`, `fetch`, `secret`, `result`, `error` (and `built`, `rejected` for a build). Lines are bounded (240 KiB and framing), the log is bounded and the script stopped when it floods it, a script may ask its supervisor 100 times per run and is refused past that, and what it was refused is noted once each.
- **D97 — The control plane never touches the container engine; a runner does, and the runner never touches the database.** A new role, `runner` (`worker:execute`, `script:build`, `script:execute`), and a REST surface under `/script-runner/…` for builds, test runs, artifacts, the egress policy of a namespace, the script activities waiting for a runner, and the record of an execution. The runner serves script steps as a worker of the platform's own protocol, so a step's lease, heartbeat, retry, timeout and cancellation are the engine's. An ordinary worker holds neither new permission. (G98, G99.)
- **D98 — An artifact is a canonical JSON bundle that carries the policy and the schemas it was built under, identified by its digest and signed by the control plane.** `{"v":1,"language","policy","inputSchema","outputSchema","entry","files"}`; the signature is Ed25519 over `sagat/script-artifact/v1 ‖ tenant ‖ digest ‖ language`, made with a key only the control plane holds, verified by the runner (with the digest of the bytes) before a container is started, and impossible to move to another tenant or another language. A row planted or edited in the database does not verify, and a trigger refuses to update or delete an artifact at all. (G101, G102.)
- **D99 — A build is the same build only if the source, the lockfile, the toolchain, the policy and the schemas are the same, and the cache belongs to the tenant.** SHA-256 over their length-prefixed parts; a ready version with the key is the cache, so a build that already exists is finished by the claim and never handed to a runner; the toolchain is the engine's image id and the hash of the shims, asked again at every claim.
- **D100 — A version is immutable by construction, and publishing is idempotent against the latest.** A trigger lets only the end of a build through (`BUILDING` → `READY`/`FAILED` with its artifact, key, toolchain, log, never touching what was published); a draft is a compare-and-swap on its revision; publishing takes the script row lock (numbers are assigned one at a time), compares the draft's revision with the one the publisher read (a draft that moved on is a conflict, not a surprise version), and returns the latest version when the content is the same and its build did not fail. A script that has a version cannot be deleted. The database's `script_versions_guard` also refuses a truncate, and a rollback with data present is tested.
- **D101 — A `script` node becomes the activity `script.sha256-<hex>`, and publishing a workflow checks the digest.** The name says what the step runs; it can be named by a worker binding (`script.*`); the schema's `artifactDigest` is now a full digest. Publishing the workflow asks the store for the digests that no ready version of the tenant has built and refuses with `UNKNOWN_SCRIPT` (a typo, a failed build, another tenant's artifact — the answer is the same). `secrets` on a script node are the activity's. (G106.)
- **D102 — The runner advertises what is ready, not what might be.** One indexed range query on the ready steps of a namespace gives the script activities waiting; a session is registered for those no session covers. (G103.)
- **D103 — The script of a workflow receives the step document, and the schemas describe it.** `{run, node, input, steps}`, exactly what any worker of the engine is given, so a script can use the outputs of earlier steps; its declared schemas are validated against that document and not against a sub-field. A test run receives exactly the input it is given, which is the shape to test with.
- **D104 — A test run is the same machinery with less.** The draft as it was, built and run by a runner; it counts against the namespace's `script_jobs` (8 builds and test runs in progress), has no secrets ever, and the network only if the draft's policy and the namespace's egress policy both say so; one no runner takes within two minutes fails as unavailable (when it is read or when the quota is counted, not by a timer). (G104.)
- **D105 — The lockfile of v1 must pin nothing.** It is part of the key, so a script that will one day have dependencies is not rebuilt for nothing, but a lockfile that names a package is refused with the names; there is no silent ignoring and no pretence of supply-chain control. (G97.)
- **D106 — Failures have codes, and the message to the engine never repeats the script's words.** `SCRIPT_ERROR`, `_TIMEOUT`, `_OUT_OF_MEMORY`, `_OUTPUT_LIMIT`, `_DENIED`, `_SCHEMA_VIOLATION` (rule and path, never the value), `_NO_RESULT`, `_SANDBOX_UNAVAILABLE`, `_BUILD_REJECTED`, `_UNTRUSTED_ARTIFACT`; retryable are the error, the timeout and the unavailable. The step's `safe_message` is a fixed sentence per code; the detail is in the execution record, which has a retention and is redacted, because a script's error often contains the data it was handed.
- **D107 — What ran is kept once per attempt and for as long as the script says; what was refused is audited once.** `script_executions` (unique per run, node, attempt), `expires_at` from the script's retention (1 to 365 days, 14 by default), purged by the scheduler; a listing never carries a log (a page is small), one record does. `script.violation` is written once per actor, resource and reason, so a script in a loop cannot grow the trail; the reason is `fetch <scheme>://<host>` or `secret <name>`.
- **D108 — The policy is part of the artifact and cannot be asked past the ceiling.** A request above the platform's ceiling is refused (`ABOVE_CEILING`), not clamped, so nobody believes in a limit they do not have; at run time the artifact's policy is clamped again by the runner's own ceiling (the smaller of each limit, and no network if either says none).
- **D109 — Three permissions for people, two for the runner; two quotas.** `script:read` (Viewer, Operator, Developer), `script:write` (Developer), `script:publish` (Developer); `script:build` and `script:execute` (the runner and the admin). `scripts` (500) and `script_jobs` (8) per namespace, counted under a lock in the transaction that creates the thing counted.
- **D110 — Cold and warm are defined, and measured.** *Start* is from asking for a container to the first instruction of the script; the first run of a language since the runner began is cold, the rest warm (the image is on the machine in both; pulling it is the network's time). `script_start_seconds{language,temperature}`. (`tests/performance/reports/005-inline-code-sandbox.md`.)
- **D111 — A secret is a name in a step and a value in a lease.** The runner takes the secrets of the step with `ResolveSecrets` (so the access list, the publisher's right and the audit of feature 009 apply), hands out only the names the step declared, and searches every value it handed out in the log and the result before either is kept. It is a net, not a wall: a script can encode what it knows. What stops a script from reading a secret it was not given is that it is not in the sandbox.
- **D112 — Cancellation and lease loss stop the container.** The heartbeat of a step is the engine's; when it says "cancel" or the lease is gone, the run's future is dropped and the container is removed by a guard (and by the sweeper if the runner itself dies). A completion the engine refuses as stale is dropped without error.
- **D113 — Schemas are checked where they are written, and inferred where they are seen.** The author's schema is compiled when the script is saved (a bad one, a non-object, one over 64 KiB, or one with a reference outside the document is a `422`, and no schema ever causes a request); `infer` makes a JSON Schema from the input and the result of a run (types, required properties, items merged across an array) for the author's form.
- **D114 — The idempotency key of a step is given to the script.** `octopus.idempotencyKey`, the same on every attempt of the step (`{run}:{node}` unless the activity says otherwise), because a step may run again and the only safe repeat is one the receiver can recognise. (G114.)
- **D115 — The feature ends at the API.** Studio's editor and test panel are feature 007; the contract is `openapi.yaml` (25 operations marked `x-implemented: '005'`), checked by a conformance suite that drives every one of them, normal and error paths.
- **D116 — Two independent reviews (security, correctness) made 35 findings; what was done about each is here.** Every finding was checked against the code before anything was changed; none was refuted; five pairs were the same finding seen twice (S3/C3, S4/C21, S6/C8, S7/C7, S12/C18), so there are 30 distinct ones. Where a test could fail first, it did (the sabotaged supervisor wedged; the old runner got one task for two ready scripts; five guards of the registry were switched off and five tests failed).

# Research & Decisions: Platform foundation and contracts

## Main decision

Rust workspace with domain/application/infra-postgres/api-http/api-grpc, Axum+tonic+SQLx. Protobuf and JSON schema are canonical contracts. RLS as an optional additional defense, never replacing the tenancy filter in the application layer.

## Rationale

Provide a foundation of tenants, namespaces, HTTP/gRPC contracts and a reproducible environment without coupling the domain to infrastructure. The decision respects the recovery, auditability, security and versioning properties defined in the Constitution.

## Alternatives considered

1. **Generic ad hoc queue-based solution:** rejected as the sole durability mechanism, since message delivery is not equivalent to a transaction over workflow state.
2. **Independent services per feature from day 1:** postponed to avoid operational and consistency complexity without a benchmark.
3. **SDK-specific logic:** rejected for core invariants, to avoid behavior differences between languages.

## Risks and mitigation

- Complexity/scope risk: deliver P1 user stories separately, running contract tests.
- Semantic ambiguity risk: encode reducers and golden fixtures, do not decide via UI alone.
- Crash/redelivery risk: test harness with real failures at checkpoints.
- Security risk: specific pentest and tenant isolation from the first milestone.

## Questions for spike validation

- Latency and overhead benchmarks on the critical path defined for this feature.
- Detail compliance and retention requirements according to the deployment environment.

## Decisions taken in this feature

- **D1 — Namespace uniqueness is per tenant, not per workspace.** The OpenAPI header and `schema.sql` (`UNIQUE(tenant_id, slug)`) address a namespace by name alone, so the name must resolve unambiguously inside a tenant. A namespace still belongs to exactly one workspace.
- **D2 — Built-in roles only.** `admin`, `developer`, `operator`, `viewer`, with a fixed permission table in the domain. Custom roles and advanced RBAC belong to feature 009. The permission table is deny-by-default.
- **D3 — One membership per subject per tenant.** A subject holds a single role in a tenant, which keeps authorization deterministic. A subject that must act in two tenants has two memberships, resolved by the tenant claim of the token.
- **D4 — The tenant is never an input.** Every tenant-scoped constructor takes an authenticated `Principal` and inherits its tenant; the domain exposes no constructor that accepts a client-supplied tenant id. A cross-tenant reference is reported to callers as "not found" so tenant existence is not disclosed.
- **D5 — Tenant creation is not a tenant API.** Tenants are provisioned by operators or the development seed (`Tenant::provision`, `Membership::bootstrap_admin`).
- **D6 — Slugs are DNS-label-like** (3–63 characters, `[a-z0-9-]`, start with a letter, end with a letter or digit, no `--`) so they are safe in hostnames, paths and subjects.
- **D7 — Fail closed with the right signal.** When the signing keys cannot be obtained (provider down and cached keys older than `jwks_ttl + jwks_max_stale`) or the database is unavailable, the API answers a retryable `503` with `Retry-After`, never `401` (which would make clients discard valid credentials) and never access.
- **D8 — One answer for every authentication failure.** Unknown tenant, no membership, bad signature, expired, wrong audience and malformed tokens all produce the same `401` body, so a caller cannot probe which tenants or subjects exist.
- **D9 — Cross-tenant access is a `404` plus an audit record.** The record is stored in the *actor's* tenant and carries only the identifier the caller sent and the request's trace id. It is written best effort and **off the response path** (so response time does not reveal that the identifier exists elsewhere), identical events from the same actor are collapsed within a 5-minute window (atomically, with a per-event lock), and at most 64 writes may be pending (further events are dropped and logged). The denial never depends on the audit write.
- **D10 — The JWKS location is configuration, never token content.** `jku`, `x5u` and embedded `jwk` headers are ignored, the fetch is HTTPS-only (relaxable for local development), follows no redirects, is size- and time-bounded, and refreshes are rate limited.
- **D11 — Connection-level protection is part of the server.** `axum::serve` gives hyper no timer, which silently disables its header-read timeout. The server therefore runs its own HTTP/1 loop with a header-read timeout (also reclaiming idle keep-alive connections), a connection cap that applies back-pressure instead of exhausting descriptors, and a bounded shutdown grace.
- **D12 — Expired signing keys are served while refreshing.** Keys past `jwks_ttl` (and inside `jwks_max_stale`) keep verifying while a background refresh runs, so a slow provider never stalls the API. A key the provider withdraws therefore keeps working until `jwks_ttl` plus one refresh. A key set without a single usable key is treated as a provider incident and never replaces a good cache.
- **D13 — The runtime role is provisioned, the grants are migrated.** The role `sagat_app` is created by whoever provisions the database (it carries a password, so it does not belong in a migration; the compose stack does it in `postgres-init/`). The migration grants it its fixed privilege set if the role exists when it runs, so create the role *before* the first migration.
- **D14 — Privileged writes outside the tenant API are audited too.** Provisioning a tenant and granting its first administrator (and any membership added by an operator) write `tenant.provisioned` and `membership.granted` records in the same transaction as the change. The actor is the non-authenticatable subject `system:provisioning`; the operator's own identity is not captured yet (the control plane CLI has none).
- **D15 — Metrics are an operations surface, not part of the API.** They are served on their own listener (`SAGAT_ADMIN_ADDR`, loopback by default, `off` to disable), labels are route templates, status codes and fixed reason names, and a test asserts that no subject, tenant or identifier ever becomes a label.
- **D16 — Fairness is charged to the authenticated tenant only.** Anonymous or forged requests are rejected before any tenant budget is touched, so they can neither exhaust nor be blamed on a tenant; a global in-flight cap bounds what they can cost.
- **D17 — Real tenants are created by an explicit operator command.** `seed-dev` stays gated on `SAGAT_ENV=dev`; `provision-tenant` works everywhere but has no defaults (slug and first administrator are mandatory), reports a duplicate instead of ignoring it, is audited like D14 and never logs the administrator's subject. It must run as the owner role: the runtime role cannot insert tenants.
- **D18 — Metric labels come from closed sets, and the recorder forgets idle series.** The HTTP method label is one of `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS` or `OTHER`, because the server accepts any token as a method and the Prometheus recorder keeps every series it has seen (the review measured 300 methods -> 300 series and 100 KB methods -> 41 MB). As a backstop the recorder drops series idle for 10 minutes; since it only does so while rendering, the control plane renders (and discards) every minute so a process whose `/metrics` listener is off or unscraped stays bounded too. Proven by `tests/fault/platform-foundation/metrics.rs` and `crates/telemetry/tests/metrics.rs`.
- **D19 — Two request budgets, both before the work they protect.** A token bucket per verified subject (key: the token's `sub`; the verifier accepts a single issuer, so `(iss, sub)` adds nothing; default 20 req/s, burst 40) runs right after the JWT verifies and before `authenticate`, which costs two lookups; a non-member or an unknown tenant claim therefore cannot make the database work for free, and one member cannot spend the tenant's whole bucket alone. The per-tenant bucket (100 req/s, burst 200) still runs after authentication. Only a verified token is ever charged. Budgets are validated (finite rate of at least 0.001, finite burst of at least 1; `1e-300` used to panic the first over-budget request), the wait is capped at one hour, the refill clock never moves backwards, the table sweeps at most once per refill window and holds at most 100 000 keys (further keys share one overflow bucket), and the shed `Retry-After` cycles through 3-8 s so refused clients do not return together.
- **D20 — A tenant cannot hold more than its share of the slots.** The authenticated `Caller` owns a permit of a per-tenant concurrency cap (default `max(1, SAGAT_MAX_IN_FLIGHT / 4)`, `SAGAT_MAX_IN_FLIGHT_PER_TENANT`), so the slot lives as long as the handler, including while it reads a slow body; over the cap the request is refused at once with a retryable `429` and counted in `http_tenant_concurrency_rejected_total`. A request-body idle timeout (`SAGAT_BODY_IDLE_TIMEOUT_SECS`, default 5 s) ends a stalled upload with a retryable `408` long before the request timeout. Proven by `limits.rs::stalled_uploads_of_one_tenant_cannot_starve_the_others`.
- **D21 — Readiness is single-flight, bounded and diagnosable.** Concurrent probes that find the 1 s cache stale wait for one ping; the ping gives up after 500 ms (not ready); the reason is logged at `warn` (the store logs the detail, including "schema not migrated") and never returned.
- **D22 — The `system:` subject namespace belongs to the platform.** `Subject::parse` rejects it (case-insensitively, `SubjectViolation::Reserved`), so neither a token `sub` nor `provision-tenant` / `seed-dev` can produce the audit actor `system:provisioning`, which only `Subject::provisioning()` constructs.
- **D23 — The required token type is a media type.** `SAGAT_OIDC_REQUIRED_TYP` is trimmed and compared after normalising both sides (RFC 7515 4.1.9: a `typ` without `/` means `application/` + it), so `at+jwt` and `application/at+jwt` are the same type.
- **D24 — Outside development the process proves its own least privilege.** At start `serve` checks that the connected role is not a superuser, does not own `audit_records` (directly or through a role it belongs to) and holds no UPDATE (any column), DELETE or TRUNCATE on it; otherwise it exits with code 2 before listening, with a message that names the problem and never a credential. A missing `audit_records` is refused too (privileges cannot be established), so staging and production run `migrate` first. `SAGAT_MIGRATE_ON_START` needs the owner role and is therefore accepted only in dev. Role attributes other than those listed (`CREATEROLE`, `REPLICATION`) are not checked, and the check runs once, not periodically.
- **D25 — The unauthenticated metrics port warns when exposed.** Binding `SAGAT_ADMIN_ADDR` to a non-loopback address logs a warning at start; restricting the port (NetworkPolicy, firewall) is the operator's job and is not enforced by the process.

- **D700 — Security fixes younger than two weeks: Rust is time-boxed, npm takes the fix.** Gap and decision numbers 700 onwards were chosen on 2026-10-24 so that they cannot clash with the numbers other branches are adding. The two-week rule for new dependency versions (D138) met six RustSec advisories and seven npm findings whose fixes were published 2 to 18 days earlier. *Rust:* `cargo audit` has a native ignore list, so, as for G271, each advisory is ignored in `.cargo/audit.toml` with a written justification and an expiry that is the fix's release date plus 14 days (G700 to G703); CI stays green and an expired entry is a visible task. *npm:* `npm audit` has no ignore mechanism and the windows (1 to 9 days) are shorter than a review cycle, so a time-box would have to be a custom gate that goes red again within days. The findings are taken now (G704) as a bounded exception: patch releases of lines already in use, exact pins and integrity hashes in `package-lock.json`, installs with `--ignore-scripts` (`frontend/.npmrc`) and the whole Studio gate run on the result. The exception covers only a version that an advisory makes necessary; it does not relax the rule for new packages or for feature upgrades. If the owner prefers the rule without exception, the previous pins are in the git history of `frontend/package.json` and `frontend/package-lock.json`, and the red `studio` job returns until 2026-11-02.

## Release 0.4.0 dependency gate (2026-10-12)

The release CI detected RUSTSEC-2024-0449: `unsafe-libyaml` is unmaintained. The dependency
came through `serde_yaml_ng` in the CLI and contract-test helpers, including YAML manifests supplied
by users. The integrated branch uses the maintained safe-Rust `serde-saphyr` implementation
recommended by the RustSec advisory. Its explicit compatibility options preserve YAML 1.2 booleans,
last-wins duplicate keys, ordinary merge keys and raw binary-tagged strings while disabling source
snippets in diagnostics. The CLI retains its 32 MiB expanded-value guard and single-document rule.
No advisory exception is added; `cargo audit --deny warnings` passes after the replacement. The
manifest tests additionally cover anchors, alias expansion limits, redacted parse failures and path
confinement; the full release CI checks contracts and CLI journeys.

Source: [RustSec advisory](https://github.com/RustSec/advisory-db/blob/main/crates/unsafe-libyaml/RUSTSEC-2024-0449.md).

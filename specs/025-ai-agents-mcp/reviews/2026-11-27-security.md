1. Major — The exposure check trusts the workflow output annotations, so model-written content can reach an MCP caller below the transcript level
   Where: specs/025-ai-agents-mcp/spec.md:222-224, 612-616, 745-747; specs/025-ai-agents-mcp/contracts/mcp-server.md:93-96; specs/001-platform-foundation/contracts/workflow.schema.json:692-695; crates/application/src/classification.rs:412; crates/domain/src/classification.rs:100-117
   What: The floor that keeps model-written values at or above the transcript level applies only to the agent node's own generated output carrier. The exposure checks "every field's effective classification (the workflow outputSchema carrier)" against `maxResultClassification`. The existing publication check refuses a looser annotation only inside one schema ("less strict than its effective parent", verified in code). It does not follow values through `end.outputExpr`. Scenario: an agent's transcript level is `pii`. An `end` node has `outputExpr: steps.triage.output.result.summary`, and the workflow `outputSchema` annotates `summary` as `public`. The exposure is saved with `maxResultClassification: public`. Any holder of `mcp:call` and `run:start` then receives model-written `pii` text. The same applies to a `child` tool whose child workflow wraps an agent and annotates its output `public`.
   Why: This contradicts non-functional requirement 025-004 ("model-written values are never classified below the transcript level") and the claim in user story 05 scenario 5 that "a model cannot relabel what entered its transcript". It creates a remote disclosure path to callers without `pii` rights.
   Correction: Compute the effective level of each workflow output field (and of each child-tool result carrier) as the stricter of its annotation and the level it inherits from the agent output it is drawn from. This is the inherited-level rule `written_level` already used for destinations. Refuse `CLASSIFICATION_LOOSENED` at publication, and use that inherited level in the exposure checks at save time and at call time.

2. Major — The unattended-write refusal is one level deep and rests on an `effect` the author declares
   Where: specs/025-ai-agents-mcp/spec.md:568-574; specs/025-ai-agents-mcp/data-model.md:128-130; specs/025-ai-agents-mcp/contracts/agent-node.schema.json:238-245, 414-437; docs/adr/ADR-0060-mcp-exposes-declared-tools-and-calls-pinned-tools.md:41-48
   What: `agent_unattended_writes` is computed per version and covers only agent `write` tools acknowledged `approval: "none"`. An exposed workflow can bypass it in two ways. It can contain a `child` node, or an agent `child` tool declared `effect: "read"` (which needs no approval), whose child workflow, chosen by its active version when the child starts, contains an agent with an unattended `write` tool or ordinary write activities. A `child` or `mcp` tool can also be declared `read` while it writes, because only `operation` tools have their effect checked against the target. Scenario: an MCP caller puts injected text into the run input and reaches an unattended effect two levels down. The exposure and the call-time check both pass.
   Why: The defence exists so that "a manipulated model must not reach an unattended effect from an anonymous or remote caller" (D1296). As written it does not hold for any workflow that starts children.
   Correction: Make the flag transitive. A version is unattended if it, or any child workflow it can start (child nodes and `child` tools, under their version policy), contains an unattended write. Re-evaluate it at child admission for runs whose root came from MCP or a public link, and refuse there. Refuse `effect: "read"` without approval for `child` tools, and for `mcp` tools whose snapshot annotations do not state read-only. Annotations may only tighten this rule, never loosen it.

3. Major — An approver can approve a tool call whose arguments were all withheld from them
   Where: specs/025-ai-agents-mcp/spec.md:171-173, 499-505; specs/025-ai-agents-mcp/plan.md:221-222, 233-234; specs/025-ai-agents-mcp/contracts/ai-api.openapi.yaml:184-194
   What: Every field of the approval view is at least the transcript level. That level is `pii` whenever a context path or tool result has no carrier, which includes every MCP tool without an `outputSchema`. Fields above the approver's level are withheld, and the reveal grant is held by no role. Scenario: an injected model requests `issue_refund` with an attacker-chosen account and amount. The eligible `operator` sees only withheld nodes and approves. The approval decision endpoint does not require that the decider was able to see the input.
   Why: Human approval is the main control the set offers against prompt injection reaching a sensitive effect. A blind approval gives none of that protection while it records an approval in the audit trail.
   Correction: Make a tool-call approval decidable only by someone who can see every non-`secret` field of the input. Refuse a decision with a typed reason when any field was withheld, and refuse at publication a tool input field annotated `secret`. Alternatively, require the approval policy's eligible audience to hold the rights of the transcript level, checked at publication and at decision time.

4. Major — Revisions chosen at admission are never checked against what publication approved
   Where: specs/025-ai-agents-mcp/contracts/agent-node.schema.json:117-121; specs/025-ai-agents-mcp/spec.md:366-371, 514-525, 633-636; specs/025-ai-agents-mcp/contracts/mcp-client.md:30-31; specs/025-ai-agents-mcp/data-model.md:70; specs/025-ai-agents-mcp/quickstart.md:96
   What: Unless the author fixes a revision, admission pins the provider's current revision. The transcript-level checks against `maxPromptClassification` and `maxArgumentClassification`, the model allowlist and the publisher's `secret:use` on the named secrets are stated only at publication, plus `secret:use` at delivery. Scenario: an administrator finds a provider unsuitable for `internal` data and saves a revision with `maxPromptClassification: public`. Every already-published agent keeps sending `internal` context to it, and the quickstart shows the refusal only on republication. The MCP snapshot pin also contradicts itself: "publication pins the snapshot" versus "the server's current revision and snapshot ... at admission". If admission pins the current snapshot, any refresh silently changes the descriptions and schemas the author reviewed, and the drift check compares against the new snapshot.
   Why: This is egress above a destination's current declared ceiling, and it defeats the review guarantee of ADR-0060 decision 6. It also weakens the claim that the secrets are those "that version pins" (Decision 025-001), because the version pins no revision.
   Correction: Record the snapshot identifier in the published version and copy it at admission. At admission and at every resolution, recheck the transcript level against the pinned revision's ceilings, the model allowlist and the closed input of every pinned tool. Refuse with `CLASSIFICATION_EGRESS_REFUSED` or `AI_CAPABILITY_UNAVAILABLE` before dispatch. Add the "ceiling lowered after publication" case to the quickstart and to Task 025-040.

5. Major — Credential headers are re-sent to the target of a GET redirect
   Where: specs/025-ai-agents-mcp/spec.md:388-393, 544-547; crates/infra-egress/src/lib.rs:251-277
   What: Requirement 025-023 forbids redirects only "for non-GET". The provider probe lists models with a GET that carries `x-api-key`, `api-key`, a bearer header or SigV4 headers. The guard follows GET redirects hop by hop and copies every request header to each hop (verified in code, lines 257-259 inside the loop). It checks only the destination policy. Scenario: an `openai-compatible` gateway, or a compromised or misconfigured endpoint, answers 302 to a host the namespace egress policy allows. The tenant's provider key is sent to that host.
   Why: This is secret exposure to a third party, which Principle V makes release-blocking. Nothing in the set forbids `max_redirects` above zero for the agent runner.
   Correction: Require `max_redirects = 0` for every provider and MCP request, the probe included, and add a runner test that a 302 on the probe is treated as a failure. Alternatively, make the guard drop every credential header on a cross-origin hop and test that.

6. Major — The ordinary `ResolveSecrets` path is not closed for agent-runner leases
   Where: specs/025-ai-agents-mcp/contracts/agent-runner-protocol.md:47-49, 51-69; specs/025-ai-agents-mcp/data-model.md:95-110; crates/application/src/worker/secrets.rs:41-49; crates/application/src/worker/secret_resolution.rs:19-28
   What: The set closes generic `ReadBlob` for managed leases but says nothing about the ordinary secret resolution. That path delivers `node.secrets()` of whatever node the instance materializes, checks only `worker:execute`, the lease, the binding, the pools and the publisher, and does not refuse managed kinds (verified in code). The set frames provider and MCP credentials as "the declared secrets of that task definition". If the derived-node function puts them in the materialized node's `secrets`, the agent-runner token can fetch them through `ResolveSecrets`. That path skips the lease-owner session binding, the initiator's `ai:use`, the per-call reveal-grant recheck, `ai.pii_egress` and the per-slot credential pins.
   Why: Several checks the set claims for every disclosure would be bypassable through an existing call.
   Correction: State that the node materialized for every `sagat.ai.*` kind has an empty `secrets` list. Make ordinary `ResolveSecrets` (and every other secret-bearing worker call) refuse any lease whose node has a managed kind. Add both to Tasks 025-017 and 025-091 with a denial test.

7. Major — Idempotency receipts are keyed by an undefined "caller" and ignore the exposure
   Where: specs/025-ai-agents-mcp/data-model.md:79-80; specs/025-ai-agents-mcp/contracts/mcp-server.md:63, 84-85
   What: The primary key of `mcp_call_receipts` and the binding of task handles use `caller`, which is not defined. The replay rule is "same key and argument digest gives the same run", with no comparison of the exposure. If `caller` is the scoped token's minter, every token of that minter shares receipts. Scenario: token A, scoped to exposure Y, calls with key `order-42`. Token B, scoped only to Z and given to another client, calls Z with the same predictable key and arguments. B is answered with Y's run and its projected result.
   Why: The token scope can be bypassed, and the result of an exposure outside the scope is disclosed.
   Correction: Define `caller` as the credential identity: the scoped token identifier, or the OAuth issuer and subject. Include the exposure identifier in the receipt match, and answer `IDEMPOTENCY_KEY_REUSED` when the exposure differs. Disclose a replayed result only through the replaying call's own exposure revision after its authorization.

8. Major — Model-written and provider-written strings reach surfaces the set says carry no payload
   Where: specs/025-ai-agents-mcp/contracts/model-turn.schema.json:13-14, 22-26; specs/025-ai-agents-mcp/contracts/ai-api.openapi.yaml:368; specs/025-ai-agents-mcp/contracts/agent-stream-events.md:26, 32; specs/025-ai-agents-mcp/plan.md:310-315; specs/025-ai-agents-mcp/spec.md:141-142, 287-288, 535-536
   What: The model chooses the requested tool name (64 characters of `[a-zA-Z0-9_-]`, possibly undeclared) and `providerCallId` (up to 128 characters). The provider supplies `reportedModel`. The set does not say these are dropped for undeclared requests or replaced by fixed values. They flow into `AgentProgress.toolCalls.name` (readable with `run:read`, which the `viewer` role holds), journal events such as `agent.tool_refused`, the stream's `toolName` (`internal`), and span attributes. Scenario: an injected model requests 256 "tools" named after the digits of a customer's tax number, and a viewer reads them from the run graph.
   Why: This is a bounded but real covert channel for `pii`, contrary to Requirement 025-022.
   Correction: Record an undeclared request as the fixed marker `UNKNOWN_TOOL` and its call index, never the requested name. Show only declared tool names in the graph, the journal, the stream and spans. Keep `providerCallId` and `reportedModel` out of `run:read` surfaces, or bound them to a closed pattern and treat them as transcript content.

9. Major — Client secrets and signing keys reach the runner directly, while the same pattern is refused for MCP
   Where: specs/025-ai-agents-mcp/contracts/ai-api.openapi.yaml:248-254; specs/025-ai-agents-mcp/spec.md:44-50, 372-387; specs/025-ai-agents-mcp/research.md:129, 147; docs/owner-decisions.md:168
   What: The modes `azure-entra-client-credentials` and `aws-access-key` deliver an Entra client secret and an AWS secret access key (a long-lived signing key) to the agent runner, which then performs the token exchange or signing itself. MCP `oauth-client-credentials` is refused until design 047's broker exists, and Decision 1306 explains why: a client secret must go only to a recorded token endpoint. The Entra mode records no authority or token endpoint, so the same redirection concern is not addressed. The approved constitution 5.1.0 admits, for an executor of a declared resource, "its settings and its current access token, never a refresh token, client secret or signing key" (docs/owner-decisions.md:168). Providers are exactly such 021 resources. Decision 025-001 nonetheless says a third set was "rejected".
   Why: The Principle V basis for provider credentials is a reading taken under delegation that conflicts with the rule the owner approved for resources. A security finding cannot be accepted under OD-2026-11-25-2.
   Correction: Either refuse `azure-entra-client-credentials` (and decide the same for `aws-access-key` with a role) under the same Gap 025-001 until the broker issues access tokens, or obtain an explicit owner decision that the first set covers 021-resource client secrets and signing keys. In either case, record the Entra authority host in the revision, confirmed by the saving administrator, and send the client secret only there.

# Data model — feature 017

## Secret provider lifecycle

`secrets` remains the namespace/name identity and owns its ACL. Its `authority` is `local` or `openbao`. Active version pointers never refer to a pending provider write.

`secret_versions` has exactly one representation: a non-null local envelope, or a non-null immutable `provider_operation` reference with all envelope columns null. Remote reads derive tenant/namespace/operation from persisted metadata, never a client path. Provider identity and version are distinct from encryption-key identity; remote records have no local key.

`secret_provider_operations` holds UUID identity, tenant/namespace, logical secret identity/name, actor, client request UUID, expected version, 32-byte keyed content binding, state and timestamps. The unique receipt scope is tenant/namespace/actor/request. One pending operation per name fences concurrent management and migration. An operation is prepared and audited in one transaction; OpenBao I/O occurs after commit; activation locks and revalidates current membership, namespace/name identity and expected revision in another transaction. Revocation or a competing edit prevents activation. A replay with different content is a typed conflict. A pending operation without a provider value needs secure resubmission, never background plaintext recovery.

Provider objects not referenced by retained secret versions are garbage after the receipt window. Keep idempotency receipts for 24 hours, then cleanup may remove unreferenced objects and receipts. Pending intents expire after 24 hours with an audited abandonment. The cleanup order is provider deletion first, then metadata deletion; failures leave retryable metadata. A hard bound of 1,024 receipts per namespace prevents unlimited metadata growth during a provider/cleanup outage. The existing secret-count quota and the 32 pending-operation ceiling apply at preparation and activation. Current and four previous logical versions are retained. Remote secret byte length is accounted even though the plaintext is held by OpenBao; it must not become a retained-content quota bypass.

Logical deletion immediately removes resolution/ACL authority and fences pending activation. It does not promise synchronous destruction of provider bytes; retention cleanup performs that bounded, recoverable external action. No remote data can be restored as authoritative merely by replaying a deleted receipt.

## Connection and execution records

Connection identities, immutable revisions, current enabled/tombstoned state and per-run node bindings are separate records. A binding retains a revision while a run can use it; changing the head never retargets a retry. Provider credential version is resolved independently at each permitted attempt. `database_connections` stores tenant/namespace/name identity, current revision and ACTIVE/PAUSED/DELETED authority. `database_connection_revisions` stores configuration JSON, requested status, actor/request UUID and timestamp. A unique tenant/namespace/actor/request receipt binds the exact settings and expected revision. Updates are forbidden by an ALWAYS trigger; a deferred composite FK ensures every head references a committed revision. Identity/name cannot change and tombstones cannot be revived.

`run_database_connections` has one immutable tenant/namespace/run/node → connection/revision binding with tenant-and-namespace composite FKs. Publication validates every connection against the author's current role and secret ACL. Run admission now populates bindings in the run transaction, after acquiring any parent reservation and before commit. Current connection state, OpenBao authority, publisher and initiating actor permissions/ACLs are checked under locks. Triggered trees use their publisher when there is no human initiator; `system:engine` grants no database authority. Receipt replay validates the persisted pins and current authority. A new rerun resolves floating references at its own admission; an explicit revision remains explicit. Settings/names are charged through existing ALWAYS retained-byte triggers. The initial catalog enforces 100 current connections, 1,024 retained identities per namespace and 1,000 revisions per identity; configurable namespace/deployment catalog ceilings and eventual retention cleanup remain delivery work.

Lock order for admission is an existing parent/root run reservation (for children), then namespace secret/catalog lock, current membership rows, namespace, connection heads, secret rows and existing ACL rows. Revision selection, run/pin insertion, initial journal/task/outbox records and receipt commit together. ACL removal and role changes wait for an admission already holding their share locks; subsequent admissions see the revocation. A crash before commit leaves no run or pin. A denied child admission completes the parent step with `DATABASE_UNAVAILABLE`; a denied event/cron admission creates no run and records a bounded `database.denied` audit. Dedicated managed leases/capability use remain pending T017-013.

A catalog write takes the existing namespace secret-management lock, checks the current membership and OpenBao authority, then commits revision/head/audit together. Creates and rotations cannot race the count or head. Historical reads show historical settings with current lifecycle status. Catalog HTTP routes are metadata operations only; no route executes SQL or claims a successful probe.

Implementation status: the intent/version schema, immutable content-binding guard, byte-accounting trigger, explicit migration fence and provider-aware resolution have real-service evidence. Scheduled provider-object/receipt cleanup is still pending T017-024; current hard bounds fail closed when full. Explicit OpenBao settings now enable management routes and runtime resolution; production deployment profiles and the database connection feature remain incomplete.

# Data model — feature 029

Proposed, not implemented. All tables are created by one additive migration whose timestamp is allocated at
implementation time (after `20261220000000`). Feature 029 creates no capability tables: it uses feature
018's instance-capability registry (below), which must be deployed fleet-wide in a release before narrowing
is enabled (FR-029-037, T029-003, 018 G1607). Every table carries `tenant_id`; every reference is a composite foreign key
that includes it, following `20261008000000_identity.up.sql`. Identifiers are UUIDv7 generated by the
application. Names are slugs `^[a-z][a-z0-9-]{1,61}[a-z0-9]$` without `--`. No existing table gains a
column, so no existing trigger (for example 017's `sagat_database_identity_immutable`) or row lock changes.

## Permission catalog (code, not a table)

`crates/domain/src/access.rs` classifies permissions with a `match` whose explicit arms give each known
permission its assignability, meaningful scopes, and for item permissions the kinds and whether it is a
**level** or **sensitive** permission; its compile-time default arm yields `reserved` (unclassified), so a
permission added by another feature compiles and stays reserved until classified, and a contract test lists
the unclassified ones. Counts are derived (53 permissions with this feature: 43 assignable, 10 reserved; 13 level, 11
sensitive; `quota:manage`, `egress:manage`, `audit:read` marked administrator-equivalent, `audit:read` also
"sees past restriction"). The combined catalog will grow with the permissions other drafts add. The REST catalog endpoint and the
Studio read the same table; a contract test compares it with
[contracts/permission-catalog.json](./contracts/permission-catalog.json).

## Tables

### `custom_roles` and `custom_role_revisions`

| Column | Type | Rule |
|---|---|---|
| `tenant_id`, `id` | uuid | PK `(tenant_id, id)` |
| `owner_namespace_id` | uuid null | null = tenant role; else FK `(tenant_id, owner_namespace_id)` → `namespaces` |
| `name` | text | slug; unique per owner: partial unique `(tenant_id, name) WHERE owner_namespace_id IS NULL` and `(tenant_id, owner_namespace_id, name) WHERE owner_namespace_id IS NOT NULL` |
| `description` | text null | ≤ 512 UTF-8 bytes; `content` class |
| `current_revision` | integer | ≥ 1; CAS token of edits |
| `created_by`, `created_at`, `updated_at` | text, timestamptz | subject bounded like `memberships.subject` |

`custom_role_revisions (tenant_id, role_id, revision, permissions text[], actor, created_at)`, PK
`(tenant_id, role_id, revision)`, FK to the role `ON DELETE CASCADE`; `permissions` is the sorted, unique set
of catalog names, cardinality from 1 to the number of assignable permissions (43 today; derived, application check against the catalog plus a `CHECK` on the name
grammar). An `ALWAYS` trigger rejects `UPDATE`. A deferred constraint ensures `current_revision` names a
committed revision (as `database_connections` does). At most 1,000 revisions per role and 20 namespace roles
per namespace (hard 100). Deleting a role (only without assignments) removes its revisions; the audit trail
keeps each revision's permission list in its server-built reason.

### `role_assignments`

`(tenant_id, id, role_id, principal_kind, subject, group_id, scope_namespace_id, granted_by, granted_at)`:
`principal_kind ∈ {subject, group}` with exactly one of `subject`/`group_id` (`CHECK`); `subject` FK →
`memberships ON DELETE CASCADE`; `group_id` FK → `access_groups ON DELETE RESTRICT`; `role_id` FK →
`custom_roles ON DELETE RESTRICT`; `scope_namespace_id` null = tenant scope, else FK → `namespaces`. Unique per
(role, principal, scope) through partial unique indexes. An `ALWAYS` trigger enforces that a namespace role
is assigned only in `owner_namespace_id` and that `subject` holds a human built-in role. Insert/delete only.
The human set is fixed (`admin`, `developer`, `operator`, `viewer`); built-in roles are additive, and any role
another feature adds (021 `integration-runner`, 025 `agent-runner`, …) counts as a machine role, so the
trigger refuses it without change.
Indexes `(tenant_id, subject)`, `(tenant_id, group_id)`, `(tenant_id, scope_namespace_id)`,
`(tenant_id, role_id)`.

### `access_groups` and `access_group_members`

`access_groups (tenant_id, id, name, description, created_by, created_at, updated_at)`, `UNIQUE (tenant_id,
name)`. Local groups only: a future source feature adds its own columns additively (contracts/group-source.md).

`access_group_members (tenant_id, group_id, subject, added_by, added_at)`, PK `(tenant_id, group_id,
subject)`; FK to the group `ON DELETE CASCADE`; FK → `memberships ON DELETE CASCADE`; trigger: human role.
Index `(tenant_id, subject)`. A group may be named by at most 128 folder entries and operation-list
principals together (hard 256), which bounds the checks and widening audits of a member addition.

### `folders` and `folder_entries`

`folders (tenant_id, namespace_id, id, name, display_name, description, mode, revision, created_by,
created_at, updated_at)`, PK `(tenant_id, namespace_id, id)`, `UNIQUE (tenant_id, namespace_id, name)`, FK →
`namespaces`; `mode ∈ {open, restricted}` default `open`; `revision` increments on every rename, mode change,
entry change and placement in or out (the preview/apply CAS); `display_name` ≤ 128 bytes and `description`
≤ 512 bytes, both `content`.

`folder_entries (tenant_id, namespace_id, folder_id, principal_kind, subject, group_id, level, granted_by,
granted_at)`: FK to the folder `ON DELETE CASCADE`; subject → `memberships ON DELETE CASCADE` (human-role
trigger); group → `access_groups ON DELETE RESTRICT`; `level ∈ {viewer, runner, editor, owner}`; one entry per
(folder, principal) by partial unique indexes; setting a level replaces it in one transaction. ≤ 256 per
folder.

### `item_placements`

`(tenant_id, namespace_id, item_kind, workflow_id, script_id, connection_id, folder_id, placed_by,
placed_at)`:

- `item_kind ∈ {workflow, script, connection}` and exactly the matching id column non-null (`CHECK`).
- FKs `(tenant_id, namespace_id, workflow_id)` → `workflows (tenant_id, namespace_id, id)` (constraint
  `workflows_tenant_namespace_id_uniq` exists), `(tenant_id, namespace_id, script_id)` → `scripts`
  (additive `UNIQUE (tenant_id, namespace_id, id)` on `scripts`), `(tenant_id, namespace_id, connection_id)`
  → `database_connections` (unique exists); all `ON DELETE CASCADE` (scripts are hard-deleted; connections
  are tombstoned and keep their row).
- FK `(tenant_id, namespace_id, folder_id)` → `folders ON DELETE RESTRICT`.
- Unique per item: partial unique indexes on `(tenant_id, workflow_id)`, `(tenant_id, script_id)`,
  `(tenant_id, connection_id)`; index `(tenant_id, namespace_id, folder_id)` for filtered listings.
- A trigger refuses a placement of a private 017 definition (`workflows.internal`).
- A folder is **empty** when no placement references a live item (a workflow, a script, or a connection
  whose status is not `DELETED`); deleting an empty folder first deletes the placements of tombstoned
  connections.

A run's folder is derived through `runs.workflow_id` at read time; runs carry no folder (D1451).

### `operation_lists` and `operation_list_principals`

`operation_lists (tenant_id, namespace_id, workflow_id, kind, operation_name, revision, created_by,
created_at)`, PK `(tenant_id, workflow_id, kind, operation_name)`, FK `(tenant_id, namespace_id,
workflow_id)` → `workflows`; `kind ∈ {query, update}`; `operation_name` matches
`^[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$`; at most 64 per workflow.

`operation_list_principals (tenant_id, workflow_id, kind, operation_name, principal_kind, subject, group_id,
granted_by, granted_at)`, FK to the list `ON DELETE CASCADE`, subject → memberships `ON DELETE CASCADE`,
group → `access_groups ON DELETE RESTRICT`; ≤ 128 per list. An empty list means "nobody"; removing the list
restores ADR-0031 behaviour.

### Instance-capability registry (owned by feature 018; cited, not redefined)

029 uses the deployment-level registry defined in `specs/018-schedules-bulk-operations/data-model.md`
("Instance-capability registry", T018-080, D1034): `serving_instances` (one row per control-plane and
execution-engine process, `kind`, `capabilities`, `last_seen`), `platform_requirements` (`capability`,
`kinds`) and `platform_requirement_epoch`, with 018's rules: register before serving under the epoch share
lock, 10 s heartbeat on the database clock, live = seen within 30 s, re-check on every API admission and
stream re-evaluation when the epoch moves (`503` `BINARY_CAPABILITY_MISSING`), activation in one
transaction that locks the epoch `FOR UPDATE`, verifies every live instance of the required kinds and
records the requirement. 018 owns those tables, their grants and their migration.

What 029 adds is only its capability and how its use is gated:

- Capability `access-narrowing-v1`, required of kind `CONTROL_PLANE` (018 registry rule 5).
- **Activation is an operator act**: an administrator of the deployment runs 018's audited activation
  command for `access-narrowing-v1` (registry rule 4: lock the epoch `FOR UPDATE` → verify every live
  `CONTROL_PLANE` instance lists it → insert the requirement and bump the epoch → audit). No tenant
  transaction activates it.
- Until it is recorded, creating a restricted folder, changing a folder to `restricted` or creating an
  operation list is refused with `ACCESS_CAPABILITY_DISABLED`. Those transactions read
  `platform_requirement_epoch` `FOR SHARE` after their access fences and check the requirement, so they
  serialize with activation and removal.
- Removal is 018's command in reverse; 029's precondition, checked under the epoch `FOR UPDATE`, is that no
  restricted folder and no operation list remains in any tenant.

## States and transitions

```text
Folder.mode:  open ──(preview revision R, folder:manage)──▶ restricted ──(folder:manage)──▶ open
              (delete only when empty of live items)
Capability:   disabled ──(kind gate evidence + operator activation of access-narrowing-v1)──▶ enabled (per kind)
Role:         exists (revisions 1..n) ──(no assignment)──▶ removed
```

No access entity is journaled or visible to the run state machine.

## Membership interaction

- Deleting a membership cascades to assignments, group memberships, folder entries and list principals of
  that subject (and to reveal grants, as today).
- Changing a membership's role fires an `ALWAYS` `SECURITY DEFINER` trigger (`search_path = pg_catalog,
  pg_temp`, `REVOKE ALL FROM PUBLIC`, executable by nobody else) that removes the subject's direct
  assignments, group memberships, folder entries and list principals, and inserts one
  `access.revoked_on_role_change` audit record with counts only and actor `system:operator` (FR-029-024,
  pending O1441).

## Grants for the runtime role

Inside the usual `IF EXISTS (… 'sagat_app')` block: `SELECT, INSERT, DELETE` on every new access table;
`UPDATE` on the mutable columns only (`custom_roles.current_revision/description/updated_at`,
`access_groups.name/description/updated_at`, `folders.name/display_name/description/mode/revision/updated_at`,
`operation_lists.revision`); revisions are `SELECT, INSERT` only. Privileges on the registry tables are 018's
(T018-080), including the `SECURITY DEFINER` activation function that 029 calls for `access-narrowing-v1`.
Writers' `NOWAIT`
pre-locks on items (`KEY SHARE` for the placement and list foreign keys) use the existing table-level
`UPDATE` grants on `workflows`, `scripts` and `database_connections`. Membership locks use
`sagat_lock_memberships`. The runtime privilege sweep
(`tests/integration/platform-foundation/runtime_privileges.rs`) must pass with every new statement.

## Storage classification and retention

`crates/infra-postgres/storage-classification.json` gains: role, group and folder `name` (bounded slug,
`content`), `description` and `display_name` (`content`), permission arrays, levels and kinds
(`protected_system`, closed vocabulary bounded by `CHECK`). Access rows live until removed; role revisions are
bounded per role; audit records are protected system records under ADR-0027. No access row holds a payload,
a secret or a token.
